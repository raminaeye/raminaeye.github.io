Transformer Cost and Efficiency

Quadratic attention, the KV cache and streaming

On this page

This page picks up from Cross-Attention and the Q-Former. Attention scores every query against every key and blends the values with the resulting weights.

Attention, the operation this page prices.
Attention(Q, K, V) = softmax(QKT√dk)V
Q, K and V hold one row per token, dk numbers each; QKT is the n by n score table, and that table sets the bill.

A Transformer reads n tokens, each a vector of d numbers, the model width. After attention, a feed-forward network (FFN) widens each token to dff numbers and back to d. A decoder-only model like GPT generates one token per step and feeds it back in as input.

Attention's cost grows with the square of the sequence length

I count the bill in FLOPs: one multiply or one add is one FLOP, so a multiply-add costs 2. I leave out the projections, the softmax and the norms; they don't change the story.

The two bills per layer, attention against the FFN, in FLOPs.
attention FLOPs = 4n2d
Building the score table and blending the values each take n2d multiply-adds, so doubling n quadruples this bill.
FFN FLOPs = 4nddff = 16nd2
Two matrix multiplications per token, d up to dff and back; with dff = 4d, as in the original Transformer (Vaswani et al. 2017), it grows only linearly in n.
4n2d = 16nd2 at n = 4d
The crossover: shorter sequences are FFN-bound, longer ones are attention-bound.

Memory follows the same square: at 100,000 tokens, one head's score table holds 10 billion entries.

The quadratic bill, per layer.

attention: 4n2d FFN: 16nd2 your length n

The crossover always sits where n is four times d.

That bill is why long-context models restrict attention: windowed (Streaming models look back through a window), sparse (each token reads a chosen subset) or linear (rewritten so the cost grows in a straight line with the length).

The KV cache keeps past keys and values

A naive generation loop reruns the whole sequence at every step. But under the causal mask (a token never sees later tokens), a past token's keys and values never change. So real systems store them in a KV cache: each step computes only the new token's key and value, appends them, and scores the new query against everything stored.

The attention cost of step t, per layer, with and without the cache.
cost with cache = 4dt
At step t, with t tokens so far and d = 512 here, one new query is scored against t stored keys.
cost without cache = 4dt2
Without a cache all t queries are recomputed against t keys, so step t costs t times the cached step.

One decode step in code, generating one new token: 

# one decode step in one layer; the cache holds T tokens, shapes (B, h, T, d_k)
# q_new, k_new, v_new: (B, h, 1, d_k), projected from the newest token only
k_cache = torch.cat([k_cache, k_new], dim=2)   # (B, h, T + 1, d_k)
v_cache = torch.cat([v_cache, v_new], dim=2)   # (B, h, T + 1, d_k)
scores = q_new @ k_cache.transpose(-2, -1) / q_new.size(-1) ** 0.5   # (B, h, 1, T + 1)
# no causal mask: the one new query is the latest token, so every cached key is in its past
out = scores.softmax(dim=-1) @ v_cache          # (B, h, 1, d_k)

The cache trades compute for memory

The cache holds a key and a value for every token, in every head of every layer:

The size of the KV cache for one sequence.
cache bytes = 2 · L · hkv · dk · T · b
Key plus value, times L layers, hkv stored heads, dk numbers per head, T tokens and b bytes per number.
# toy config: 12 layers, 12 KV heads of size 64, 4096 cached tokens, 16-bit floats (2 bytes)
L, h_kv, d_k, T, b = 12, 12, 64, 4096, 2
per_seq = 2 * L * h_kv * d_k * T * b   # 150,994,944 bytes, about 151 MB for one sequence
batch_32 = 32 * per_seq                # 4,831,838,208 bytes, about 4.8 GB for a batch of 32

That memory also sets the speed: Shazeer (2019) notes that every decode step reloads the large key and value tensors, so memory bandwidth, not arithmetic, is the bottleneck.

Query heads can share keys and values

Multi-query attention (MQA, Shazeer 2019) keeps all h query heads but gives them one shared key head and one shared value head. Grouped-query attention (GQA, Ainslie et al. 2023) splits the query heads into g groups, and each group shares one key head and one value head.

How much of the multi-head cache grouped-query attention keeps.
GQA cache = gh · multi-head cache
Storing g key-value heads instead of h shrinks the cache by h over g; g = h is multi-head and g = 1 is MQA.
import torch.nn.functional as F
# q: (B, h, T, d_k) with h = 8 query heads; k, v: (B, g, T, d_k) with g = 2 stored KV heads
# query heads are grouped contiguously: heads 0 to 3 read KV head 0, heads 4 to 7 read KV head 1
k = k.repeat_interleave(h // g, dim=1)   # (B, 8, T, d_k): each KV head copied 4 times in a row
v = v.repeat_interleave(h // g, dim=1)   # (B, 8, T, d_k)
out = F.scaled_dot_product_attention(q, k, v, is_causal=True)   # (B, 8, T, d_k), as in multi-head

Shazeer tested MQA on WMT 2014 English to German translation with an 8-head encoder-decoder of 211 million parameters. Decoding fell from 46 to 3.8 microseconds per token on one TPUv2 (a Google accelerator), while the development-set BLEU score (translation quality, higher is better) slipped from 26.7 to 26.5.

Ainslie et al. converted a pretrained T5 XXL (a large encoder-decoder) by averaging each group's key and value heads, then trained it for 5% more steps. Averaged over summarization, translation and question answering, 8 groups scored 47.1 against 47.2 for multi-head and 46.6 for MQA, at 0.28 seconds per sample against 1.51 and 0.24.

FlashAttention does the same math with less memory traffic

A GPU has a large, slow high bandwidth memory (HBM, 40 to 80 GB on an NVIDIA A100) and a tiny, fast on-chip memory (SRAM, 192 KB on each of its 108 compute units). Dao et al. (2022) point out that standard attention writes the whole n by n score table to HBM and reads it back, and that this traffic, more than the arithmetic, sets the time.

FlashAttention computes exactly the same output in tiles: it loads one block of queries, keys and values into SRAM, scores that tile, and keeps a running maximum and sum for each row so the softmax finishes piece by piece. The full table never lands in HBM. In training's backward pass (the gradient computation) it recomputes the tiles instead of storing them, so it does more arithmetic, not less.

Dao et al. timed attention in GPT-2 medium (1024 tokens, 16 heads of size 64, batch 64, forward and backward passes, one A100):

In PyTorch, on an NVIDIA GPU, F.scaled_dot_product_attention can run a FlashAttention kernel (one fused GPU routine); its docs list FlashAttention-2 among the backends. Prefill, running the whole prompt through at once, also fills the KV cache: 

import torch.nn.functional as F
# full sequence or prefill: q, k, v are (B, h, T, d_k); is_causal builds the lower-triangular mask
out = F.scaled_dot_product_attention(q, k, v, is_causal=True)    # (B, h, T, d_k)
# one-token decode: q_new is (B, h, 1, d_k), the cache is (B, h, T, d_k). is_causal aligns its
# mask to the top-left corner, so the new query would see only key 0; turn it off here
out = F.scaled_dot_product_attention(q_new, k_cache, v_cache, is_causal=False)  # (B, h, 1, d_k)

Streaming models look back through a window

In online speech recognition or live translation the model can't see the whole sequence: the future hasn't been spoken yet. Windowed attention lets each query look back only a fixed number of frames (time slices of the input, such as 10 ms of audio) and masks everything else to negative infinity. This caps the cost: it grows in a straight line with the length. 

# windowed causal mask: each query sees the last `window_size` frames
# additive mask of shape (n, n): 0 = may attend, -inf = blocked; add it to the scores before the softmax
mask = torch.full((n, n), float("-inf"))
for i in range(n):
    start = max(0, i - window_size + 1)
    mask[i, start:i+1] = 0

Speech arrives continuously, so size the window from the smallest unit you must capture (a phoneme, one distinct sound of a language; a gesture; a word), converted to frames.

The window does not reset the model's memory: each layer's tokens already carry their own window's context, so the reach grows with depth, like a receptive field (the span of input a token can draw on).

Chunked streaming goes further: the model emits output in fixed-size chunks, and every token may see its whole chunk, so with chunk size 4, token 9 can peek at tokens 10 and 11. The price is latency: a chunk is emitted only after its last token arrives.

The chunked-streaming rule, written with positions.
j ≤ (⌊iC⌋ + 1) · C − 1
Query i reads key j up to the last position of its own chunk; ⌊ ⌋ rounds down to the chunk number, and C is the chunk size.

When a Transformer is the wrong tool

  • With very long sequences, the attention bill grows with the square of the length (Attention's cost grows with the square of the sequence length). Windowed, sparse or linear attention cuts it; FlashAttention cuts the memory traffic but not the arithmetic.
  • With small datasets, attention has no built-in sense of order or locality. A convolutional network (CNN) or an LSTM (a recurrent network with a memory cell) often wins there, because their built-in assumptions do some of the work for free.
  • With fixed-size inputs, such as a single vector or a small image, there is no sequence for attention to relate, so a small multilayer network or CNN usually does as well with far fewer parameters.
