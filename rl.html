RL Basics

No answers, just a score. The agent figures out the rest.

What if you could not show the model the answer? No labels, no examples of correct behavior, no dataset at all. Just a world, a few buttons, and a scoreboard. Would anything learn? Yes. That is reinforcement learning: the agent tries things, the world keeps score, and the strategy slowly bends toward whatever scores. It is how my own code learned to collect bananas, swing a robot arm, and rally a tennis ball.

Whenever the right move is unknown but the score is clear, RL is the tool that earns its keep: game agents that invent strategies no human taught them, robot hands that learn to grasp by dropping things ten thousand times.

The reinforcement learning loop

The whole field fits in five nouns. The state is what the agent sees right now. The action is what it can do about it. The reward is the score for what just happened. The next state is the world after the action lands. And the policy is the agent's strategy, the thing being learned, usually a neural net, a layered stack of simple units connected by adjustable numbers called weights, where learning means slowly nudging those weights.

Walk it with the banana collector, a Unity ML-Agents environment from my Value-based-methods repo. ML-Agents is the toolkit that connects a Unity game world to training code. Each step the Python side sends one of four moves; Unity steps the physics and sends back 37 numbers, the next state, plus a reward: +1 for a yellow banana, −1 for a blue one, 0 otherwise. One episode, a fixed stretch of time in the arena before the world resets, looks like this:

info = env.reset(train_mode=True)[brain_name]
state = info.vector_observations[0]           # 37 numbers
score = 0
while True:
    action = agent.act(state, eps)            # 1 of 4 moves; eps: how often it explores
    info = env.step(action)[brain_name]
    next_state = info.vector_observations[0]
    reward, done = info.rewards[0], info.local_done[0]
    agent.step(state, action, reward, next_state, done)   # nudge the policy
    state, score = next_state, score + reward
    if done:
        break

Sixteen hundred episodes of up to a thousand steps, up to 1.6 million in all, each step nudging the policy a hair toward whatever produced the +1s. Nothing in that loop knows what a banana is. The loop does not need to.

The banana collector environment

Forget the toy banana field in “One RL step on a toy banana field” for a minute; here is the real one.

Picture a square arena seen from above, scattered with yellow bananas worth +1 and blue ones worth −1, and a little collector trying to run up the score. The network never sees that picture. Its 37 numbers are the agent's own velocity plus a fan of ray-cast sensors, like a cheap lidar, each ray reporting how far away something is and which tagged object it hit. Just 37 numbers and a job. The job is a menu, not a dial: forward, back, left, right. There is no demonstration of the correct path, because nobody knows what it is.

What an episode feels like from inside

An episode opens and the agent gets 37 numbers that mean nothing yet. It picks one of four moves, and some steps later a number arrives: +1, −1, or nothing. That number is the only opinion the universe ever offers. Every other tutorial on this site starts with a dataset; this one starts with a dark room and a scoreboard. That is why learning takes over a million steps, why exploration is a real dilemma, and why the reward had better say exactly what you mean.

The solved threshold for the banana task

Solved is a line I drew: the training curve exceeds 14, about fourteen net yellows before the clock runs out, an average, not a streak. The code's early-stop bar was 17.0, which the run never hit, so all 1,600 episodes ran. I got there by running env.py in my Value-based-methods repo, with no demonstrations and no hints about which banana is the good one. The honest full arc lives on the DQN page.

How it learns: remembering what worked

Here is the whole trick. Every step, the agent notes "in this kind of situation, I tried forward, and it led to +1", and nudges its opinion of forward up a hair. Do that a million times and the opinions stop being guesses. Just try, score, remember, repeat.

That remembered score is a Q-value, Q for quality: one number for every situation-move pair.

The learning rule in plain words: old guess moves a little toward "what happened + what is coming", the reward just earned plus what the future looks like from the new situation. It is written out as an equation in “One RL step on a toy banana field”, where the stepper walks one step and draws these Q-values as opinion bars.

Epsilon: roll the dice early, go greedy late

Here is the dilemma the agent cannot escape. Its notes say forward has been the best move so far. Should it always step forward? If it does, it never learns that right might be better. If it rolls the dice every turn, it never uses what it knows. Pure exploitation freezes early. Pure exploration never cashes in.

The fix is a coin flip with a knob called epsilon, eps in code. With probability epsilon the agent picks a random move; otherwise it takes its current favorite. The knob turns itself down over training, from full dice to a one-percent floor:

if random.random() < eps:
    action = random.randrange(4)          # roll the dice
else:
    action = int(np.argmax(q_values))     # current favorite
eps = max(0.01, eps * eps_decay)          # after each episode

Decay the explorer into a hunter. The exact schedule from my run, and why the decay is load-bearing, live on the DQN page.

The memory cannot live in a lookup table

The obvious home for the scoreboard is a lookup table, one row per situation. That works for tic-tac-toe. Here the situation is 37 continuous numbers, so there are infinitely many rows and the agent never sees the same situation twice. So where can the scoreboard live? Hold that question. It is the entire DQN page.

The banana agent's training run

A real run moves through four eras: chaos, fear, the middle stretch, and the payoff. The full arc, era by era, lives on the DQN page. What matters here is the shape: one remembered step at a time, and a strategy falls out the other end.

Why this is hard: delayed credit, costly exploration, sample hunger

If the loop is that simple, why did it take the field decades? Three things about it are quietly brutal.

First, credit assignment. The agent turns left at step 40, drifts forward, and eats the banana at step 57. The +1 lands at 57, but the decision that mattered was the turn at 40. The memory smears the reward backward, fading with distance; get it wrong and the agent learns superstitions.

Sparse rewards make it worse: long stretches of steps that pay nothing at all. When a rare payoff also lands many steps after the move that earned it, the whisper of credit fades to nothing.

Second, exploration. You cannot learn what you never try, and trying costs blue bananas. Epsilon is the compromise, and tuning it is half the craft.

Third, hunger. The loop needs over a million steps, and the arm needed twenty copies of itself training in parallel. So you train in simulation, where crashing is free, then transfer the trained policy, unchanged, to the real robot. Sample inefficiency is the tax RL pays for learning from scratch.

Why copying an expert is not enough

The obvious alternative is behavior cloning: record an expert playing and train the network to copy the moves. No dice rolls, no million-plus steps. The problem is compounding mistakes: the clone only ever saw perfect play, so the first time it drifts somewhere the expert never went, it has no idea what to do and drifts further. RL is slower precisely because it lives in failure for a while, and that is what lets it recover.

Copying is fast and fragile. Reinforcement is slow and robust. When the world is predictable and an expert is available, clone. When nobody knows the right moves, as in my banana arena, you pay the million-plus steps.

One learning step in one line: nudge the picked move's opinion toward the reward plus the discounted best next opinion.
Q(s,a) ← Q(s,a) + α[r + γ·max Q(s′,a′) − Q(s,a)]
Q(s,a) is my current opinion of move a in state s. The bracket is the gap between the target, the payoff r just earned plus the discount γ times the best next opinion max Q(s′,a′) (primes mark the next state and move), and the current opinion. The learning rate α takes only a share of that gap, so one lucky step cannot rewrite the opinion, and γ keeps the future from counting as much as the payoff in hand.

Design the reward, design the agent

Two identical arenas. Two different scoreboards. Same agent machinery.

The agent learns the loophole, not the job

Here is the gotcha that bites everyone exactly once: the agent does not learn what you meant. It learns what you rewarded. If the reward has a loophole, the agent will find it and exploit it with zero shame. Below, you will watch one vibrate in a corner and never touch a banana. I learned this the embarrassing way: I once watched one of my agents do exactly that before I fixed the scoreboard.

So design the reward like the agent is a clever lawyer, because it is. Ask not "does this reward sound right" but "what is the dumbest way to score without doing the job". If you can find it in ten seconds, the optimizer will find it in ten thousand.

There is a second-order version of this trap. A reward that only arrives at the very end gives almost no signal, so people reach for shaping: small rewards for getting closer to the goal. Pay for getting closer to the banana and the agent learns to approach and back away, farming approach rewards forever without eating. Shape as little as you can, and run the dumb-test on the shaped version too.

The workflow that survives: write the dumbest reward you can, run the ten-second lawyer test on paper, train a little, and watch what the agent actually does. Then fix the reward, not the agent. Three algorithms, one loop

This page was the loop every RL method shares. Here are the three brains I built on it; each exists because the previous one hit a wall.

How each brain picks its move.
DQN: a = argmaxa Q(s, a)
The menu judge: score every move a in state s and play the biggest. Four moves, fine; four thousand, and the scoreboard becomes a joke.
DDPG: a = μ(s)
The actor μ outputs the move directly, a vector of joint torques, and a critic Q(s, a) grades the pair. No argmax over infinitely many moves.
Tennis: ai = μ(oi)
One shared actor drives both rackets from each racket i's own observations oi, i being A or B, training against itself, so the opponent improves every episode.

DQN hits the wall of discrete menus. DDPG climbs over it with an actor and a critic, a chef inventing the dish while a critic tastes. Tennis adds a world that fights back: every rally feeds both sides' experience into one shared buffer, and the quiet assumption under everything so far, that the world behaves the same way twice, breaks. Same loop all the way down, stranger brain each time.
