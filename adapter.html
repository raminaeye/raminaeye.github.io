Adapters

Fine-tuning without the fine-tuning bill.

On this page

How do you teach a giant model a new trick without retraining the whole thing? You know me, I do not like paying for compute twice.

Full fine-tuning a transformer is simple and brutal. A transformer is a stack of blocks where the positions of a sequence first exchange information and then each position is processed on its own; that stack is what this page modifies. You update all 110 million parameters, the learned numbers that make up its weights, and keep one full copy per task. Ten tasks means ten copies of the model on disk.

Worse, Adam, the optimizer that runs training, keeps extra state for every parameter:

GPU memory needed just to hold the weights and the optimizer state.
weights + Adam state ≈ P + 2P = 3P
P is the model size in parameters. Adam adds 2 numbers per parameter, a running average of its direction and of how spread out its recent steps have been. Weights plus Adam state take about three times the model size in GPU (graphics processing unit) memory, and the gradients add one more P.

And there is the quiet part nobody likes to admit: the model learns your new task and starts forgetting the old ones. That is catastrophic forgetting, and it is exactly what it sounds like.

Adapters flip the deal. Freeze the big model, bolt on tiny trainable modules, and train only those. The backbone never moves. One frozen copy, a small adapter per task, like changing lenses on a camera instead of buying a new camera body.

Bottleneck adapters add tiny trainable layers

The original idea (Houlsby et al.) is almost embarrassingly simple. Each transformer layer has an attention block, where each position mixes in information from the other positions, and a feed-forward block, which processes each position on its own. After each one you insert a small two-layer MLP (multilayer perceptron) with a bottleneck: the hidden state, the vector that carries one position through the layer, is 768 numbers wide, and you squeeze it through a 64-wide hallway and expand it back. The squeeze is the whole trick: the hallway is the only thing that learns.

They were solving the many-tasks problem. A pretrained model, one already trained on a large body of general text, fine-tunes well, but every downstream task (each later task it gets adapted to) needs its own full copy. With adapters the base stays frozen and a new task never revisits the old ones.

Transferring BERT (Bidirectional Encoder Representations from Transformers, a large pretrained language model) to 26 text classification tasks including GLUE (a standard suite of language-understanding tests), adapters land within 0.4% of full fine-tuning while adding only 3.6% parameters per task, against 100% for fine-tuning.

Here is the entire module: down project, ReLU (positive values pass unchanged, negative values become zero), up project, and add the input back so the frozen signal flows through untouched if the adapter does nothing:

class SimpleAdapter(nn.Module):
    def __init__(self, hidden_dim, bottleneck_dim):
        super().__init__()
        self.down_proj = nn.Linear(hidden_dim, bottleneck_dim)
        self.relu = nn.ReLU()
        self.up_proj = nn.Linear(bottleneck_dim, hidden_dim)

    def forward(self, x):
        return x + self.up_proj(self.relu(self.down_proj(x)))

The same module as two lines:

The adapter's whole job in two lines: squeeze the frozen features down, bend them, lift them back, and add the result as a small nudge on top.
h = Wup·σ(Wdown·x)
Read it inside out: each dot means times. The frozen input x is squeezed by Wdown, 768 numbers down to 64, bent by σ, the ReLU bend, where ReLU passes positive values through unchanged and turns negative values to zero, then lifted by Wup, 64 numbers back to 768, and the result is named h, the learned nudge.
y = x + h
y is the frozen input x plus the learned nudge h: I add it back to the input so the frozen signal flows through untouched if the adapter does nothing.

In the listing, down_proj, relu and up_proj are the first line, read inside out, and adding x back is the second.

LoRA: shrink the update, not the model

LoRA (low-rank adaptation) looks at what fine-tuning does to a weight matrix. You start with the pretrained weight W and end with W plus a big dense update, dense meaning its entries are filled in rather than mostly zero. The useful part of that update lives in a tiny subspace, a low dimensional slice of all possible updates, so LoRA learns it as two skinny matrices multiplied together.

Rebuilt from the LoRA paper's Figure 1, this picture holds the whole method.

Figure 1. Our reparametrization. We only train A and B. Reparametrization is the idea taught just above: instead of training the weight itself, you write the trained weight as the frozen W plus the learned BA detour, so the same weight gets expressed through the two small matrices. Rebuilt from Figure 1 of Hu et al. (ICLR 2022). arXiv:2106.09685

Written as one line, the effective weight is the frozen weight plus the side path:

Freeze what the model already knows and learn only the change, as a detour through a tiny bottleneck.
W + BA
Read BA as one learned update: A squeezes the input down to rank r, B lifts it back up, and the pair is added to the frozen pretrained weight W.

The r brace between the slabs is the rank, the entire budget of new parameters:

What LoRA trains for one weight matrix, against the full update.
LoRA: r(d + k)    full: d · k
d is the input size and k the output size of the weight, and r is the rank. A smaller r means far fewer new parameters and a coarser approximation of the update.
8 · (768 + 768)768 · 768 ≈ 2%
A 768 by 768 attention projection at rank 8: A and B hold 6,144 numbers each, 12,288 in all against 589,824, about 2 percent of the matrix they modify.

The update is a shadow of the original weight, and a shadow is all you need.

The two slabs start differently. A starts from random values, the N(0, σ²) on its slab: each entry is drawn from a bell curve centered at 0 with spread σ (a different σ from the ReLU bend in the adapter card above). B starts at exact zeros, so at step one the side path adds nothing and the model behaves exactly like the pretrained model.

The code wraps a frozen linear layer: self.linear is W, the side path through A then B is BA, and B starts at zero. The extra scale, alpha / rank, multiplies the side path, so turning alpha up strengthens the update without widening the rank hallway.

class LoRALinear(nn.Module):
    def __init__(self, linear, rank=8, alpha=16.0):
        super().__init__()
        self.linear = linear
        self.linear.weight.requires_grad = False   # W stays frozen
        in_dim, out_dim = linear.in_features, linear.out_features
        self.A = nn.Parameter(torch.randn(rank, in_dim) * 0.01)    # (r, d)
        self.B = nn.Parameter(torch.zeros(out_dim, rank))          # (k, r), zero so BA = 0 at init
        self.scale = alpha / rank

    def forward(self, x):
        return self.linear(x) + self.scale * (x @ self.A.T @ self.B.T)

Before serving, fold BA into W once and call the plain layer, so inference costs nothing extra:

with torch.no_grad():
    lora.linear.weight += lora.scale * (lora.B @ lora.A)   # (k, r) @ (r, d) = (k, d)
merged = lora.linear                                       # serve this, no side path

In practice you wrap the query and value projections of each attention block and leave the rest frozen. A projection is a learned matrix that turns each position into a new vector: the query says what a position is looking for, the key is what it advertises so others can match against it, and the value is what it passes along to positions that attend to it. In a BERT-base model:

model.requires_grad_(False)                  # freeze everything
for block in model.encoder.layer:            # BertModel; unfreeze your task head
    attn = block.attention.self
    attn.query = LoRALinear(attn.query, rank=8)
    attn.value = LoRALinear(attn.value, rank=8)

A quarter of one percent of the model, and it usually lands within a point of full fine-tuning on classification-style tasks. That is stupid easy and gives you a fast win.

After the merge shown above, the model runs exactly as fast as the original; bottleneck adapters cannot merge, because their nonlinearity blocks it, so their extra layers stay forever.

Compacter: cheaper matrices inside the adapter

Adapters are already small. Compacter asks whether the adapter's own matrices can be cheaper. The trick is the Kronecker product: instead of storing a big dense matrix, you store two small factors A and B and let their product stand in for it. Think of describing a tiled floor by one tile plus a repeat pattern instead of listing every tile.

The key property, written A ⊗ B: each element of A scales a whole copy of B.

One factor pair is enough to build a full adapter matrix:

A big adapter matrix from two small factors.
W768×64 = A8×8 ⊗ B96×8
W is one adapter weight matrix, ⊗ is the Kronecker product, and the subscripts are the shapes: every entry of A scales a whole copy of B.
stored: 8·8 + 96·8 = 832    dense: 768·64 = 49,152
You only store the factors, not the big matrix.

Earlier parameter-efficient methods either still used many parameters or underperformed full fine-tuning. Compacter builds each adapter matrix as a sum of these products:

Compacter's adapter weight: shared slow factors times per-layer fast factors.
W = Σi=1..n Ai ⊗ Bi
The Ai are shared "slow" weights, reused across layers; the Bi are per-layer "fast" weights; Σ adds the n products.
Bi = si tiT
Each fast factor is rank one: built from a single pair of vectors si and ti, where T lays ti flat as a row.

Training only 0.047% of the model's parameters, it matches full fine-tuning on GLUE and beats it on SuperGLUE, GLUE's harder successor suite, and in low-resource settings, where only a little task data is available.

The code below keeps the simplest case, one product with a full B. You never build the big matrix; a reshape and two small multiplications apply it:

def kron_linear(x, A, B):
    # computes x @ (A ⊗ B) without ever building A ⊗ B
    # A: (m, n), B: (p, q), x: (batch, m*p) -> (batch, n*q)
    X = x.view(-1, A.shape[0], B.shape[0])
    return (A.T @ X @ B).reshape(x.shape[0], -1)

class CompacterAdapter(nn.Module):
    def __init__(self, d_model=768, bottleneck=64, n=8):
        super().__init__()
        self.A = nn.Parameter(torch.randn(n, n) * 0.01)                       # shared factor
        self.B_down = nn.Parameter(torch.randn(d_model // n, bottleneck // n) * 0.01)
        self.B_up = nn.Parameter(torch.randn(bottleneck // n, d_model // n) * 0.01)
        self.act = nn.ReLU()

    def forward(self, x):
        h = self.act(kron_linear(x, self.A, self.B_down))   # 768 -> 64
        return x + kron_linear(h, self.A, self.B_up)        # 64 -> 768

Adapter limitations: latency, rank tuning, and overfitting

  • Unmerged adapters cost latency. Two extra matmuls, matrix multiplications, per block, every token, one unit piece of the input sequence, forever. Bottleneck adapters cannot merge, so they stay in the graph.
  • On big datasets, full fine-tuning still wins sometimes. Adapters shine when data or compute is scarce, not when you have both in abundance.
  • Adapt query and value first, skip the rest. Most of the gain comes from the attention projections; adapters on the feed-forward layers add parameters for less return on many tasks.
  • Soft prompts look sad on small models. Prompt and prefix tuning, prefix tuning being the one that adds extra learned key and value vectors set in front of the sequence in each attention layer, need a big frozen model to steer. On base-size models, LoRA beats them cleanly.
  • Frozen does not mean forget-proof. The backbone is safe, but the adapter can still overfit 500 examples, learning those few examples too closely instead of the pattern that carries to new examples. Validate like always.

Other ways to shrink the update

LoRA and Compacter are not the only way to keep the update small.

  • Prompt tuning trains a soft prompt of about 20K parameters. On base-size models it trails LoRA on SST-2, and it only pays off with a much bigger frozen model to steer.
  • Prefix tuning prepends learned keys and values to each attention layer, a similar parameter budget, with the same catch: it needs a big frozen model to steer.

Next: quantize the frozen 98%

Adapters shrink what you train. Quantization, storing each weight with fewer bits per number instead of at full precision, shrinks what you store: the frozen 98 percent of the model still has to live in memory at inference time. The quantization tutorial picks up where this one ends.
