Tool Calls Written as Code

Code lets later tool calls reuse earlier results as variables.

1 JSON calls cannot share results

A multi-step task needs more than one tool call, each needing what the last one found. A JSON call is a fixed object, a tool name and its arguments, and its result comes back as text the next call cannot point at: the only way to use it is to copy it into the next call or ask the same question again from scratch.

Training here is GRPO with a dynamic sample queue: each training step samples a few fresh rollouts per task, filling the rest of the group from the queue, so the whole group is not regenerated from scratch every step. In a rollout, the state is the variables the code has set so far: what one step stored, the next step reads. This page is the second of the three stages the survey of agentic reinforcement learning maps out: copying tool use, optimizing outcomes by reward, and long multi-turn tool use, still open.

Copying costs more than length. A copied result is dead text: the next call cannot filter it, sort it, or pick one item out of it without the model reading and writing it all again. A three-step task pays for the first result at every later step, each copy risking a dropped or changed detail.

2 Code as the tool language

Code replaces the fixed call object with a program. Each step is a short thought in words, then a block of code that calls tools and runs, landing its result in a variable the next block reads. The model writes the program as it goes, one block per step, and the running program is the workflow.

A variable is a name that holds a value: once a step stores a result under a name, later steps can use the name instead of the value. That is the whole trick. Filtering, picking one item, and passing a result on are ordinary code, not extra calls: a search result can feed a file reader, a file read an image check.

Each step runs in the same Thought, Code, Observation cycle the ReAct page teaches, with code in place of the fixed action: the thought says what to do next, the code does it, and the observation, the tool response, comes back for the next thought. The paper's tools are web search, a page reader, a file parser, an image reader, and a final answer call.

One step: the thought first, then the code that acts on it.

# thought: find the dam first
links = web_qa("tallest dam")
page = visit_qa(links[0], "where?")
final_answer(page)
  1. 1 The comment stands for the thought the model writes in words before the code: what this step is for.
  2. 2 The first call stores its result in the variable links. web_qa is the web search tool.
  3. 3 The second call reuses links instead of searching again: links[0] is the first result. visit_qa is the page reader.
  4. 4 The answer is submitted from the variable, not retyped. final_answer ends the task.

3 The reward in three parts

This section leans on the GRPO page for the group comparison and on the ToRL page for the code rollout, including the group relative advantage, how much better one answer scored than the group mean. What it teaches is the one change code forces on the loss and the three-part reward judging the whole trajectory.

3.1 The mask

The rollout mixes two authors: the model's own tokens sit next to tool observations the model never wrote. The loss is the number training pushes down; only tokens in it are learned from. The mask marks every token by its author, so the loss trains on the model's words only.

Equation 1. The masking indicator. One for the model's own tokens, zero for tool observations.
\(\displaystyle \begin{aligned}&\htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{M}}(\htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{y_t}}) = \\&\begin{cases} 1, & \text{model token} \\ 0, & \text{tool observation} \end{cases}\end{aligned}\)
The mask sorts tokens by author. \(y_t\) is token \(t\) of the rollout; \(M(y_t)\) is 1 when the model wrote that token, a thought or a line of code, and 0 when it came back from a tool.
\(M(y_t)\) the mask \(y_t\) one token
The paper introduces this masking in section 3.1, so only tokens the model generated enter the policy gradient.

3.2 The masked loss

The base objective is the one the GRPO page teaches; this section shows only the masked form. The change is in two places: every token sum runs only over tokens with mask 1, and the count dividing the sum counts only those tokens. The ratio, clip, and group advantage are the ones that page teaches.

Equation 2. The token level GRPO loss with response masking. The group loss from the GRPO page, summed over the model's tokens only.
\(\displaystyle \begin{aligned}&\htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{\mathcal{L}_{\mathrm{GRPO}}}}(\htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{\theta}}) = \frac{1}{\htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{G}}} \sum_{i=1}^{\htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{G}}} \\&\quad \frac{1}{\sum_t \htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{M}}(\htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{y_{i,t}}})} \\&\quad \sum_{t: \htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{M}}(\htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{y_{i,t}}})=1} \\&\quad \min \big( \htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{r_{i,t}^{\mathrm{ratio}}}} \htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{\hat{A}_{i,t}}}, \\&\quad \operatorname{clip}(\htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{r_{i,t}^{\mathrm{ratio}}}}, \\&\quad 1-\epsilon, 1+\epsilon) \htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{\hat{A}_{i,t}}} \big) \\&\quad - \htmlClass{eqt sym-wait}{\htmlStyle{color:var(--sym-wait)}{\beta}}\, \htmlClass{eqt sym-wait}{\htmlStyle{color:var(--sym-wait)}{\mathbb{D}_{\mathrm{KL}}}} \big[ \htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{\pi_\theta}} \,\|\, \htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{\pi_{\mathrm{ref}}}} \big]\end{aligned}\)
The masked group loss, pushed down in training. \(G\) is the group size, how many rollouts the model writes to the same task; \(i\) counts the rollouts in the group; each rollout is scored by the same masked clipped term, with its own mask \(M(y_{i,t})\) and its own advantage \(\hat{A}_{i,t}\), how much better rollout \(i\) scored than the group mean, as taught on the GRPO page; \(r_{i,t}^{\mathrm{ratio}}\) is the ratio from the GRPO page, the new chance of token \(t\) divided by the chance under the policy that wrote the rollout; \(\operatorname{clip}\) holds the ratio between \(1-\epsilon\) and \(1+\epsilon\); the KL term at the end is the drift penalty, with \(\beta\) setting how strongly it counts, \(\mathbb{D}_{\mathrm{KL}}\) measuring how far the policy \(\pi_\theta\) drifted from the reference model \(\pi_{\mathrm{ref}}\).
\(G\) the group size \(M(y_{i,t})\) the mask \(r_{i,t}^{\mathrm{ratio}}\) the ratio \(\hat{A}_{i,t}\) the group advantage \(\beta\) the drift weight
The paper writes this loss as its equation 1, in section 3.1, with the masking factor as the new part: the token average divides by the count of the model's own tokens, not the whole rollout length.

3.3 The answer reward

Most real tasks have no single right string: an open-ended answer can be right in different words. So a small language model, a judge model used as a grader rather than the policy being trained, grades the predicted answer against the reference on accuracy, completeness, relevance and precision: correct, partly correct, or wrong.

Equation 3. The answer reward. Full credit, half credit, or none, as the judge grades it.
\(\displaystyle \begin{aligned}&\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R_{\mathrm{answer}}}} = \\&\begin{cases} 1, & \text{correct} \\ 0.5, & \text{partly correct} \\ 0, & \text{wrong} \end{cases}\end{aligned}\)
The answer part of the reward. \(R_{\mathrm{answer}}\) is 1 when the judge grades the predicted answer correct, 0.5 when it grades it partly correct, and 0 when it grades it wrong.
\(R_{\mathrm{answer}}\) the answer reward
The paper writes this reward as its equation 2, in section 3.3.

3.4 The code quality rewards

Two more rewards judge the code itself: the parse reward is the share of blocks that parse, and the execution reward is the share of parsed blocks that run without errors. A trajectory that lands the answer by luck with broken code earns the answer reward and little else.

Equation 4. The parse and execution rewards. The share of code that parses, and the share of that code that runs.
\(\displaystyle \begin{aligned}&\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R_{\mathrm{parse}}}} = \frac{\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{N_{\mathrm{parsed}}}}}{\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{N_{\mathrm{total}}}}}, \\&\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R_{\mathrm{exec}}}} = \frac{\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{N_{\mathrm{executed}}}}}{\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{N_{\mathrm{parsed}}}}}\end{aligned}\)
The code quality rewards. \(N_{\mathrm{total}}\) is the number of code blocks the model wrote across the steps; \(N_{\mathrm{parsed}}\) is how many of them parse, with no syntax errors; \(N_{\mathrm{executed}}\) is how many of the parsed blocks run without errors; \(R_{\mathrm{parse}}\) is the share that parses; \(R_{\mathrm{exec}}\) is the share of parsed blocks that run.
\(R_{\mathrm{parse}}\) the parse reward \(R_{\mathrm{exec}}\) the execution reward \(N_{\mathrm{total}}\) blocks written \(N_{\mathrm{parsed}}\) blocks that parse \(N_{\mathrm{executed}}\) blocks that run
The paper writes these rewards as its equation 3, in section 3.3.

3.5 The total reward

The total reward is the answer reward plus the two code rewards, each weighted. The weights are fixed numbers the paper sets, unchanged through training. Clean runnable code earns a real share, but never outweighs the answer itself.

Equation 5. The total reward. The answer reward plus the two code quality terms.
\(\displaystyle \begin{aligned}&\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R}} = \htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R_{\mathrm{answer}}}} + \htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{\lambda_{\mathrm{parse}}}} \htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R_{\mathrm{parse}}}} \\&\quad + \htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{\lambda_{\mathrm{exec}}}} \htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R_{\mathrm{exec}}}}\end{aligned}\)
The whole reward for one trajectory. \(R\) is the total reward; \(R_{\mathrm{answer}}\) is the answer reward from Equation 3; \(R_{\mathrm{parse}}\) and \(R_{\mathrm{exec}}\) are the code rewards from Equation 4; \(\lambda_{\mathrm{parse}}\) and \(\lambda_{\mathrm{exec}}\) are the weights on the two code rewards, and the paper sets both to 0.3 (paper section 3.3).
\(R\) the total reward \(\lambda_{\mathrm{parse}}\) the parse weight \(\lambda_{\mathrm{exec}}\) the execution weight
The paper writes this reward as its equation 4, in section 3.3.

4 Training cheaply

Tool calls are slow: each rollout step waits on a search engine, a file reader, or a page load, and a GRPO group needs many rollouts per task, so training from scratch would spend most of its time waiting on tools. The queue is the fix: each task keeps a cache of past trajectories, and each training step draws a few fresh ones, filling the rest of the group from the cache and dropping the oldest as new ones arrive.

The queue also filters by difficulty: it keeps only trajectories in the moderate range, a pass rate, the share of sampled answers that were right, from 0.2 to 0.8 (paper section 3.2). Tasks solved nearly always teach nothing new, and tasks solved almost never teach nothing either, so training focuses on tasks the model nearly gets right.

5 Practice

Each step costs one code execution and waits while the tools run, at training and at inference. A rollout runs at most ten steps per task (paper section 4.1), so the cost per task stays bounded.

The total reward is answer plus 0.3 parse plus 0.3 execution (paper section 3.3). Training runs GRPO over groups of rollouts to the same task, the dynamic queue reusing past trajectories (paper sections 3.1 and 3.2).

The official repository is github.com/YBYBZhang/Tool-R1, verified live: the official PyTorch implementation, carrying the project README.

6 Failure modes

Four failures cover most of what goes wrong, each with a cause, a visible symptom, and a fix.

6.1 Code that does not parse

Cause: the model writes a block with a syntax slip, a missing bracket, a mistyped name. Symptom: the step produces no observation and the parse reward falls. Fix: the parse reward pays for blocks that parse (paper section 3.3), steering training toward well-formed code.

6.2 Code that runs and crashes

Cause: a wrong argument, or a variable read before the step that sets it. Symptom: the observation carries an error, and the execution reward falls. Fix: the execution reward pays for blocks that run cleanly, and the error returns as the observation for the next thought to repair the call (paper sections 3.1 and 3.3).

6.3 The judge lets a near miss through

Cause: the answer reward grades open-ended answers, so a partly right answer earns partial credit. Symptom: the model settles for close answers instead of checking them against the tools. Fix: partial credit stays below full credit, and the code rewards pay only for code that parses and runs, so a checked answer beats a guessed one (paper section 3.3).

6.4 The queue goes stale

Cause: cached trajectories come from an older policy. Symptom: updates push toward moves the current policy no longer makes, so learning wobbles. Fix: each step drops the oldest entries as fresh ones arrive, keeping only trajectories in the moderate range (paper section 3.2).
