1 Full fine-tuning is too heavy

How do you teach a large model a new task without retraining the whole thing?

Full fine-tuning updates every parameter of a transformer, a stack of blocks where the positions of a sequence first exchange information and then each position is processed on its own, and keeps one full copy per task. This page uses RoBERTa-base as its example model: 12 layers with hidden size 768.

Worse, Adam, the optimizer that runs training, keeps extra state for every parameter:

GPU memory needed just to hold the weights and the optimizer state.
\(\displaystyle \htmlStyle{color:#2c3e50}{P} + \htmlStyle{color:#b45309}{2P} = 3\htmlStyle{color:#2c3e50}{P}\)
The weights take \(P\), the model size in parameters, and the Adam state takes \(2P\). Adam adds 2 numbers per parameter, a running average of its gradient and a running average of its squared gradient. Weights plus Adam state take about three times the model size in GPU memory, and the gradients add one more \(P\).

And the model learns the new task and starts forgetting the old ones. That is catastrophic forgetting.

Adapters do the opposite: freeze the big model, add small trainable modules, and train only those (Figure 1).

Adapters train like ordinary fine-tuning, on every step of the new task's data, and the state a task leaves behind is its adapter (Figure 2). The gradient still has to pass through the frozen backbone to reach the adapters. At serving time the adapter layers stay in every forward pass, so they cost two extra matrix multiplications per block per token; the method that folds away instead is LoRA, taught on the LoRA and QLoRA page.

2 Bottleneck adapters

The original idea (Houlsby et al. 2019) is simple. Each transformer layer has an attention block, where each position mixes in information from the other positions, and a feed-forward block, which processes each position on its own. After each one you insert a small two-layer MLP (multilayer perceptron) with a bottleneck: the hidden state, the vector that carries one position through the layer, is 768 numbers wide, and the adapter projects it down to 64 numbers and back up to 768.

With adapters the base stays frozen and a new task never revisits the old ones.

Transferring BERT (Bidirectional Encoder Representations from Transformers, a large pretrained language model) to GLUE (a standard suite of language-understanding tests), adapters nearly match full fine-tuning while training only a small share of parameters per task.

The listing is the whole module, kept whole at 15 lines; input and output are both hidden_dim wide.

import torch.nn as nn

class SimpleAdapter(nn.Module):
    def __init__(self, hidden_dim, bottleneck_dim):
        super().__init__()
        h, m = hidden_dim, bottleneck_dim
        self.down_proj = nn.Linear(h, m)
        self.relu = nn.ReLU()
        self.up_proj = nn.Linear(m, h)

    # x: (batch, seq, hidden_dim)
    def forward(self, x):
        z = self.relu(self.down_proj(x))
        # residual: frozen x plus update
        return x + self.up_proj(z)
  1. 1down_proj to the bottleneck, ReLU (negatives become 0, positives pass), up_proj back up.
  2. 2forward adds the input back, so the frozen signal passes untouched if the adapter does nothing.

A wider bottleneck adds capacity and parameters; a narrower one is cheaper but can underfit. The bottleneck width is picked per task, wider for larger tasks, and one fixed width costs little on average.

Adapters start near the identity: the projection layers start near zero and the adapter carries its own internal skip connection, so the frozen model is almost unchanged at step one (the paper, sections 2 and 2.1).

The parameter count below uses a hidden size of 768 and a bottleneck of 64; a bias is one learned number added to each output of a projection, on top of its weights.

Training only a small share of the model leaves the rest where pretraining put it. That is why the model does not forget.

The frozen input \(x\) is projected down by \(W_{\text{down}}\) to the bottleneck, passed through \(\sigma\), then lifted by \(W_{\text{up}}\); the result \(h\) is the learned update. The 64-number bottleneck is what keeps the adapter cheap: both matrices are thin, so the parameter count stays far below a full square matrix. 3 Compacter: cheaper matrices inside the adapter

Adapters are already small. Compacter (Karimi Mahabadi et al. 2021) asks whether the adapter's own matrices can be cheaper. Compacter uses the Kronecker product: instead of storing a big dense matrix, store two small factors \(A\) and \(B\) (Compacter's own, not LoRA's) and let their product stand in for it.

The idea comes from a way of building big matrices from shared small pieces.

In the Kronecker product \(A \otimes B\), each element of \(A\) scales a whole copy of \(B\).

One factor pair is enough to build a full adapter matrix:

A big adapter matrix from two small factors.
\(\displaystyle \htmlStyle{color:#2c3e50}{W_{768\times64}} = \htmlStyle{color:#b45309}{A_{8\times8}} \otimes \htmlStyle{color:#2471a3}{B_{96\times8}}\)
\(W\) is one adapter weight matrix (not the frozen \(W\) of LoRA), \(\otimes\) is the Kronecker product, and the subscripts are the shapes: every entry of \(A\) scales a whole copy of \(B\).

Only the factors are stored, far fewer numbers than the dense matrix holds.

Compacter builds each adapter matrix as a sum of these products:

Compacter's adapter weight: shared slow factors times per-layer fast factors.
\(\displaystyle \htmlStyle{color:#2c3e50}{W} = \sum_{i=1}^{n} \htmlStyle{color:#b45309}{A_i} \otimes \htmlStyle{color:#2471a3}{B_i}\)
The \(A_{i}\) are shared "slow" weights, reused across layers, so one set serves every layer and changes slowly; the \(B_{i}\) are per-layer "fast" weights, free to adapt quickly to each layer; \(\sum\) adds the \(n\) products.
\(\displaystyle \htmlStyle{color:#2471a3}{B_i} = \htmlStyle{color:#5d6d7e}{s_i} \htmlStyle{color:#5d6d7e}{t_i^{\mathsf{T}}}\)
Each fast factor is rank one, built from a single pair of vectors \(s_{i}\) and \(t_{i}\), where the superscript T, the transpose, lays \(t_{i}\) flat as a row.

Compacter trains a tiny share of the parameters and still matches full fine-tuning.

Use Compacter when the parameter budget is tighter than a plain bottleneck adapter allows, for example when serving many tasks or when only a little task data is available.

The listing uses one product with a full \(B\); Compacter sums \(n\) of them and makes each \(B\) rank one. The big matrix is never built.

def kron_linear(x, A, B):
    # apply the Kronecker product without building it
    # A: (m, n), B: (p, q), x: (batch, m*p)
    m, p = A.shape[0], B.shape[0]
    X = x.view(-1, m, p)
    Y = A.T @ X @ B
    # (batch, n*q)
    return Y.reshape(x.shape[0], -1)
  1. 1Reshapes each input row into an \(m\) by \(p\) matrix.
  2. 2Multiplies by the two small factors and flattens back: the same result as the full Kronecker product.

The cost is that the weight matrix is no longer fully free; it has to factor this way.

4 Other parameter-efficient fine-tuning methods

Bottleneck adapters and Compacter are not the only way to keep the update small.

MethodWhat trainsWhen it helps
Prompt tuning (Lester et al. 2021)A short soft prompt: learned vectors placed in front of the real wordsVery large frozen models; it closes the gap to fine-tuning as models exceed billions of parameters
Prefix tuning (Li and Liang 2021)Learned key and value vectors set in front of the sequence in every attention layerGeneration tasks on large frozen models
BitFit (Ben Zaken et al. 2022)Only the bias termsThe smallest budget: only the biases train

AdapterDrop (Rücklé et al. 2021) is a bottleneck adapter that drops the adapters in the lowest layers; it trains the rest and helps when serving speed matters.

LoRA is the contrast: instead of adding a module, it changes the weight itself with a low-rank update that folds away at serving.

5 Adapters in practice

Adapters plug in after the attention block and after the feed-forward block, two per layer, in every layer of the Transformer block. Training runs the usual loop over the new task's data, with the optimizer holding only the adapter parameters.

Training is the usual loop with one filter, so the optimizer keeps no state for the backbone. The learning rate is a placeholder.

for name, param in model.named_parameters():
    # all else frozen
    param.requires_grad = "adapter" in name
ps = model.parameters()
trainable = [p for p in ps if p.requires_grad]
optimizer = torch.optim.AdamW(trainable, lr=1e-4)
  1. 1Freezes every parameter whose name lacks "adapter".
  2. 2Gives the optimizer only the trainable adapter parameters.

The paper also trains per-task layer-normalization parameters and the classification head (the paper, section 2), so the listing above is a simplified freeze filter showing the adapter-only core, not the paper's full training setup.

A step costs a full forward and backward pass through the frozen backbone, with gradients and Adam state only for the trained parameters (adapters, layer norms, head). At serving time the extra layers stay in every forward pass, so serving is slower than the frozen model alone.

The bottleneck sizes the paper uses per task are listed in section 2. For an implementation, the adapters library is AdapterHub.

6 What breaks and what to watch

  • Unmerged adapters cost latency. Cause: the nonlinearity blocks merging. Symptom: two extra matrix multiplications per block per token, slower serving. Fix: accept it for small models, or use a mergeable method, LoRA and QLoRA.
  • Full fine-tuning still wins sometimes on big datasets. Cause: with enough data the full model can use all of its capacity while the adapter bottleneck caps what it can learn. Symptom: adapter accuracy plateaus below full fine-tuning as data grows. Fix: use full fine-tuning when data and compute allow; adapters shine when data or compute is scarce.
  • The adapter can still overfit a small dataset. Cause: the frozen backbone is safe, the adapter is not. Symptom: training accuracy up, held-out accuracy down. Fix: validate, narrow the bottleneck.

Tips: bottleneck width is the main dial, wider adds room to learn and costs more, narrower is cheaper and can underfit; validate like always.

What if the update itself could fold away, so serving costs nothing extra? That is LoRA, taught on the LoRA and QLoRA page.
