ToRL: Discovering Tool Use by Reward Alone

A tool result that disagrees with hand reasoning is a signal, not noise.

1 Learning tool use with no teacher

The pages before this one taught tool use by showing the model how. Prompting shows worked examples, and fine tuning trains on traces a teacher built. Both copy a pattern someone already chose. This page drops the teacher entirely: the model starts from a base model, a model with no training after pretraining, and learns when to use a tool from reward alone.

Training is reinforcement learning directly from the base model, one rollout per problem. A rollout is one full attempt at one problem, from the question to the final answer. The reasoning, the code and the outputs so far are the state within one problem: what the model has tried and what the interpreter said. Nothing carries between problems.

That fits the three stages of tool-use learning the survey of agentic reinforcement learning maps out. The first stage copies tool use, by prompting or fine tuning. The second stage, where this page sits, optimizes outcomes: the reward judges the answer, and the model discovers for itself when a tool helps. The third stage, tool use across long multi-turn tasks, is still the open frontier.

The field where this bites hardest is contest math, problems with exact answers where a single miscalculation sinks an otherwise sound solution. A code interpreter changes that. It is a sandbox, an isolated place where code runs safely, that executes code and returns what the code prints, or the error when it fails. Writing the arithmetic as code hands the fragile part to a machine that does not slip, and the model keeps the part it is good at: deciding what to compute.

2 The rollout that pauses for code

The rollout has four moves. The model thinks in words, writes a block of code, the sandbox runs it, and the model reads the result back before thinking on. The loop repeats until the model writes its final answer.

Code goes between markers that say where it starts and ends. When the closing marker appears, generation pauses, the code is parsed out and sent to the sandbox, and the sandbox output is pasted back between output markers for the model to read. A rollout is a chain of thoughts, code blocks and interpreter outputs, ending in the final answer. That chain is the trajectory, and it is the object the equations below describe.

The pause is the point. Generation stops at the closing code marker, so the model never writes past a result it has not seen. The interpreter output joins the reasoning as feedback, not as an appendix at the end, and the next thought starts from what the code actually did. That is the same shape as the Thought Action Observation loop, with a code block as the action and the interpreter output as the observation. When code fails, the error message comes back too, so the model can see what broke.

2.1 The trajectory

Each step of the rollout adds three pieces to the history: a stretch of reasoning, a block of code, and the output that code produced. The trajectory after step k is the whole history so far, and the next step is written given the question and that history.

Equation 1. The trajectory. The history after step k: reasoning, code and output, step by step.
\(\displaystyle \begin{aligned}&\htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{s_k}} = \{ \htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{r_1}}, \htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{c_1}}, \htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{o_1}}, \dots, \\&\; \htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{r_k}}, \htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{c_k}}, \htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{o_k}} \}\end{aligned}\)
The trajectory is everything so far. \(s_k\) is the history after step \(k\); \(r_i\) is the reasoning in words at step \(i\); \(c_i\) is the code written at step \(i\); \(o_i\) is the output that code produced.
\(r_i\) reasoning in words \(c_i\) code written \(o_i\) output of the code \(s_k\) the history so far
The paper writes this trajectory as its equation 1, in section 2.2.

2.2 One step of the rollout

At each step the model writes the next reasoning and the next code block given the question and the history, the sandbox runs the code, and the three new pieces join the history. The model is the policy, its current way of choosing what to write next, and the sandbox is the interpreter.

Equation 2. The step update and the interpreter step. The model writes the next step, the sandbox runs it, and the history grows.
\(\displaystyle (\htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{r_k}}, \htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{c_k}}) = \htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{M}}(\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{Q}} \oplus \htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{s_{k-1}}})\)
The model writes the next step. \(M\) is the model; \(Q\) is the question; \(s_{k-1}\) is the history before this step; \(\oplus\) joins the question and the history together.
\(\displaystyle \htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{o_k}} = \htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{I}}(\htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{c_k}})\)
The interpreter step. \(I\) is the code interpreter, the sandbox; it runs the code \(c_k\) and returns the output \(o_k\).
\(\displaystyle \htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{s_k}} = \htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{s_{k-1}}} \oplus \htmlClass{eqt sym-x}{\htmlStyle{color:var(--sym-x)}{r_k}} \oplus \htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{c_k}} \oplus \htmlClass{eqt sym-y}{\htmlStyle{color:var(--sym-y)}{o_k}}\)
The history grows. The new reasoning, code and output are joined onto the history, and the next step starts from the longer history.
\(M\) the model \(I\) the interpreter \(Q\) the question \(\oplus\) joined together
The paper writes these as its equations 2, 3 and 4, in section 2.2.

The sandbox output is left out of the loss, the number training pushes down: tokens in the loss are the ones the model learns from, so masking the feedback means the model never learns to write interpreter output itself.

for problem, answer in problems:
  trace = model.generate(problem)
  while trace.has_code_block():
    code = trace.last_block()
    out = sandbox.run(code)
    trace.add(out, feedback=True)
    trace = model.resume(trace)
  reward = 1 if matches(
    trace.answer, answer) else -1
  loss = grpo_loss(trace, reward,
    mask=trace.feedback_tokens)
  loss.backward()
  1. 1 The loop pauses at each code block: the block goes to the sandbox and its output joins the trace before the model writes on. problems are the training questions with known answers; trace is the rollout so far; sandbox is the code interpreter.
  2. 2 The reward judges only the final answer: plus one when it matches, minus one otherwise. matches is the equivalence check from Equation 3.
  3. 3 The loss learns from the model’s own words only: interpreter output is masked out of it. grpo_loss is the group update taught on the GRPO page; feedback_tokens are the interpreter’s words in the trace.

3 The reward

This section leans on the GRPO page for the group comparison that turns rewards into an update. In GRPO, the model writes a group of answers to the same question, and each answer’s advantage is how much better it scored than the group’s mean. The objective itself is taught there, not here.

3.1 The outcome reward

The reward judges only the final answer. A program checks whether the predicted answer matches the known one, and the model earns plus one when it matches and minus one otherwise. Nothing is paid for code that merely runs, and nothing is paid for the steps in between: the reward cares only about where the rollout lands.

Equation 3. The outcome reward. Plus one for a correct final answer, minus one otherwise, with nothing paid for code that merely runs.
\(\displaystyle \begin{aligned}&\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R(a, \hat{a})}}=\\&\begin{cases} 1, & \text{is\_equivalent}\\ & (a, \hat{a}) \\ -1, & \text{otherwise} \end{cases}\end{aligned}\)
The whole reward is the final answer. \(a\) is the known answer; \(\hat{a}\) is the predicted answer; \(\texttt{is\_equivalent}\) is the program check that the two match in meaning, so the same value written another way still counts; \(R\) is the reward.
\(R(a, \hat{a})\) the reward \(a\) the known answer \(\hat{a}\) the predicted answer
The paper writes this reward in section 2.3.3, with correct answers earning 1 and incorrect answers earning -1.

One training step runs the loop of section 2, scores the answer, and updates from the reward. The group comparison on the GRPO page decides which rollouts get pushed up: a rollout that lands the answer earns more than the group mean, so the update pushes the policy toward the moves that produced it, including the code calls along the way.

3.2 The executability penalty that did not help

The interpreter already reports whether code ran, so the paper tried paying for that too: a response with code that does not run loses half a point. The idea was to teach the model to write code that works. It did not help, and the paper says why it might hurt: a penalty on broken code can push the model toward overly simple code that runs but solves nothing.

Equation 4. The optional executability penalty. Half a point off when the code does not run, on top of the outcome reward.
\(\displaystyle \htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R_{\mathrm{total}}}} = \htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R(a, \hat{a})}} + \htmlClass{eqt sym-wait}{\htmlStyle{color:var(--sym-wait)}{R_{\mathrm{exec}}}}\)
The total reward is the outcome reward plus the executability term. \(R(a, \hat{a})\) is the outcome reward from Equation 3; \(R_{\mathrm{exec}}\) is the executability term below.
\(\displaystyle \begin{aligned}&\htmlClass{eqt sym-wait}{\htmlStyle{color:var(--sym-wait)}{R_{\mathrm{exec}}}} =\\&\begin{cases} 0, & \text{code runs} \\ -0.5, & \text{code does not run} \end{cases}\end{aligned}\)
The penalty charges only for code that fails to run. It says nothing about whether the code is right: code that runs and computes the wrong thing pays no penalty, and code that fails pays half a point even when the reasoning around it was sound.
\(R_{\mathrm{total}}\) the total reward \(R_{\mathrm{exec}}\) the executability term
The paper writes this penalty in section 2.3.3, then reports in section 3.3.2 that adding it did not improve performance, and the default experiments keep only the outcome reward.

The lesson is that a reward for running code is a reward for easy code. The default setup leaves the penalty out, so the only thing that pays is the right answer, and the model is free to write ambitious code, fail, and learn from the error.

4 The tool call cap

Every code block costs a sandbox run, and while the sandbox runs, the training GPUs wait. The more the model calls the tool, the slower each training step gets. So the rollout carries a cap, C, the maximum number of tool calls the model can make in one response. Once the cap is reached, further code execution requests are ignored, and the model must finish in pure text.

The cap is the setting that trades accuracy against speed. A higher cap lets the model check more and recheck when answers disagree, but each extra call waits on the sandbox. The default cap is one call per problem, and the paper tests caps of zero, one and two. At zero the model never touches the tool at all, which is plain reinforcement learning without code. 5 What emerges

Nothing in the reward asks for any of this. It pays for right answers only. Yet as training runs, the model starts using code on more problems, the code it writes runs cleanly more often, and code that does nothing useful fades away. Three behaviors emerge from the reward alone, with no worked example ever showing them.

The first is cross-checking: the model works a problem out by hand, checks the same problem in code, and when the two disagree it treats the disagreement as a signal to recheck, not as noise to ignore. The second is self-regulation: code that fails or leads nowhere gets written less, because rollouts full of dead code land wrong answers and earn minus one. The third is adaptation: the model picks between hand reasoning and code depending on the problem, computing by hand where that is enough and calling the tool where checking matters.

6 Practice

Each code block costs one interpreter run, at training and at inference, and the training step waits on the sandbox while it runs (paper section 2.3.1). More calls mean more checking, and a slower step.

The headline setting is the tool call cap C, tested at 0, 1 and 2 (paper Table 4). The default cap is one call per problem (paper section 3.1). Training runs in the veRL reinforcement learning framework with Sandbox Fusion as the code interpreter (paper section 3.1), and the sandbox outputs are masked from the loss (paper section 2.3.2).

The official repository is github.com/GAIR-NLP/ToRL, verified live. It carries the training pipeline, the dataset of questions and the trained models.

7 Failure modes

Four failures cover most of what goes wrong. Each has a cause, a visible symptom, and a fix.

7.1 The tool never gets called

Cause: the cap is zero, or it is spent before the step where checking matters. Symptom: the model reasons in words only even where code would settle the question. Fix: raise the cap, the default is one call per problem (paper section 3.1); the slider in Figure 4 shows what each cap allows.

7.2 The first code output is trusted blindly

Cause: the model treats the first output as the answer instead of one check among others. Symptom: a wrong code result is copied straight into the final answer. Fix: the recheck behavior the reward teaches (Figure 3); a rollout that stops at a disagreement and picks one side blindly earns minus one when it picks wrong.

7.3 Overly simple code from the executability penalty

Cause: penalizing code that does not run rewards code that is easy to run. Symptom: trivial code that runs and solves nothing. Fix: leave the penalty out, as the default experiments do (paper section 3.3.2); only the right answer pays.

7.4 Interpreter output mistaken for reasoning

Cause: interpreter text sits inside the trace next to the model’s own words. Symptom: the model quotes an output as if it derived it, or tries to write interpreter-style text itself. Fix: mask interpreter tokens from the loss (paper section 2.3.2), so training never teaches the model to produce them.

8 What comes next

ToRL shows that a model can discover tool use with no teacher at all, straight from a base model, when the reward pays only for the right answer. The tool here was a code interpreter, a calculator the model can program. The next page changes the tool: Search as a Tool Learned by Reward teaches the model to call a search engine when what it needs is not in its weights but out in the world.
