The KV Cache

When a model writes one token at a time, the keys and values of earlier tokens never change, so it stores them and computes only the new token's.

1 A naive loop redoes the whole text every step

A chat model answering a long prompt writes one token, appends it, and runs again. A naive loop feeds the whole text back in each time, so every step rebuilds the full score table to get one new row.

2 Past keys and values never change, so keep them

Under the causal mask a token never sees later tokens, so the keys and values of earlier tokens never change. Real systems store them in a KV cache. Each step computes only the new token's key and value, appends them, and scores the new query against everything stored. Prefill runs the prompt through in one pass to fill the cache; decode then adds one token per step.

Queries are not cached. A query is used once, at its own step, to score the keys; no later token ever reads an earlier query, while every later token reads every earlier key and value.

The cache exists once per layer. The new token still runs through every layer: in each one, its own input to that layer gives that layer's key and value, which are appended to that layer's cache, and that layer's attention reads only its own cache.

At step \(t\) the one new query is scored against the \(t\) stored keys, and one weighted sum runs over the \(t\) stored values, so the cost grows in a straight line with \(t\). The 4 counts two products of \(d\) multiply-adds per stored token, the scores and the weighted sum, at two FLOPs per multiply-add.

Without the cache all \(t\) queries are recomputed against all \(t\) keys, the full table, though only its last row is new; so step \(t\) costs \(t\) times the cached step. Both lines are the attention line of Transformer Cost and Efficiency, with one query row or with all of them.

import torch

B, h, T, d_k = 1, 8, 10, 64
K = torch.randn(B, h, T, d_k)  # cache so far
V = torch.randn(B, h, T, d_k)
q, k, v = torch.randn(3, B, h, 1, d_k)  # the new token

K = torch.cat([K, k], dim=2)
V = torch.cat([V, v], dim=2)
S = q @ K.transpose(-2, -1) / d_k ** 0.5  # (B, h, 1, T + 1)
out = S.softmax(dim=-1) @ V               # (B, h, 1, d_k)

4 The cache trades compute for memory

The saved arithmetic is paid for in memory: the cache holds every key and value of every layer for the whole conversation.

The size of the cache.
\({\displaystyle \htmlClass{eqt sym-cb}{\htmlStyle{color:#a04000}{B_{\text{cache}}}}=2\,\htmlClass{eqt sym-L}{\htmlStyle{color:#2c3e50}{L}}\,\htmlClass{eqt sym-hkv}{\htmlStyle{color:#a04000}{h_{kv}}}\,\htmlClass{eqt sym-dk}{\htmlStyle{color:#1f618d}{d_k}}\,\htmlClass{eqt sym-T}{\htmlStyle{color:#9a6400}{T}}\,\htmlClass{eqt sym-b}{\htmlStyle{color:#1e8449}{b}}}\)
A long chat fills this fast. \(B_{\text{cache}}\) is the cache size in bytes. The 2 is one key and one value; then come the layers \(L\), the stored heads per layer \(h_{kv}\), the numbers per head \(d_k\), the tokens kept \(T\) and the bytes per number \(b\). Every factor scales the cache in proportion. \(h_{kv}\) is the one that sharing heads cuts.
stored headshead sizetokens keptbytes per number
def kv_cache_bytes(L, h_kv, d_k, T, b):
    return 2 * L * h_kv * d_k * T * b  # 2 = key + value

mistral_7b = kv_cache_bytes(L=32, h_kv=8, d_k=128, T=4096, b=2)
  1. 1The cache-size line of the card above, factor for factor.
  2. 2Each factor in the formula scales the cache in proportion: more layers, more stored heads, wider heads, more bytes per number and more tokens kept all grow it. A rolling buffer caps the cache at the window even though the context is longer.

Shazeer (2019) pointed out what this does to speed: each decode step must read the whole cache, so memory bandwidth, not arithmetic, sets how fast tokens come out.

A lower bound on one decode step, this page's summary of Shazeer (2019).
\({\displaystyle \htmlClass{eqt sym-ts}{\htmlStyle{color:#2c3e50}{t_{\text{step}}}}\;\gtrsim\;\frac{\htmlClass{eqt sym-cb}{\htmlStyle{color:#a04000}{B_{\text{cache}}}}}{\htmlClass{eqt sym-bw}{\htmlStyle{color:#1e8449}{\text{bandwidth}}}}}\)
Every step reads every stored key and value once, so the step time \(t_{\text{step}}\) is at least the cache size in bytes \(B_{\text{cache}}\) divided by the memory bandwidth, the bytes memory can deliver per second. The model weights are read every step too, so this is a bound from the cache alone. A bigger cache makes every token slower even though each token needs little arithmetic.

6 Prefill, decode and cache types

Generation runs once over the prompt, then once per token against the cache.

import torch
import torch.nn.functional as F

sdpa = F.scaled_dot_product_attention
B, h, T, d_k = 1, 8, 16, 64
q, K, V = torch.randn(3, B, h, T, d_k)  # the prompt
prompt_out = sdpa(q, K, V, is_causal=True)
# K and V are now the cache

q_new = torch.randn(B, h, 1, d_k)
k_new, v_new = torch.randn(2, B, h, 1, d_k)
K = torch.cat([K, k_new], dim=2)  # cache grows by one
V = torch.cat([V, v_new], dim=2)
step_out = sdpa(q_new, K, V)  # no is_causal here

  2. 2One decode step: append one key and value, attend from one query, step 4 of Figure 2.

The same reuse happens in translation: the decoder's cross-attention reads the encoder's keys and values, computed once.

7 Fitting the cache in memory when serving

A server answering many chats at once holds one cache per request, and the batch it can run is set by how many caches fit. Serving systems shrink the cache, move it, or stop wasting it.

  • Quantized cache. Store the keys and values at lower precision, fewer bytes per number \(b\). Hugging Face's QuantizedCache does this; its docs warn it can slow short generations that already fit in memory.
  • Offloaded cache. Keep every layer's cache in CPU memory except the layer running now, and fetch the next layer's cache ahead of time. GPU memory drops for a small loss in speed (Hugging Face's offloaded caches).
  • Paged blocks. PagedAttention (Kwon et al. 2023) splits each request's cache into fixed-size blocks, allocated only as tokens arrive and placed anywhere in memory, found through a per-request block table, as an operating system pages memory. Earlier servers reserved one contiguous run per request for its maximum length, so most of that memory sat empty. Blocks can also be shared, for example between several samples of the same prompt. Paging reclaims that wasted memory.

The model itself can also store less: fewer stored heads (Multi-Query and Grouped-Query Attention), a window that caps the tokens kept (Sliding-Window Attention), or, for a model trained with full attention, a window plus a few pinned first tokens (Attention Sinks and Streaming Generation).
