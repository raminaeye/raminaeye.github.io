Transformer Cost and Efficiency

Quadratic attention, the KV cache and streaming

This page picks up from Cross-Attention and the Q-Former. A Transformer's bill comes from two places: compute that grows with the square of the length, and memory that grows with every generated token. Each trick on this page attacks one of them.

The pieces being priced: a Transformer reads n tokens, each a vector of d numbers, the model width. In every layer, attention runs h heads; each head gives every token a query, a key and a value of dk numbers (the width split evenly across the heads), scores every query against every key in an n by n table, and turns each row into weights (a softmax) that blend the values. A feed-forward network (FFN) then widens each token to dff numbers and back to d. Generation is autoregressive: a decoder-only model like GPT writes one token per step and feeds it back in as input for the next.

Attention's cost grows with the square of the sequence length

I count the bill in FLOPs. One FLOP is one floating-point operation, a single multiply or a single add, so one multiply-add costs 2.

In attention the expensive part is the score table: every query meets every key, and blending the values with the weights costs the same again. The FFN does two matrix multiplications per token. I leave out the projections, the softmax and the norms; they don't change the story.

The two bills per layer, attention against the FFN, in FLOPs.
attention FLOPs = 4n2d
Attention costs four times n squared times d, where n is the sequence length in tokens and d is the model width. The 4 counts two jobs, building the score table and blending the values, each n2d multiply-adds at 2 FLOPs apiece. This line is why long sequences hurt: double n and the bill quadruples.
FFN FLOPs = 4nddff = 16nd2
The FFN costs four times n times d times dff, the FFN's inner width: two matrix multiplications per token, d up to dff and back, at 2 FLOPs per multiply-add. When dff is four times d, as in the original Transformer (width 512, 2048 inside the FFN), that is 16nd2. It grows only in a straight line with n, so short sequences are FFN-bound, long ones are attention-bound, and the two lines meet where n equals dff, four times the width.

Memory follows the same square. At 100,000 tokens one head's score table alone holds 10 billion entries.

The quadratic bill, per layer.

attention: 4n2d FFN: 16nd2 your length n

Change the width and the crossover moves with it, always to where n is four times d.

That bill is why long-context models restrict attention: windowed (Streaming models look back through a window because the future has not arrived), sparse (each token reads only a chosen subset of tokens) or linear (rewritten so the cost grows in a straight line with the length).

The KV cache keeps past keys and values instead of recomputing them

Generation adds a second bill. A naive loop reruns the whole sequence at every step, so step t recomputes keys and values for all t tokens so far. But under the causal mask (which stops a token from seeing later tokens), a past token's keys and values never change. So real deployments store them in a KV cache:

  1. When a token is generated, its keys and values are stored, one entry per token per layer.
  2. At the next step, the stored keys and values are reused and are not recomputed.
  3. Only the new token's keys and values are computed, and its query is scored against the stored keys.
  4. The new token's keys and values are appended to the cache for the following step.

The per-step cost of each path, per layer:

The per-step cost of each path, with and without the KV cache.
cost with cache = 4dt
With a cache, step t reuses the stored keys and values and only touches the new token, so the cost grows with t, not with t squared. Both lines are per step t, per layer. t is the number of tokens so far, which is also the step index. d is the model width, 512 in this section. The factor 4 is the two counted operations (the query-key scores and the weighted sum) at 2 FLOPs per multiply-add.
cost without cache = 4dt2
Without a cache, step t recomputes attention over all t tokens so far. The uncached path pays t times more at step t, so the saving grows with the sequence.

In code, one decode step (generating one new token) appends to the cache along the token axis and scores the single new query against everything stored: 

# one decode step in one layer; the cache holds T tokens, shapes (B, h, T, d_k)
# q_new, k_new, v_new: (B, h, 1, d_k), projected from the newest token only
k_cache = torch.cat([k_cache, k_new], dim=2)   # (B, h, T + 1, d_k)
v_cache = torch.cat([v_cache, v_new], dim=2)   # (B, h, T + 1, d_k)
scores = q_new @ k_cache.transpose(-2, -1) / q_new.size(-1) ** 0.5   # (B, h, 1, T + 1)
# no causal mask: the one new query is the latest token, so every cached key is in its past
out = scores.softmax(dim=-1) @ v_cache          # (B, h, 1, d_k)

The cache trades compute for memory

The cache is not free. It holds a key and a value for every token, in every head of every layer, for every sequence in the batch. Its size:

The size of the KV cache for one sequence.
cache bytes = 2 · L · hkv · dk · T · b
Read it as a stack of counts multiplied together; each · dot means times. The 2 is one key plus one value. L is the number of layers, hkv the number of heads that store keys and values (every head, in plain multi-head attention), dk the numbers per head, T the tokens cached so far, and b the bytes per number (2 for 16-bit floats). Multiply by the batch size for a whole batch. Every factor is plain multiplication, so the cache grows by the same amount with every generated token. The code under this card computes it for one toy setup.
# toy config: 12 layers, 12 KV heads of size 64, 4096 cached tokens, 16-bit floats (2 bytes)
L, h_kv, d_k, T, b = 12, 12, 64, 4096, 2
per_seq = 2 * L * h_kv * d_k * T * b   # 150,994,944 bytes = 144 MiB for one sequence
batch_32 = 32 * per_seq                # 4,831,838,208 bytes = 4.5 GiB for a batch of 32

That memory also sets the speed. Shazeer (2019) points out that decoding is slow because every step has to load the large key and value tensors from memory again, so memory bandwidth, not arithmetic, becomes the bottleneck.

Query heads can share keys and values

The cache size has hkv in it, and nothing says every query head needs its own keys and values. Multi-query attention (MQA, Shazeer 2019) keeps all h query heads but gives them one shared key head and one shared value head. Grouped-query attention (GQA, Ainslie et al. 2023) sits in between: the query heads split into g groups, and each group shares one key head and one value head.

How much of the multi-head cache grouped-query attention keeps.
GQA cache = gh · multi-head cache
The GQA cache is g over h of the multi-head cache, where g is the number of key-value groups and h the number of query heads; the · dot means times. So the cache shrinks by a factor of h over g. With g equal to h you are back to plain multi-head attention; with g equal to 1 you get MQA and the smallest cache. In the cache-size card this is the hkv factor set to g. In the code under this card, repeat_interleave copies each of the g stored heads out to its group of query heads.
# q: (B, h, T, d_k) with h = 8 query heads; k, v: (B, g, T, d_k) with g = 2 stored KV heads
# query heads are grouped contiguously: heads 0 to 3 read KV head 0, heads 4 to 7 read KV head 1
k = k.repeat_interleave(h // g, dim=1)   # (B, 8, T, d_k): each KV head copied 4 times in a row
v = v.repeat_interleave(h // g, dim=1)   # (B, 8, T, d_k)
# attention then runs exactly as in multi-head; the cache only ever stores the g = 2 heads

Shazeer tested MQA on English-to-German translation (WMT 2014) with an 8-head encoder-decoder of 211 million parameters, the same count for both versions. Decoding fell from 46 to 3.8 microseconds per token on one TPUv2 (a Google accelerator), and the dev-set BLEU score (translation quality, higher is better) slipped from 26.7 to 26.5 (Tables 1 and 2).

Ainslie et al. converted a pretrained T5 XXL (a large encoder-decoder) by averaging each group's key and value heads, then trained it for 5% more steps. Over summarization, translation and question answering, 8 groups averaged 47.1 against 47.2 for multi-head and 46.6 for MQA, at 0.28 seconds per sample against 1.51 and 0.24 (Table 1).

FlashAttention does the same math with less memory traffic

A GPU has a large, relatively slow high bandwidth memory (HBM, 40 to 80 GB on an A100) and a tiny, fast on-chip memory (SRAM, 192 KB on each of its 108 compute units). Dao et al. (2022) point out that standard attention writes the whole n by n score table to HBM and reads it back, more than once, and that this traffic, more than the arithmetic, sets the time.

FlashAttention computes exactly the same output in tiles. It loads one block of queries and one block of keys and values into SRAM, scores that tile, and keeps a running maximum and a running sum for each row so the softmax can be finished piece by piece. The full table never lands in HBM. For the backward pass it recomputes the tiles instead of storing them, so it does more arithmetic, not less.

Timing attention in GPT-2 medium (1024 tokens, 16 heads of size 64, batch 64, forward and backward on an A100), FlashAttention did 75.2 GFLOPs (billions of FLOPs) against 66.6, yet moved 4.4 GB to and from HBM instead of 40.3 and ran in 7.3 ms instead of 41.7 (Dao et al., Figure 2).

In PyTorch you rarely write this kernel yourself. On a CUDA GPU, F.scaled_dot_product_attention can dispatch to a FlashAttention kernel (its docs list FlashAttention-2 among the backends). Prefill means running the whole prompt through at once, which also fills the KV cache: 

import torch.nn.functional as F
# full sequence or prefill: q, k, v are (B, h, T, d_k); is_causal builds the lower-triangular mask
out = F.scaled_dot_product_attention(q, k, v, is_causal=True)    # (B, h, T, d_k)
# one-token decode: q_new is (B, h, 1, d_k), the cache is (B, h, T, d_k). is_causal aligns its
# mask to the top-left corner, so the new query would see only key 0; turn it off here
out = F.scaled_dot_product_attention(q_new, k_cache, v_cache, is_causal=False)  # (B, h, 1, d_k)

Streaming models look back through a window because the future has not arrived

Think about online speech recognition or real-time translation: the model can't see the whole sequence, because the future hasn't been spoken yet. Instead of full causal attention, you use windowed attention: each query only looks back a fixed number of frames (time slices of the input, such as 10 ms of audio), enforced by masking everything outside the window to negative infinity. It also caps the bill: each query scores at most a window's worth of keys, so the cost grows in a straight line with the length (Vaswani et al. list this restricted attention in Table 1). 

# windowed causal mask: each query sees the last `window_size` frames
# additive mask of shape (n, n): 0 = may attend, -inf = blocked; add it to the scores before the softmax
mask = torch.full((n, n), float("-inf"))
for i in range(n):
    start = max(0, i - window_size + 1)
    mask[i, start:i+1] = 0

Say your frames are 10 ms each and phonemes, the distinct units of sound in a language, are 20 to 50 ms long, about 2 to 5 frames per phoneme. You'd pick a window around 10 frames: enough to cover a whole phoneme plus blurry boundaries, without paying for word-level context you don't need. The rule of thumb: find the smallest unit you must capture (a phoneme, a gesture, a word), convert it to frames, and start there.

The window doesn't reset the model's memory the way chopping the input into chunks would. Each layer's tokens already carry their own window's context, so the effective span grows with depth, just like a receptive field, the span of input a token's representation can reach back and draw on. Stack enough layers and a small window still sees far.

The extreme version of this is chunked streaming: the model emits output in fixed-size chunks, and within a chunk every token may see the whole chunk. That means token 9 in a chunk of 4 can peek at tokens 10 and 11, slightly into its own "future". The price of that peek is latency: you can't emit the chunk until all 4 tokens have arrived. Bigger chunks, more context, slower response.

Stated as a rule: a query may read a key exactly when the key position is at or before the end of the query's own chunk. Written with positions:

The chunked-streaming bound, written with positions.
j ≤ (⌊iC⌋ + 1) · C − 1
A query may read a key exactly when the key position is at or before the end of the query's own chunk. i is the query position, j is the key position, and C is the chunk size in tokens. The ⌊ ⌋ pair around i divided by C is the floor: it rounds that division down to the whole chunk number the query sits in. The · dot after the bracket is multiplication: that chunk number plus one, times C. The right side is the last key position in the query's own chunk. Keys past that point are masked to negative infinity, the mechanism from Positional Encoding and Masking.

And the waiting relation: emission of a chunk waits for all C tokens of that chunk, so you wait C tokens per chunk to buy that extra context.

When a Transformer is the wrong tool

  • Quadratic cost. The score table is n by n per head, so the attention bill grows with the square of the sequence length (Attention's cost grows with the square of the sequence length). Very long sequences need windowed, sparse or linear attention; FlashAttention cuts the memory traffic but not the arithmetic.
  • Data hunger. Attention has no built-in notion of order or locality; the model has to learn all of that from data. On small datasets, a CNN or even an LSTM (a recurrent network with a memory cell) will often beat a transformer because their inductive biases (built-in assumptions, like a CNN's preference for local patterns) do some of the work for free.
  • Positions past the training length. Positional Encoding and Masking shows why learned and sine-cosine positions break down past the length a model was trained on, and how relative positions help.
  • Not every problem is a sequence problem. If your data is a fixed size vector or a small image, a transformer is overkill. The failure mode here is never "the model is too weak." It's that the model is too strong for the data you have. You need more data, not more model.

Where to go after the Transformer

The five pages covered Attention, Positional Encoding and Masking, The Transformer Block, Cross-Attention and the Q-Former, and here what it all costs and how to cut the bill. Where to go from here:

  • Conformer: what happens when you put convolution back next to attention, for speech.
