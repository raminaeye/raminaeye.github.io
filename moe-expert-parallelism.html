Expert Parallelism

How MoE models put different experts on different GPUs, move each token to its experts and back with an all-to-all, and why that changes batch size, memory and serving.

1 Experts on different GPUs

The experts of one MoE layer do not fit, or do not run fast enough, on one GPU. Expert parallelism gives each GPU a few experts and moves every token to the GPUs that hold its experts. The older options both fail here. Data parallelism, where every GPU holds a full copy of the model and works on its own slice of the batch, copies every expert to every GPU. Model parallelism splits every weight matrix across GPUs and adds communication inside every layer (Switch Transformers, sections 5.1 and 5.2). Shazeer et al. (2017) already spread experts across devices; GShard (Lepikhin et al. 2020) made it practical with annotation APIs and a compiler extension, sharding the MoE layers while every other layer was replicated, for a 600B-parameter translation model trained on 2048 TPU v3 cores in 4 days.

It happens twice in every MoE layer, in training and in serving: once before the experts and once after. What travels is token vectors, never weights.

2 Dispatch and combine

Each GPU runs the router on its own tokens and groups them by the expert they picked. One all-to-all exchange, in which every GPU sends a different slice to every other GPU, delivers each group to the GPU holding its expert: the dispatch. The experts run, and a second all-to-all returns the outputs: the combine (Switch Transformers, section 5.4).

3 Walkthrough: one layer on four GPUs

How much work each expert gets, where its tokens come from, and how much traffic moves.

(1)\(\displaystyle {\begin{aligned}&\text{tokens per expert} \\ &\quad \approx \frac{\htmlClass{eqt sym-k}{\htmlStyle{color:#117864}{k}}\,\htmlClass{eqt sym-t}{\htmlStyle{color:#1f6aa5}{T}}}{\htmlClass{eqt sym-n}{\htmlStyle{color:#a85a14}{N}}}\end{aligned}}\)
With \(T\) tokens in a step, each sent to \(k\) of \(N\) experts, an even router gives every expert the same share of the work: \(k\) over \(N\) of the tokens. More experts means fewer tokens per expert.
(2)\(\displaystyle {\htmlClass{eqt sym-t}{\htmlStyle{color:#1f6aa5}{T}} = B_{\text{micro}} \cdot \htmlClass{eqt sym-d}{\htmlStyle{color:#7d3c98}{D_{\text{DP}}}}}\)
The tokens an expert draws from are every data-parallel replica’s micro-batch together. \(B_{\text{micro}}\) is the tokens in one replica’s micro-batch and \(D_{\text{DP}}\) the number of data-parallel replicas sending to the same experts (Wang et al. call \(T\) the computation batch). Back in equation (1): raise \(D_{\text{DP}}\) to keep each expert’s share large.
(3)\(\displaystyle {\begin{aligned}&\text{all-to-all volume} \\ &\text{per layer} \\ &\quad \le\; c \cdot 2\,\htmlClass{eqt sym-k}{\htmlStyle{color:#117864}{k}}\,\htmlClass{eqt sym-t}{\htmlStyle{color:#1f6aa5}{T}}\,\htmlClass{eqt sym-v}{\htmlStyle{color:#c0392b}{d_{\text{model}}}}\end{aligned}}\)
Every token vector, of width \(d_{\text{model}}\), travels out to each of its \(k\) experts and back again: two trips. It is an upper bound because tokens whose expert sits on their own GPU never cross the network, and DeepSeek-V3 sends a token once per node. \(c\) is the bytes per number. Switch Transformers dispatches a padded version of this, one tensor of experts by capacity slots by \(d_{\text{model}}\).

4 The tool: where the traffic goes

Packing the experts a token tends to pick together, or limiting each token to fewer nodes, keeps more of the traffic on the fast links inside a node. The busy bars show the other cost: when one GPU’s experts are hot, the rest wait for it.

5 Keeping traffic inside a node

A node is one machine holding several GPUs; DeepSeek-V3 uses 8 per node. Inside a node GPUs talk over NVLink, which is much faster than the InfiniBand links between nodes (about 3.2 times, in the DeepSeek-V3 report). DeepSeek-V3’s node-limited routing lets each token reach at most \(M\) nodes: it ranks each node by the summed scores of its best few experts for that token and keeps the top \(M\), then picks experts only on them. Its DualPipe schedule overlaps both all-to-alls with computation, and DeepSeek-V3 drops no tokens during training.

6 Each expert sees a smaller batch

Equation (1) says each expert works on only a \(k\)-over-\(N\) share of the step’s tokens. Shazeer et al. (2017) call this the shrinking batch problem: with many experts, each one’s batch gets small and the GPU runs it inefficiently. The fix is equation (2): many data-parallel replicas, each with its own slice of the batch and its own copy of the non-expert weights, all send tokens to one shared copy of each expert. Larger computation batches also balance better with the bias method (Auxiliary-Loss-Free Load Balancing; Wang et al. section 5.1).

7 Combining the kinds of parallelism

Real runs mix expert, data and model parallelism. Switch Transformers (section 5.5) notes the trade: wider experts need more model-parallel cores each, which leaves fewer cores for experts and a smaller batch; its largest model, Switch-C, used expert parallelism only. DeepSeek-V3 keeps expert parallelism inside 8 nodes and uses no tensor parallelism at all (the report, section 3.2).

8 Serving: memory and redundant experts

Every expert must sit in GPU memory, though each token uses only a few (Mixture of Experts, store versus use): memory follows the total weights, compute follows the active ones. In Mixtral’s words, “The memory costs for serving Mixtral are proportional to its sparse parameter count”. Storing weights in fewer bits (Quantization) shrinks what has to sit in memory. DeepSeek-V3 serves the prompt and the generated tokens with different layouts: prefilling uses 32 GPUs over 4 nodes, decoding 320 GPUs over 40 nodes with one expert per GPU. Its busiest experts get redundant copies, re-chosen from load statistics about every 10 minutes.

9 In practice

Code 1, a toy dispatch and combine for one MoE layer with torch.distributed.all_to_all_single. Each rank holds E experts.

import torch
import torch.distributed as dist

def moe_layer(x, expert_idx, local_experts, E):
    # x: (tokens, d); expert_idx: (tokens,) picked expert per token
    world = dist.get_world_size()
    dest = expert_idx // E                     # rank holding each expert
    order = torch.argsort(dest)
    x, expert_idx = x[order], expert_idx[order]
    send = torch.bincount(dest, minlength=world)
    recv = torch.empty_like(send)
    dist.all_to_all_single(recv, send)         # exchange the split sizes
    s, r = send.tolist(), recv.tolist()
    xin = x.new_empty(sum(r), x.shape[1])
    dist.all_to_all_single(xin, x, r, s)       # dispatch
    ein = expert_idx.new_empty(sum(r))
    dist.all_to_all_single(ein, expert_idx, r, s)
    yin = torch.zeros_like(xin)
    for j, f in enumerate(local_experts):      # run the local experts
        m = (ein % E) == j
        yin[m] = f(xin[m])
    y = torch.empty_like(x)
    dist.all_to_all_single(y, yin, s, r)       # combine
    return y[torch.argsort(order)]             # back to the original order
  1. 1Walkthrough steps 2 and 3: each token’s destination rank, and tokens sorted so every rank’s group is contiguous.
  2. 2Every rank tells every other rank how many tokens to expect, so receive buffers can be sized.
  3. 3Walkthrough step 4, the dispatch: the token vectors, then their expert ids, cross in one all-to-all each.
  4. 4Walkthrough step 5: each rank runs only its own experts, on only the tokens sent to them.
  5. 5Walkthrough steps 6 and 7, the combine: the same exchange with the split sizes swapped, then the sort undone. Weighting by the gates happens after this, as on Mixture of Experts.
