1 Sparse models overfit small tasks

Fine-tuning means continuing to train a pretrained model on a smaller, task-specific dataset. MoE models pretrain faster than dense models of the same compute, but early sparse models (Switch Transformers; Artetxe et al. 2021) lagged dense ones once fine-tuned. ST-MoE (Zoph et al. 2022) names the two problems as “training instabilities and uncertain quality during fine-tuning”. Fine-tuned on SuperGLUE, a set of English understanding tasks, the sparse model fits the tiny CommitmentBank task faster but does worse on its held-out data, while on the large ReCoRD task it wins.

It happens once per downstream task, after pretraining, and starts from the pretrained weights and routers.

2 Walkthrough: the recipe

Split the weights, train the shared ones, keep a small balance loss.

The weights \(\theta\) split into two groups. \(\theta_{\text{shared}}\) is what every token passes through: attention, the dense feed-forward layers, the routers and the embeddings. \(\theta_{\text{experts}}\) is the experts’ own weights, most of the model, of which each token meets only a few.

Each gradient step moves only the shared weights, downhill on the task loss \(\mathcal{L}_{\text{task}}\); the experts stay as pretraining left them. \(\eta\) is the learning rate, which ST-MoE sets higher than a dense model would use. Back to equation (1): the frozen part is the larger one, the trained part the one every token sees.

Keep a small balance loss while fine-tuning so the router keeps spreading tokens. \(\alpha\) sets its weight; its form is on Mixture of Experts, the balance loss.

3 Train fewer weights

ST-MoE fine-tunes its ST-MoE-L model on SuperGLUE five ways: all weights, only the non-MoE weights, only attention, only the dense feed-forward layers, and only the MoE weights. Updating only the non-MoE weights works about as well as updating all of them, the feed-forward-only run is slightly better, and the MoE-only run is much worse, even though the MoE layers hold most of the weights. The reason is how few expert weights one token meets: expert layers sit in every fourth block, and a token visits at most two experts in each. Freezing the experts also saves memory and time.

4 Smaller batches, higher learning rates

ST-MoE also finds the sparse and dense models want opposite settings: the sparse model does better with smaller batches and higher learning rates, the dense one nearly the reverse (section 4.3). Reusing a recipe tuned for a dense model can hide the sparse model’s gain.

5 Expert dropout

6 Dropped tokens are fine

When an expert is full, extra tokens skip it (Mixture of Experts, capacity). ST-MoE finds that dropping even a tenth or more of the tokens during fine-tuning costs little, that keeping the balance loss helps slightly, and that the capacity factor can be raised at evaluation time (sections 4.4 and 5).

7 The tool: what fine-tuning touches

MoE only paints most of the weight bar green yet lights only a few rungs on the token’s path; Non-MoE paints a thin bar and lights every rung.

8 In practice

Code 1, fine-tuning Mixtral with the experts frozen, in PyTorch with Hugging Face Transformers. Capital names are placeholders.

import torch
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained(
    "mistralai/Mixtral-8x7B-v0.1",
    output_router_logits=True,      # return router logits so the balance loss is added
    router_aux_loss_coef=0.001)     # alpha in equation (3), the config default
for name, p in model.named_parameters():
    p.requires_grad = "experts" not in name   # freeze every expert weight
opt = torch.optim.AdamW(
    [p for p in model.parameters() if p.requires_grad],
    lr=LR)                          # sparse models: smaller batch, higher lr than dense
for batch in LOADER:
    out = model(**batch)            # out.loss = task loss + alpha * balance loss
    out.loss.backward()
    opt.step(); opt.zero_grad()
  1. 1output_router_logits=True makes the model add the router balance loss to its loss, weighted by router_aux_loss_coef: equation (3).
  2. 2Equation (2): every parameter whose name contains experts is frozen; the routers, attention and embeddings still train.
  3. 3The optimizer sees only the trainable weights. Choose the batch size and learning rate for the sparse model, not by copying a dense recipe.
  4. 4One fine-tuning step; loss already includes the balance term.
