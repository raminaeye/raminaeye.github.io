1 LoRA: learn only the change

A bottleneck adapter adds a small module after the frozen layers, while LoRA changes the weight itself.

LoRA (low-rank adaptation, Hu et al. 2022) looks at what fine-tuning does to a weight matrix. It starts from the pretrained weight \(W\) and ends with \(W\) plus a big dense update, dense meaning its entries are filled in rather than mostly zero. The useful part of that update lives in a tiny subspace, a small set of directions inside the big weight space, so LoRA learns it as two skinny matrices multiplied together.

LoRA trains on every step of the new task's data, and only \(A\) and \(B\) change; at serving it folds once into \(W\). The memory problem is the same one adapters solve: Adam keeps two extra numbers per parameter, so full fine-tuning needs about three times the model size just for weights and optimizer state, as counted in section 1 of Bottleneck Adapters and Compacter.

The \(r\) brace between the slabs in Figure 1 is the rank, the entire budget of new parameters.

Reparametrization means writing the trained weight as the frozen \(W\) plus the learned \(BA\) detour, so the update lives in the two small matrices.

\(A\) starts as small random numbers from a bell curve centered at 0; Figure 1 names that curve \(N\) with spread \(\sigma\) (not the ReLU \(\sigma\) of Bottleneck Adapters and Compacter, section 2), set by the small multiplier in the listing. \(B\) starts at zeros, so at step one the side path adds nothing to the pretrained model.

Freeze what the model already knows and learn only the change, as a detour through a tiny bottleneck.
\(\displaystyle \htmlClass{eqt}{\htmlData{k=W}{\htmlStyle{color:#2c3e50}{W}}} + \htmlClass{eqt}{\htmlData{k=BA}{\htmlStyle{color:#b45309}{BA}}}\)
Read \(BA\) as one learned update: \(A\) projects the input down to rank \(r\), \(B\) projects it back up, and the pair is added to the frozen pretrained weight \(W\).

The listing wraps a frozen linear layer with the side path through \(A\) then \(B\). It keeps all 20 lines because it is the whole layer, frozen path and scale included. Alpha is the knob that scales the side path before it is added, and the full alpha-over-r teaching lives in section 2.

import torch
import torch.nn as nn

class LoRALinear(nn.Module):
    def __init__(self, linear, rank=RANK, alpha=ALPHA):
        super().__init__()
        # frozen W
        self.linear = linear.requires_grad_(False)
        k = linear.out_features
        d = linear.in_features
        a0 = torch.randn(rank, d) * INIT_SCALE
        self.A = nn.Parameter(a0)
        # BA = 0 at start
        self.B = nn.Parameter(torch.zeros(k, rank))
        self.scale = alpha / rank

    # x: (..., d) -> (..., k)
    def forward(self, x):
        side = x @ self.A.T @ self.B.T
        return self.linear(x) + self.scale * side
  1. 1Keeps the original linear layer \(W\) frozen.
  2. 2Low-rank factors: \(A\) small random, \(B\) zero, so \(BA\) = 0 at start; scale is \(\alpha\)/\(r\).
  3. 3Output is the frozen path plus the scaled low-rank path.

2 Rank and scale

What LoRA trains for one weight matrix, against the full update.
\(\displaystyle \htmlStyle{color:#b45309}{r}(\htmlStyle{color:#2471a3}{d} + \htmlStyle{color:#2c3e50}{k})\)
\(A\) holds \(r \times d\) numbers and \(B\) holds \(k \times r\), where \(d\) is the input size, \(k\) the output size and \(r\) the rank.
\(\displaystyle \htmlStyle{color:#2471a3}{d} \cdot \htmlStyle{color:#2c3e50}{k}\)
What a full update trains for the same matrix. A smaller \(r\) means far fewer new parameters and a coarser approximation of the update.
The second knob sets how strongly the learned update is added.
\(\displaystyle \htmlClass{eqt}{\htmlData{k=h}{\htmlStyle{color:#2c3e50}{h}}} = \htmlClass{eqt}{\htmlData{k=W}{\htmlStyle{color:#2471a3}{W}}} \htmlClass{eqt}{\htmlData{k=x}{\htmlStyle{color:#2471a3}{x}}} + \frac{\htmlClass{eqt}{\htmlData{k=alpha}{\htmlStyle{color:#b45309}{\alpha}}}}{\htmlClass{eqt}{\htmlData{k=r}{\htmlStyle{color:#b45309}{r}}}} \htmlClass{eqt}{\htmlData{k=BA}{\htmlStyle{color:#b45309}{BA}}} \htmlClass{eqt}{\htmlData{k=x}{\htmlStyle{color:#2471a3}{x}}}\)
\(x\) is the layer input and \(h\) its output; \(\alpha/r\) (scale in the code) scales \(BA\). Raising \(\alpha\) makes every step change the update \(BA\) more, much like a larger learning rate; lowering it shrinks every update, and at \(\alpha\) = 0 the model stays frozen. Set alpha once to the first rank tried and leave it, since it acts like a learning rate.

In practice LoRA wraps the query and value projections of each attention block and leaves the rest frozen. A projection is a learned matrix that turns each position into a new vector: the query says what a position is looking for, the key what it advertises, and the value what it passes along (see Attention). The listing wraps them in RoBERTa-base. The classifier head stays trainable as well, so the task head learns alongside the LoRA factors.

# RobertaForSequenceClassification, backbone frozen
model.requires_grad_(False)
model.classifier.requires_grad_(True)  # re-enable the classifier head
for block in model.roberta.encoder.layer:
    attn = block.attention.self
    attn.query = LoRALinear(attn.query)
    attn.value = LoRALinear(attn.value)
# classifier head stays trainable
  1. 1Freezes the whole RoBERTa backbone and re-enables the classifier head.
  2. 2Wraps the query and value projections of every attention block with LoRA.

The rank \(r\) sets those numbers. A task close to what the model already does, such as sentiment classification, needs little rank; a task far from it, such as reasoning or code, can keep using more.

Raising \(r\) gives the update more directions in which to change \(W\), at \(r \cdot (d + k)\) trainable numbers per matrix; lowering it can miss part of the update, and \(r\) = 0 is the frozen model. At \(r\) = min(\(d\), \(k\)) the update is as free as full fine-tuning. A small rank is often enough.

At the largest rank LoRA trains as many parameters as a bottleneck adapter, still only a fraction of the dense matrix. Start low, go up only if the loss says so.

Figure 6. Illustrative curves; only the hard task keeps gaining.

LoRA trains a quarter of one percent of the model, and it usually lands within a point of full fine-tuning on classification-style tasks.

3 LoRA matches full fine-tuning on sentiment classification

SST-2 (the Stanford Sentiment Treebank: movie-review sentences labeled positive or negative) is the sentiment task the LoRA paper reports on RoBERTa-base. BitFit trains only the bias terms; AdapterDrop (Rücklé et al. 2021) is a bottleneck adapter that drops the adapters in the lowest layers.

LoRA trains a small fraction of the parameters and matches full fine-tuning on sentiment classification.

The paper's wider result reaches beyond this one task: LoRA lands on par or better than fine-tuning in model quality on RoBERTa, DeBERTa, GPT-2 and GPT-3 on language understanding and generation tasks (paper section 5). The GPT-2 and GPT-3 results cover generation tasks such as E2E, writing a description from table data, WikiSQL, and SAMSum, summarizing a chat, as well as understanding tasks such as MultiNLI.

4 LoRA in practice

A LoRA fine-tune is an ordinary training loop on a model whose chosen projections were swapped for LoRALinear, with an optimizer that holds only \(A\), \(B\) and the task head. Microsoft's loralib packages the same steps: build the layer with lora.Linear (shown for one projection), freeze everything else in model, and save only the LoRA weights.

The q_proj line demonstrates the replacement call, and the snippet assumes a model that already carries lora.Linear layers. It keeps all 15 lines because it is the whole flow from layer to save, and train_data is the task's training batches.

import torch
import loralib as lora

# replaces nn.Linear
q_proj = lora.Linear(WIDTH, WIDTH, r=RANK, lora_alpha=ALPHA)
lora.mark_only_lora_as_trainable(model)
model.classifier.requires_grad_(True)  # re-enable the classifier head
ps = model.parameters()
trainable = [p for p in ps if p.requires_grad]
optimizer = torch.optim.AdamW(trainable, lr=LEARNING_RATE)
for x, y in train_data: loss = model(x, labels=y).loss; loss.backward(); optimizer.step(); optimizer.zero_grad()
# LoRA factors only
sd = lora.lora_state_dict(model)
torch.save(sd, "lora.pt")
torch.save(model.classifier.state_dict(), "head.pt")
  1. 1A loralib layer at low rank, then freeze everything except the LoRA factors and the classifier head.
  2. 2Optimizer over the LoRA factors and the classifier head.
  3. 3Saves the LoRA factors to lora.pt and the classifier head to head.pt.

Before serving, fold \(BA\) into \(W\) once and call the plain layer, so inference costs nothing extra. Here layer is one LoRALinear layer from section 1:

# (k, r) @ (r, d) = (k, d)
delta = layer.scale * (layer.B @ layer.A)
with torch.no_grad():
    layer.linear.weight += delta
# serve this plain layer
merged = layer.linear
  1. 1Forms the full update \(BA\), scaled.
  2. 2Adds it into \(W\) once, so serving uses one plain layer.

After the merge, the model runs exactly as fast as the original; bottleneck adapters cannot merge, because their nonlinearity blocks it, so their extra layers stay forever.

  • A step still runs the full forward and backward pass (Figure 2), so it costs most of a full fine-tuning step; the big saving is memory: no gradients or Adam state for the frozen weights.
  • The loralib examples adapt only the query and value projections; on RoBERTa-base that trains only a small share of the model. The classifier head trains additionally. Figure 5 shows the small trained share.
  • A LoRA checkpoint holds only \(A\) and \(B\), so load the pretrained weights first and then the LoRA file, both with strict=False, which lets the LoRA file load into the pretrained model even though most weights are missing from it. The trained classifier head is saved on a separate line, in head.pt; it is not in the LoRA file.
  • In loralib, model.eval() merges \(BA\) into \(W\) and model.train() splits it out again, so evaluation in the middle of training is safe.
  • A fused qkv projection, one matrix computing query, key and value together, needs lora.MergedLinear with enable_lora, or each part gets one shared update instead of its own.

5 QLoRA: LoRA through a 4-bit base

This section needs one more idea: quantizing one tensor.

Adapters shrink what is trained, and quantization, storing each weight with fewer bits, shrinks the frozen rest that still sits in memory. QLoRA (Dettmers et al. 2023) trains LoRA adapters through a frozen base quantized to 4 bits.

4-bit NormalFloat (NF4) is a data type whose bins follow the quantiles of a normal distribution, a quantile being a cut point that splits the values into equal-sized groups, so each bin holds about the same number of values. It saves memory without losing accuracy because pretrained weights cluster near zero in a normal shape, so the data type spends its precision where the weights actually sit, near zero, instead of wasting bins on empty ranges.

Double quantization starts from the quantization constants, the rescaling numbers that map quantized values back to real values, one per block of weights. It quantizes those constants themselves, so the constants take less room. It saves memory because the constants are many small numbers of their own, and shrinking them shrinks the footprint per parameter.

Paged optimizers keep the optimizer states in paged memory built on NVIDIA unified memory, which moves memory between the GPU and CPU RAM automatically. When the GPU runs out of memory during a spike, the optimizer states are evicted to CPU RAM and paged back into GPU memory when the optimizer update step needs them. It saves the run because the spikes come from gradient checkpointing, recomputing saved activations instead of storing them, on long sequences, and paging rides them out instead of crashing.

At large scales, 4-bit QLoRA matches 16-bit LoRA, and at smaller scales it matches full 16-bit fine-tuning.

One plain limit: the largest-scale claim is matching 16-bit LoRA, not matching full fine-tuning.

QLoRA fits fine-tuning on a single consumer-size GPU.

Field example: the Guanaco models, instruction fine-tuning that reached near-ChatGPT quality on the Vicuna benchmark after a day of fine-tuning on one GPU. The Vicuna benchmark is a set of prompts where GPT-4 scores each model's answer against ChatGPT's answer out of ten, and the result is reported as a percentage of ChatGPT's score; the best Guanaco was finetuned on a variant of the OASST1 dataset, crowd-written assistant conversations.

Quantization-aware training with LoRA adapters also shows up in Meta's Llama 3.2 models, which used QAT with LoRA adapters for 4-bit weights, as taught in Quantization-Aware Training.

6 Related methods

The full table lives on the Bottleneck Adapters and Compacter page; here is the short list.

  • Prompt tuning (Lester et al. 2021) trains only a short soft prompt, learned vectors placed in front of the real words, and helps only on very large models.
  • Prefix tuning (Li and Liang 2021) trains learned key and value vectors set in front of the sequence in every attention layer, and helps generation tasks on large frozen models.
  • BitFit (Ben Zaken et al. 2022) trains only the bias terms, and helps on the smallest budget.
  • AdapterDrop trains a bottleneck adapter that drops the adapters in the lowest layers, as the paper describes, and helps when serving speed matters.

Where the update itself must stay small and mergeable, LoRA is the choice; where only a prompt or a bias may move, the others are cheaper.

7 What breaks and what to watch

  • Adapt query and value first. Cause: at a fixed parameter budget, LoRA on query and value together did best (the LoRA paper, section 7.1). Symptom: same budget, worse result when wrapping the wrong matrices. Fix: wrap query and value first at a fixed budget.
  • Unmerged LoRA still costs latency only if never merged. Cause: the side path stays in the forward pass. Symptom: slower serving per token while the side path stays in the forward pass. Fix: merge before serving, or use eval-time merging in loralib.
  • Full fine-tuning still wins sometimes on big datasets. Cause: with enough data the full model can use all of its capacity while the low rank caps what the update can learn. Symptom: LoRA accuracy plateaus below full fine-tuning as data grows. Fix: use full fine-tuning when data and compute allow; LoRA shines when data or compute is scarce.
  • The LoRA factors can still overfit a small dataset. Cause: the frozen backbone is safe, the LoRA factors are not. Symptom: training accuracy up, held-out accuracy down. Fix: validate, narrow the rank.

Tips: start at a low rank and go up only if the loss says so; set alpha to the first r tried and do not tune it; wrap query and value first.

What shrinks the frozen rest that still sits in memory? That is Quantization Basics, and Post-Training Quantization: Dynamic and Static tells the other half of the story.
