The Multitask Field Guide

Diagnose which failure you have, batch jointly (every batch carries every task), admit only the losses that must shape the shared trunk (the layers all tasks share), and know what no optimizer can fix.

Three failures break multitask training: scale, speed, and direction (the Introduction to Multitask Learning draws each one, with the geometry that tells them apart). Three lines of logging tell you which one you actually have, and the rest is running that shared trunk well.

Diagnose your failure mode first

Three lines of logging tell you which of the three failures you actually have. Only then do you pick the fix.

  1. Each task's loss, compared with training that task alone and with its own starting value. Doing worse than the task trained alone is called negative transfer. Dividing each task's loss by its value at the start shows how far each task has come. If one task's ratio has fallen far below another's, the tasks learn at different speeds, and that is the speed failure. The other two measurements check for the scale and direction failures.
  2. Each task's gradient norm at a shared layer (a task's gradient is the arrow pointing where its loss rises fastest, and its norm is that arrow's length on the shared trunk). If one is orders of magnitude bigger than the others, you have a scale problem.
  3. The cosine between each pair of task gradients. The cosine scores how much two arrows agree in direction, ignoring their lengths. If it is often negative, you have a direction problem.

The norm and the cosine are one line of arithmetic each, and both come straight from “The math kit: norms, dot products, gradients” on the Introduction to Multitask Learning page. The norm is the loudness check. If one task's arrow on the shared trunk is far longer than the others, that task is far louder, and in the plain average (every task's gradient on the trunk added with equal weight, then divided by the number of tasks) the quiet gradients are a rounding error. That is the scale failure, and the fix is rebalancing the tasks' loudness, for example with the learned per-task weights of Uncertainty Weighting (Kendall and coauthors), which sets each weight from how noisy that task is, or GradNorm, which tunes each task's weight until its gradient size matches a target, the average size boosted for tasks whose loss ratio shows them falling behind.

The cosine is the agreement check from the same math kit. A cosine of 1 means the same direction, 0 means perpendicular, and −1 means exactly opposed. Near −1, if one task is louder, the plain average goes whichever way the louder task points and pushes the other task's loss up. That is the direction failure, and the fix is removing the fighting component from the update.

A fight like this does not always fade on its own. Picture plain gradient descent (the basic training rule that moves the weights a small step against the gradient at every update) in a ravine, a long narrow valley in the loss landscape (the loss drawn as a surface over the weights) where the walls are steep but the floor barely slopes toward the exit. Say each task pulls toward a different wall, so the two gradients point against each other across the valley. Any learning rate (the size of that step) small enough not to bounce between the steep walls is too small to move far along the nearly flat floor. The run crawls along the valley, and the two gradients can keep fighting for the rest of it.

These three readings pick the fix. Once a balancing method is running, “What to log to see each interaction” in Gradient Balancing Inside the Training Loop lists what else to watch and where in the training step to read it.

These three failures, and two other causes, show up as symptoms first, and each symptom points to a first remedy.

Five multitask mistakes to avoid

Each of these five mistakes quietly undoes what the balancing methods are trying to do.

  1. Watching only the average loss. A great average can hide a task that was quietly sacrificed. Report per-task numbers too, ideally how far each task's score falls short of its single-task baseline, the run where that task trains on its own, averaged over the tasks, so every task in the joint run has a fair comparison.
  2. Doing gradient surgery in the task-specific heads, the final output layers each task keeps for itself. By surgery I mean editing gradient directions, cutting the part of one gradient that fights another, rather than changing how loud each loss is. Heads share no parameters, so there is nothing to fight over. Combine gradients on the shared trunk only.
  3. Forgetting to renormalize after reweighting. Renormalizing means rescaling the task weights (each task's loss weight) back to a fixed total after reweighting. Without it, the task weights slowly change the overall learning speed, and the comparison against baselines stops meaning anything.
  4. Running full K-task surgery (K is the number of tasks) on a 50-task problem. Its real price is K backward passes per step, where a backward pass is the reverse run through the network that computes one task's gradients. To cut that cost, sample a handful of tasks each step. CAGrad, a method that favors the worst-off task in each step, has a fast variant that does this. You then pay for those backward passes plus one for the average loss. Checking only a sample of task pairs is not enough on its own: it saves the pairwise comparisons, but every task in a sampled pair still needs its own backward pass.
  5. Treating every conflict as poison. Yu and coauthors, who introduced PCGrad, the method that cuts the part of each gradient that fights another, argue that conflict mostly hurts when it arrives together with two other conditions: high curvature, meaning the loss surface bends sharply, and a large gap in gradient sizes. They call the three together the tragic triad. Mild conflict between equals is often harmless.

Multitask deployment: what actually matters

“Our tasks have disjoint datasets. Does this still apply?” Yes. Every task can have its own dataset, with no example shared between datasets, and its own head; the gradients still meet in one place, the shared trunk. Conflict is a property of gradients on shared parameters, not of shared data.

A shared trunk with one output per task goes back to Caruana's original multitask networks. The per-task dataset, per-task head, shared-trunk setup is the standard case these methods were built on. They would only become irrelevant if the tasks shared nothing at all, and then it would not be multitask learning. To convince a skeptic, log the cosine similarity between pairs of task gradients on the shared trunk for a few hundred steps. If the cosines go negative, and in many setups they do, the conflict is real.

“What if one task's batch is much smaller?” A small batch makes a task's gradient jittery: averaged over 8 examples instead of 128, the direction swings step to step, even though it is honest on average. Plain averaging just absorbs the noise. Loudness rebalancing occasionally turns a knob, a task's loss weight, on a bad reading but self-corrects. Direction surgery sometimes cuts against a fight that was not real, which is wasteful, not dangerous.

Steering toward the worst-off task is the most sensitive: its whole decision is “who is worst off right now,” and a jittery signal sometimes makes the small-batch task look worst-off when it simply had an unlucky batch. The fixes, in rough order of importance:

  1. Oversample the small task. Going from 8 to 32 samples per step already helps a lot. No algorithmic patch beats a steadier signal.
  2. Smooth the decision signal. Keep a running average of each task's gradient, one that weights recent gradients most and forgets old values slowly (each step keeps 90 to 99 percent of the old average and takes the rest from the new gradient). Make the steering decision on that running average, and step with the real gradients. You can use this together with worst-off-task steering. The steering stays, but it stops reacting to one unlucky batch.
  3. Keep each step closer to the plain average. If you cannot oversample, limit how far the step may move away from the plain average, so one unlucky batch cannot drag the update toward a task that only looked worst-off.
  4. Log how much the gradient norm swings (its variance), not just its average. If the small task's gradient norm swings wildly over a few dozen steps, you have confirmed a shaky signal before it confuses the algorithm.

Batch jointly every step

Three layouts, and only one of them lets the methods do their job:

  1. A joint batch carries all tasks every step. This is the standard, and the layout to use. Each task produces a loss and a gradient on the shared trunk at the same weights at the same moment, which is exactly what “do these gradients fight?” and “which task is worst off?” require.
  2. Round robin carries one task per step. The methods that compare task gradients have nothing to do, with no pair to de-conflict and no worst-off task to find. Worse, round robin does not remove the conflict. It spreads it across time, as the trunk zigzags between tasks, the same back-and-forth that a too-large step causes between the walls of the ravine described in “Diagnose your failure mode first”. It removes the diagnostic, not the conflict.
  3. A random task per step is round robin, shuffled. It has the same problem and is just as incompatible with gradient-combining methods.

Within a joint batch, give every task an equal share, oversampling small datasets so every gradient is measured with equal reliability. The whole point is to let the gradients decide the weighting, which only works if every gradient is trustworthy.

If repeating a small dataset worries you, cap the repetition rather than shrinking its share. For example, allow no task to repeat its own data more than three times during one epoch of the largest dataset, where an epoch is one full pass through a dataset. And if a joint batch does not fit in memory, accumulate: run each task's sub-batch, the slice of that task's own data processed in this round, store its gradient, and combine once all tasks have reported. The direction-fixing methods need all task gradients before combining anyway, so accumulation changes where you pay the memory cost, not whether you pay it.

Only bring losses that must shape the trunk

Often each team arrives with its own mature single-task model, trained with half a dozen losses. Should all of them come into multitask training? No. The trunk is the only shared, one-shot resource in the whole system. After multitask training, a team takes the trunk, freezes it, holding its weights fixed so they stop training, and fine-tunes its own head privately, training that already trained head a little more on the team's own job, where it can use whatever losses it wants. So each loss faces one question: does this loss need to shape the shared features, or can it do its job later, on the frozen trunk, inside my own head?

Extra losses are expensive. Every added loss is another gradient pulling the trunk, the cost is paid by every team, not just the one who brought it, and the loss weights a team tuned for its single-task model no longer mean anything once loudness rebalancing or worst-off-task steering is involved. The practical filter is the frozen-head test:

  1. Baseline. Multitask-train with each task contributing exactly one loss, its main loss, the loss for the answer the task is actually scored on. Measure every task's metric, a score where higher is better, such as accuracy, and compare it with the task's target, the score it has to reach.
  2. Frozen-head check. Freeze the trunk; each team fine-tunes its head with its full private stack. Measure again.
  3. Gap analysis. If frozen-head fine-tuning reaches the target, the extra losses were head-level and stay private. If the metric is stuck no matter what the head does, the trunk never learned something the task needs, and that loss belongs in multitask training.
  4. Admit one loss at a time, and re-run. Confirm it closes the gap, and check the other tasks' metrics did not degrade.

The tool “Frozen-head test, step by step” runs this check on one task, in two cases. The head-level loss is an extra loss the head can supply on its own. The trunk-level loss is one the trunk must learn.

Each loss you admit is one arrow, one more direction the trunk must satisfy. There are two ways to combine those arrows. The plain average can give a step that raises some of the losses. The min-norm blend is the shortest mix of the arrows whose weights are not negative and add to one. If some loss arrow pointed away from the blend, mixing in a little more of that arrow would make the blend shorter. So no loss arrow points away from the shortest blend, and a small step against it lowers every loss. Once the blend shrinks to zero, no direction helps all the losses at once. MGDA is built on this blend and works it through in full.

Every pair of losses is one more relationship to manage, so the relationships grow much faster than the losses. With 8 losses there are already 28 pairs. Every extra loss is paid for by the one trunk all the teams share. Bring fewer, better losses. The tool “Each loss you add pulls the shared trunk in one more direction” draws the arrows, the average and the blend.

A few habits save real time.

  1. Start with one loss per task, no exceptions. This minimal baseline is the control group that makes every later decision measurable.
  2. Run the frozen-head check before debating a loss.
  3. When a loss joins, record the other tasks' metrics and the conflict rate, the share of steps where a pair's cosine is negative, before and after.
  4. Many tasks also have auxiliary losses, extra helper losses that support training but are not the scored answer. Pre-combine them with the main loss, using fixed weights from the task's single-task tuning history, so the multitask trainer sees one combined loss per task.
  5. When teams disagree about a loss, let the conflict measurements settle it.
  6. Re-run the frozen-head check after big changes. The verdict on a loss is not permanent.

When the trunk is too small, no optimizer can save it

This part matters as much as the methods. Gradient-level fixes redistribute a shortage; they do not remove it. If the shared trunk is simply too small to hold all the tasks, or the tasks genuinely work against each other, no optimizer can fix that. The limit is then set by the architecture (wider trunks, softer sharing, where tasks share only part of the trunk and keep the rest private, task-specific modules, small private parts each task keeps besides the shared trunk) and by task grouping (which tasks should share a trunk at all, so tasks that fight can be split into groups with separate trunks).

Optimization methods decide how well you use the sharing you chose; they cannot choose it for you. When a multitask setup is failing, the first question is not which optimizer to try. It is whether the tasks belong together and whether the trunk has room for them. The optimizer is the second question, not the first.

When the diagnosis points at the training itself, the fixes live on the method pages, and the introduction lists all of them side by side in “Three failures, and the pages that fix them”.
