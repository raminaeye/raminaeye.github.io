ReTool: Teaching Code Tools with a Cold Start

Seeing an error message can teach the model to fix its own code.

1 Text reasoning slips on arithmetic

A reasoning model can think for a long time in words and still slip on arithmetic. One small slip early on carries through every step after it, and the final answer lands wrong even when the plan was right. The field where this bites hardest is contest math, problems with exact answers where a single miscalculation sinks an otherwise sound solution.

A code interpreter changes that. It is a sandbox, an isolated place where code runs safely, that executes code and returns what the code prints, or the error when it fails. Writing the arithmetic as code hands the fragile part to a machine that does not slip, and the model keeps the part it is good at: deciding what to compute.

Training is cold start fine tuning followed by PPO, one rollout per problem. A rollout is one full attempt at one problem, from the question to the final answer. The code the model writes and the output that comes back are the state within one problem: what the model has tried and what the interpreter said so far. Nothing carries between problems.

2 Think, write code, run it, read it back

The loop has four moves. The model thinks in words, writes a block of code, the sandbox runs it, and the model reads the result back before thinking on. The loop repeats until the model writes its final answer.

Code goes between markers that say where it starts and ends. When the closing marker appears, generation pauses, the code is parsed out and sent to the sandbox, and the sandbox output is pasted back between interpreter markers for the model to read. A rollout is a chain of thoughts, code blocks and interpreter outputs, ending in the final answer.

The pause is the point. Generation stops at the closing code marker, so the model never writes past a result it has not seen. The interpreter output joins the reasoning as feedback, not as an appendix at the end, and the next thought starts from what the code actually did. That is the same shape as the Thought Action Observation loop, with a code block as the action and the interpreter output as the observation.

3 The reward that teaches strategy

This section leans on the PPO page for the clipped objective that turns rewards into an update.

3.1 The objective with code in the loop

PPO is the reinforcement learning method that makes small, limited updates to the policy, the model’s current way of choosing what to write next, so one batch cannot wreck it. ReTool keeps that objective and conditions every step on the interpreter feedback so far: the chance of each step is judged given the question, the steps before it, and the code results already seen.

Equation 1. The PPO objective with code interpreter feedback. The same clipped objective as PPO, with every step judged given the code results so far.
\(\displaystyle \htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{r_t}}=\frac{\htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{\pi_{\theta}(o_t \mid q, o_{<t}; \mathcal{CI})}}}{\htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{\pi_{\theta_{\mathrm{old}}}(o_t \mid q, o_{<t}; \mathcal{CI})}}}\)
The ratio: how much more likely the new policy makes this step than the old one did. \(o_t\) is the step being judged; \(q\) is the question; \(o_{<t}\) is everything written before this step; \(\mathcal{CI}\) is the code interpreter feedback so far; \(\pi_{\theta}\) is the policy being trained; \(\pi_{\theta_{\mathrm{old}}}\) is the policy that played the rollout.
\(\displaystyle \begin{aligned}&\htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{\mathcal{J}_{\mathrm{PPO}}(\theta)}}=\mathbb{E}\big[\min\big(\htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{r_t}}\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{\hat{A}_t}},\\&\; \operatorname{clip}\big(\htmlClass{eqt sym-p}{\htmlStyle{color:var(--sym-p)}{r_t}}, 1-\varepsilon, 1+\varepsilon\big)\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{\hat{A}_t}}\big)\big]\end{aligned}\)
The clipped objective: the average over rollouts of the smaller of the plain push and the clipped push. \(\hat{A}_t\) is the advantage, how much better this step turned out than expected; \(\operatorname{clip}\) holds the ratio between the two edges set by \(\varepsilon\), so a helpful step stops earning more push past the edge; \(\mathbb{E}\) averages over questions and rollouts. The expectation runs over rollouts that interleave code execution with reasoning, so the feedback is inside the objective, not outside it.
\(\mathcal{J}_{\mathrm{PPO}}(\theta)\) the PPO objective \(r_t\) the new over old chance ratio \(\mathcal{CI}\) the interpreter feedback so far \(\hat{A}_t\) the advantage of this step \(\varepsilon\) the clip width
The paper writes this objective as its equation 1, in section 2.3.1. The clip itself is taught on the PPO page; this page adds only the interpreter feedback inside the condition.

3.2 The reward

The reward judges only the final answer. A program checks whether the predicted answer matches the known one, and the model earns plus one when it matches and minus one otherwise. Code that runs is deliberately not rewarded separately: rewarding running code would teach the model to write code that runs but solves nothing, and a reward for correct code alone would pay for a right calculation inside a wrong solution.

Equation 2. The outcome reward. Plus one for a correct final answer, minus one otherwise, with nothing paid for code that merely runs.
\(\displaystyle \begin{aligned}&\htmlClass{eqt sym-r}{\htmlStyle{color:var(--sym-r)}{R(a, \hat{a})}}=\\&\begin{cases} 1, & \text{is\_equivalent}\\ & (a, \hat{a}) \\ -1, & \text{otherwise} \end{cases}\end{aligned}\)
The whole reward is the final answer. \(a\) is the known answer; \(\hat{a}\) is the predicted answer; \(\texttt{is\_equivalent}\) is the program check that the two match in meaning, so the same value written another way still counts; \(R\) is the reward. There is no term for whether the code ran, by design.
\(R(a, \hat{a})\) the reward \(a\) the known answer \(\hat{a}\) the predicted answer
The paper writes this reward as its equation 2, in section 2.3.1, and states plainly that it leaves code executability out of the reward to avoid reward hacking and keep the model exploring.

One training step runs the loop of section 2, scores the answer, and updates from the reward. The interpreter output is left out of the loss, the number training pushes down: tokens in the loss are the ones the model learns from, so masking the feedback means the model never learns to write interpreter output itself.

for problem, answer in problems:
    trace = model.generate(problem)
    while trace.has_code_block():
        code = trace.last_code_block()
        output = sandbox.run(code)
        trace.append(output, feedback=True)
        trace = model.continue_from(trace)
    reward = 1 if matches(trace.answer, answer) else -1
    loss = ppo_loss(trace, reward,
                    mask=trace.feedback_tokens)
    loss.backward()
  1. 1 The loop runs one code block at a time: each block goes to the sandbox and its output joins the trace before the model writes on. problems are the training questions with known answers; trace is the rollout so far; sandbox is the code interpreter.
  2. 2 The reward judges only the final answer: plus one when it matches, minus one otherwise. matches is the equivalence check from Equation 2.
  3. 3 The loss learns from the model’s own words only: interpreter output is masked out of it. ppo_loss is the clipped objective from Equation 1; feedback_tokens are the interpreter’s words in the trace.

3.3 The correction the reward teaches

Nothing in the reward asks for self-correction. It pays for right answers, and correcting broken code is what earns them. The model learns to read an error, work out what went wrong, and rewrite the code, even though no worked example ever showed it doing that. The survey of agentic RL names this shift from imitation to outcome optimisation as the second stage of tool-use learning, after prompting and fine tuning taught the model to copy tool use.

4 Cold start

Reinforcement learning from a model that has never written code inside its reasoning would flail: it would not know where code goes or how to read an error back. So training starts with a cold start: supervised fine tuning, training by copying worked examples, on traces that already show code used well, before any reward arrives.

The cold start data is built, not collected. Text reasoning traces are gathered first, then transformed: hand calculation steps that code could do better are replaced by the code and the interpreter’s result. Each trace is verified in two stages, format first, so the markers are readable and consistent, then answer, dropping every trace whose final answer is wrong. What survives is a set of code-augmented traces the model can copy.

Fine tuning on those traces gives the model its first competence: it writes code in the right places and reads the output back. The cold start alone already makes it a capable code user. Reinforcement learning then sharpens the strategy, when to call the tool, which code to write, and how to recover when it breaks.

5 Practice

Each code block costs one interpreter run, at training and at inference. The sandbox runs code in parallel workers, so one slow run does not stall the rest (paper section 2.3.2).

The headline setting is the PPO objective with code interpreter feedback (paper section 2.3.1). The interpreter feedback is masked from the loss, so the model never learns to write interpreter output itself (paper section 2.3.2).

The official repository is github.com/ReTool-RL/ReTool, verified live. It carries the evaluation code, the trained weights and the cold-start dataset, and links the training recipe in verl, the reinforcement learning framework the paper builds on (paper section 2.3.2).

6 Failure modes

Four failures cover most of what goes wrong. Each has a cause, a visible symptom, and a fix.

6.1 Broken code that never gets fixed

Cause: the reward pays only for the final answer, so nothing in training directly rewards fixing code. Symptom: the trace fills with error messages and the answer never lands. Fix: read the error and rewrite in the same scope, the correction the reward teaches (Figure 3); a trace that never fixes its code still earns minus one, and the update pushes that whole approach down.

6.2 Code for steps words could carry

Cause: once code works, it is the easy path for every step. Symptom: traces full of trivial code blocks, each costing a sandbox run. Fix: reserve code for steps where checking matters, calculation, enumeration and verification, and let short reasoning stay in words; the reward teaches this because a shorter trace that lands right earns the same plus one.

6.3 Interpreter output mistaken for reasoning

Cause: interpreter text sits inside the trace next to the model’s own words. Symptom: the model quotes an output as if it derived it, or tries to write interpreter-style text itself. Fix: mask interpreter tokens from the loss (paper section 2.3.2), so training never teaches the model to produce them.

6.4 A cold start that teaches bad habits

Cause: the synthetic traces are transformed text reasoning, so a slip in the source becomes a trace the model copies. Symptom: the model copies the pattern, code included, without checking what the code does. Fix: the two-stage verification, format then answer, dropping every trace whose final answer is wrong (paper section 2.2).
