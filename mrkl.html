MRKL: Routing Requests to the Right Expert

A wrong handoff sends the exact tool the wrong numbers.

1 One model cannot know everything

A language model answers from what it learned in training. It cannot know what changed since, what lives in a private database, or what today is. And it slips on arithmetic it should never have to do in its head. A bigger model helps with none of these: the facts are outside it, and a sum is exact work, not a guess.

MRKL, short for Modular Reasoning, Knowledge and Language, is the routing family on the section map. It keeps one large language model and surrounds it with a set of experts. An expert is a module that does one job well: a calculator, a currency converter, a lookup in a database, or a smaller model trained for one task. A router is a small trained model that reads each request and picks the expert that fits it. Toolformer teaches one model to call tools as it writes; MRKL splits the job across experts instead, and the router decides who gets asked.

MRKL runs at inference, once per request, with no memory between requests. Each request is routed fresh, and nothing carries over to the next one. The router itself is trained beforehand to recognise requests and pull out their arguments, but at run time nothing is learned.

2 The router and the experts

2.1 The router decides

Every request goes to the router first. The router reads the words and picks one expert. A sum goes to the calculator. A question about a live price goes to a database lookup. A question no expert fits goes to the general model. The router is itself a language model, and it writes out its choice and the arguments as text, one token at a time, the way Decoding teaches.

The router's choice is the whole system working or failing. Pick right and the expert answers exactly. Pick wrong and the best expert never gets asked. Unlike the ReAct loop, which thinks and acts step by step, the router decides once per request.

2.2 Two kinds of expert

A neural expert is a model: the general-purpose language model, or a smaller model trained for one job. A symbolic expert is a rule, not a model: a calculator, a currency converter, a database lookup. Symbolic means it follows fixed rules and gives the same answer every time for the same input. The calculator never guesses. That split is the point: the system keeps the language model for language and hands exact work to exact tools.

2.3 The answer can travel on

An expert's answer can be the reply, or it can go to another expert. A lookup can feed a sum. The paper calls this compositionality: answers chain from one expert to the next, so a request with two parts gets both answered.

3 The handoff that breaks

Picking the expert is only half the job. The router must also hand the expert the right inputs. For a calculator those inputs are the operation and the numbers it works on. The operation is what to do: add, subtract, multiply, divide. The numbers are the operands, the values the operation works on. Pulling those out of words is called argument extraction: turning a sentence into the exact inputs a tool needs.

That handoff is where the system breaks. The calculator is exact, so when the answer is wrong, the fault is never the arithmetic. It is the handoff: the wrong operation, or the wrong numbers, handed to a tool that does exactly what it is told.

The words make it hard. The same sum arrives as digits, as words, as synonyms, or as a story. "3 - 1" and "How much is three minus 1" ask the same sum, and "twelve", "12" and "a dozen" all name the same number. A story hides the sum further: "I lost one ball" needs world knowledge to read as a subtraction, since losing means taking away. The router must read meaning, not match symbols, and working through what the words ask is what lets it do that.

The router call as code: one call returns the expert and its arguments.

request = (
    "How much is three minus 1")
(expert, operation,
 first, second) = route(request)
answer = call(expert, operation,
    first, second)
reply = answer
  1. 1route is the router. It reads the request and returns the expert name with the operation and the two numbers: calculator, minus, 3, 1.
  2. 2call runs the named expert on those arguments, and its answer becomes the reply.

4 Adding a new expert

Adding a capability takes three steps. First, build the expert on its own: train a small model for the job, or write the rule. Second, teach the router to recognise requests for the new expert and pull out the arguments each one needs. Third, change nothing else. The existing experts are untouched, and only the router is retrained.

Compare that with fine tuning one big model on a new task. The new task can push out old skills, a failure called catastrophic forgetting: the model forgets what it knew when it learns something new. Avoiding it means retraining the whole model on everything at once, which is far too costly to repeat for every new task. Adding an expert avoids that entirely, since the old experts never change.

5 Practice

Each request costs one router call and one expert call. In the paper's test case the router is trained by prompt tuning, which trains a small set of prompt tokens while the large model stays fixed (paper section 3.2).

The headline setting is router only retraining (MRKL paper section 3). When an expert is added, only the router is retrained; the experts and the general model stay as they are.

The paper released no official implementation code, so there is no official code to link here. The experiment data was released as a public data set on GitHub.

6 Failure modes

Three failures cover most of what goes wrong. Each has a cause, a visible symptom, and a fix.

6.1 Routed to the wrong expert

Cause: the router reads the request and picks the wrong module. Symptom: a sum goes to the general model, which guesses instead of calculating, or a live question goes to the calculator, which cannot answer it. Fix: train the router on more varied phrasings of the requests it gets wrong, so it learns the boundary between experts.

6.2 Right expert, wrong arguments

Cause: the handoff pulls the wrong operation or the wrong numbers from the words. Symptom: the calculator answers a different sum than the one asked, exactly and confidently. Fix: train and test the router's argument extraction for that expert on its own, with varied phrasings, before trusting it.

6.3 A phrasing or operation the router never saw

Cause: the router only handles the phrasings and operations its training covered. Symptom: a request written with number words fails where the same request in digits works, and a new operation fails where a trained one works. Fix: train on both forms of every number and on every operation the expert offers. Training on words also covers digits, but the reverse does not hold.

7 What comes next

MRKL routes each request to one expert that answers on its own. But some questions need a model that thinks longer before it answers, checking its own work as it goes. Reasoning Models: Long Thinking Inside an Agent shows how rewarding only a correct final answer can still teach a model to pause and check itself.
