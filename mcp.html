MCP

One standard way to plug tools in beats a custom connector for every pair.

1 Every pair needs its own connector

Every agent in this section calls tools. ReAct searches, Toolformer calls a calculator, ToRL runs code. Each of those pages teaches one tool wired into one model. That wiring does not scale: without a shared standard, every host needs a custom connector for every tool, so the work grows with hosts times tools.

MCP, the Model Context Protocol, is the shared standard. A protocol is a shared set of message formats and rules that both sides agree to follow. With MCP, each host writes one client and each tool writes one server, and any client can talk to any server. The documentation compares it to a USB-C port: one plug shape for every device.

MCP runs at inference. One session opens one connection, and each tool use is one call. The session, with the tools the server listed, is the state the client carries. Nothing is trained here: the protocol only moves messages between the model and the tools.

2 Host, client and server

MCP has three roles. The host is the application the user sees: it runs the model, creates and manages clients, and enforces consent. The client is a connector inside the host, one per server, that speaks the protocol. The server is the program that offers the capability: tools to run, data to read, or prompts to use. A server can be a local process or a remote service.

Each client holds one stateful session with one server, and the host can run many clients at once. A server never sees the whole conversation or another server: the full history stays with the host, which decides what each server gets to see.

All messages are JSON-RPC 2.0. A request carries an id and expects a reply. A reply carries a result or an error. A notification travels one way, with no reply expected. Those three shapes carry every exchange on the page.

The split is the point. Servers stay simple, each offering one focused capability, while the host carries the hard parts: managing clients, keeping the conversation, and deciding what the user has agreed to.

3 The handshake

A session has three phases: initialization, operation, and shutdown. Initialization must come first, and nothing else may run until it finishes. Shutdown has no message of its own: the connection simply closes.

The client opens with an initialize request carrying the protocol version it supports, what it can do, and which program it is. The server answers with its own version, its capabilities, and its program details. Then the client sends an initialized notification, which expects no reply, and normal operation begins.

3.1 Agreeing on a version

If the server cannot use the version the client asked for, it answers with a version it does support, and the client disconnects if it cannot use that one either. Capability negotiation works the same way: each side declares what it offers, and during operation both sides may use only the capabilities that were agreed.

4 Tools, resources, prompts and sampling

Servers offer three things, and clients offer three back. Who controls each one is the difference that matters.

4.1 Tools

A tool is a function the model can run: search a database, call an API, do a computation. The client discovers tools with tools/list and runs one with tools/call, sending the tool name and its arguments. The result comes back as text or as structured content, in the structuredContent field that carries the structured result, and a failed run carries isError: true, which marks the run as failed.

A tool definition carries its name, a description of what it does, an input schema, a JSON Schema that names each argument, its type, and which arguments are required, and an optional outputSchema, a JSON Schema that fixes the shape of the structured result. The model reads the definition to decide when to call the tool and what to pass it.

{
  "name": "get_weather",
  "description": "City weather",
  "inputSchema": {
    "type": "object",
    "properties": {
      "city": { "type": "string" }
    },
    "required": ["city"]
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "sky": { "type": "string" }
    },
    "required": ["sky"]
  }
}
  1. 1The name and the description: what the tool is called and what it does.
  2. 2The input schema: each argument, its type, and which arguments are required.
  3. 3The output schema: the shape of the structured result.

4.2 Resources

A resource is data the server shares: a file, a database schema, a page of documentation. Each resource has a URI, a unique address the client uses to ask for it. The client lists them with resources/list and reads one with resources/read.

Resources are application driven, the contrast with tools. The host or the user picks what enters the context, rather than the model deciding on its own.

4.3 Prompts

A prompt is a template the server offers: a fixed set of messages with slots the user fills in. The client lists them with prompts/list and fetches one with prompts/get. Prompts are user controlled: the user picks one, often as a slash command, and the template becomes part of the conversation.

4.4 What the client offers

The client offers three things back to the server. Sampling lets a server ask the host model to generate text, for example to summarize a file the server holds. The host controls the prompt that is sent and what the server gets to see, and the user must approve it. Roots let a server ask which folders it may work in. Elicitation lets a server ask the user for structured input in the middle of a task, such as a missing value a tool needs.

5 Consent and trust

MCP moves messages, and it does not judge them. The specification says it directly: the protocol itself cannot enforce security principles, so the host must build the consent and authorization flows.

Three rules follow. First, the host must get explicit user consent before invoking any tool, and before exposing user data to a server. Second, a tool description is untrusted unless it comes from a trusted server, because the model reads the description and may follow instructions hidden inside it. Third, the host shows the user what a tool will do before it runs, so the user sees the call before it runs.

Sampling carries the same shape: the user approves any sampling request, controls whether it happens at all, and controls the prompt that is sent and what the server can see. The protocol limits what the server sees by design, and the host enforces the rest.

6 Practice

One handshake per session, then one call per tool use. The handshake runs once when the session opens; after that, each tool use is one tools/call request and one result.

The headline setting is the handshake sequence itself: initialize, list tools, call, read the result (MCP specification 2025-06-18). There is no training run and no tuning: the sequence is the whole setup.

The specification is the reference, and the official SDKs build servers and clients for TypeScript and Python: the TypeScript SDK and the Python SDK, both from the Model Context Protocol organization, verified live.

7 What breaks

Three failures cover most of what goes wrong, each with a cause, a visible symptom, and a fix.

7.1 An untrusted tool description

Cause: the tool description comes from the server, and the model reads it as guidance. Symptom: a tool that claims to check the weather carries instructions telling the model to send a file, and the model follows them. Fix: treat every description as untrusted unless the server is trusted, and show the user what the tool will do before it runs.

7.2 Consent bypass

Cause: the host approves tool calls on its own to save the user a click. Symptom: a tool sends a message or deletes a file the user never saw. Fix: ask for explicit consent on sensitive calls, and show the tool inputs to the user before calling.

7.3 A stale tool list

Cause: the client keeps the list from tools/list and the server changes what it offers without saying so. Symptom: the model calls a tool that no longer exists, or never learns about a new one. Fix: a server that declares the listChanged capability, which says it will send a notification when its list changes, sends a notifications/tools/list_changed notification, which tells the client the tool list has changed, and the client lists again on hearing it.
