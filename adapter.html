Adapters

Adapting a frozen model to a new task by training small added modules.

On this page

How do you teach a large model a new task without retraining the whole thing?

Full fine-tuning updates every parameter of a transformer, a stack of blocks where the positions of a sequence first exchange information and then each position is processed on its own, and keeps one full copy per task. This page uses RoBERTa-base as its example model: 12 layers with hidden size 768 and 125 million parameters, the learned numbers that make up its weights (BERT-base has the same shape and 110 million).

Worse, Adam, the optimizer that runs training, keeps extra state for every parameter:

GPU memory needed just to hold the weights and the optimizer state.
P + 2P = 3P
The weights take P, the model size in parameters, and the Adam state takes 2P. Adam adds 2 numbers per parameter, a running average of its direction and of how spread out its recent steps have been. Weights plus Adam state take about three times the model size in GPU (graphics processing unit) memory, and the gradients add one more P.

And the model learns the new task and starts forgetting the old ones. That is catastrophic forgetting.

Adapters do the opposite: freeze the big model, add small trainable modules, and train only those (Figure 1).

Adapters train like ordinary fine-tuning, on every step of the new task's data, and the state a task leaves behind is its adapter (Figure 2). The gradient still has to pass through the frozen backbone to reach the adapters, and at serving time LoRA, the second method here, folds away.

1 Bottleneck adapters

The original idea (Houlsby et al. 2019) is simple. Each transformer layer has an attention block, where each position mixes in information from the other positions, and a feed-forward block, which processes each position on its own. After each one you insert a small two-layer MLP (multilayer perceptron) with a bottleneck: the hidden state, the vector that carries one position through the layer, is 768 numbers wide, and the adapter projects it down to 64 numbers and back up to 768.

The adapter paper was solving the many-tasks problem: a pretrained model, one already trained on a large body of general text, fine-tunes well, but every downstream task needs its own full copy. With adapters the base stays frozen and a new task never revisits the old ones.

Transferring BERT (Bidirectional Encoder Representations from Transformers, a large pretrained language model) to 26 text classification tasks including GLUE (a standard suite of language-understanding tests), adapters land within 0.4% of full fine-tuning while adding only 3.6% parameters per task, against 100% for fine-tuning.

The listing is the whole module; input and output are both hidden_dim wide.

import torch.nn as nn

class SimpleAdapter(nn.Module):
    def __init__(self, hidden_dim, bottleneck_dim):
        super().__init__()
        h, m = hidden_dim, bottleneck_dim
        self.down_proj = nn.Linear(h, m)
        self.relu = nn.ReLU()
        self.up_proj = nn.Linear(m, h)

    # x: (batch, seq, hidden_dim)
    def forward(self, x):
        z = self.relu(self.down_proj(x))
        # residual: frozen x plus update
        return x + self.up_proj(z)
  1. 1down_proj to the bottleneck, ReLU (negatives become 0, positives pass), up_proj back up.
  2. 2forward adds the input back, so the frozen signal passes untouched if the adapter does nothing.

The parameter count, with a hidden size of 768 and a bottleneck of 64; a bias is one learned number added to each output of a projection, on top of its weights.

Training two percent of the model leaves the other 98 percent where pretraining put it. That is why the model does not forget.

Training is the usual loop with one filter, so the optimizer keeps no state for the backbone. The learning rate is a placeholder.

for name, param in model.named_parameters():

    param.requires_grad = "adapter" in name
ps = model.parameters()
trainable = [p for p in ps if p.requires_grad]
optimizer = torch.optim.AdamW(trainable, lr=1e-4)

The adapter projects the frozen features down, applies a nonlinearity, projects them back up, and adds the result to its input as a small update.
h = Wup·σ(Wdown·x)
The frozen input x is projected down by Wdown to the bottleneck, passed through σ, then lifted by Wup; the result h is the learned update. The 64-number bottleneck is what keeps the adapter cheap: both matrices are thin, so the parameter count is about 2 × 768 × 64 instead of 768 × 768. The ReLU between them matters too, because without it the two matrices would collapse into one plain low-rank matrix. This line is the listing's down_proj, relu and up_proj in order.
y = x + h

2 LoRA (low-rank adaptation)

LoRA (low-rank adaptation, Hu et al. 2022) looks at what fine-tuning does to a weight matrix. It starts from the pretrained weight W and ends with W plus a big dense update, dense meaning its entries are filled in rather than mostly zero. The useful part of that update lives in a tiny subspace, a low dimensional slice of all possible updates, so LoRA learns it as two skinny matrices multiplied together.

Reparametrization means writing the trained weight as the frozen W plus the learned BA detour, so the update lives in the two small matrices.

Freeze what the model already knows and learn only the change, as a detour through a tiny bottleneck.
W + BA
Read BA as one learned update: A projects the input down to rank r, B projects it back up, and the pair is added to the frozen pretrained weight W.

The r brace between the slabs is the rank, the entire budget of new parameters.

What LoRA trains for one weight matrix, against the full update.
r(d + k)
A holds r × d numbers and B holds k × r, where d is the input size, k the output size and r the rank.
d · k
What a full update trains for the same matrix. A smaller r means far fewer new parameters and a coarser approximation of the update.

The two slabs start differently. A starts from random values drawn from a bell curve centered at 0 with spread σ, the N(0, σ2) on its slab (not the ReLU σ of the adapter walkthrough above). B starts at exact zeros, so at step one the side path adds nothing and the model behaves exactly like the pretrained model.

The code wraps a frozen linear layer self.linear with the side path through A then B.

import torch
import torch.nn as nn

class LoRALinear(nn.Module):
    def __init__(self, linear, rank=8, alpha=16.0):
        super().__init__()
        # frozen W
        self.linear = linear.requires_grad_(False)
        k = linear.out_features
        d = linear.in_features
        a0 = torch.randn(rank, d) * 0.01
        self.A = nn.Parameter(a0)
        # BA = 0 at start
        self.B = nn.Parameter(torch.zeros(k, rank))
        self.scale = alpha / rank

    # x: (..., d) -> (..., k)
    def forward(self, x):
        side = x @ self.A.T @ self.B.T
        return self.linear(x) + self.scale * side
  1. 1Keeps the original linear layer W frozen.
  2. 2Low-rank factors: A small random, B zero, so BA = 0 at start; scale is α/r.
  3. 3Output is the frozen path plus the scaled low-rank path.

Before serving, fold BA into W once and call the plain layer, so inference costs nothing extra:

# (k, r) @ (r, d) = (k, d)
delta = lora.scale * (lora.B @ lora.A)
with torch.no_grad():
    lora.linear.weight += delta
# serve this plain layer
merged = lora.linear
  1. 1Forms the full update BA, scaled.
  2. 2Adds it into W once, so serving uses one plain layer.

In practice LoRA wraps the query and value projections of each attention block and leaves the rest frozen. A projection is a learned matrix that turns each position into a new vector: the query says what a position is looking for, the key what it advertises, and the value what it passes along (see Attention). In RoBERTa-base:

# RobertaModel, all frozen
model.requires_grad_(False)
for block in model.encoder.layer:
    attn = block.attention.self
    attn.query = LoRALinear(attn.query)
    attn.value = LoRALinear(attn.value)
# later modules stay trainable
  1. 1Freezes the whole RoBERTa encoder.
  2. 2Wraps the query and value projections of every attention block with LoRA.

The rank r sets those numbers. A task close to what the model already does, such as sentiment classification, needs little rank; a task far from it, such as reasoning or code, can keep using more.

Raising r gives the update more directions in which to change W, at r·(d + k) trainable numbers per matrix; lowering it can miss part of the update, and r = 0 is the frozen model. At r = min(d, k) the update is as free as full fine-tuning; LoRA's RoBERTa runs use r = 8 (its Table 9). In LoRA Table 6 (GPT-3 175B) r of 1 or 2 is enough, and WikiSQL and MultiNLI stay flat up to 64.

The second knob sets how strongly the learned update is added.
h = Wx + αr BAx
x is the layer input and h its output; α/r (scale in the code) scales BA. Raising α makes every step change the update BA more, much like a larger learning rate; lowering it shrinks every update, and at α = 0 the model stays frozen. Because α acts like the learning rate, the paper sets α to the first r it tries and does not tune it (the paper's Section 4.1).

At r = 64 LoRA trains as many parameters as a bottleneck adapter, still only a sixth of the dense matrix. Start at 8, go up only if the loss says so.

r = 8 · 12,288 params per projection

Figure 9. Illustrative curves; only the hard task keeps gaining.

A quarter of one percent of the model, and it usually lands within a point of full fine-tuning on classification-style tasks.

After the merge in the folding listing, the model runs exactly as fast as the original; bottleneck adapters cannot merge, because their nonlinearity blocks it, so their extra layers stay forever.

3 Compacter (Kronecker-factored adapters)

Adapters are already small. Compacter asks whether the adapter's own matrices can be cheaper. Compacter uses the Kronecker product: instead of storing a big dense matrix, store two small factors A and B and let their product stand in for it.

In the Kronecker product A ⊗ B, each element of A scales a whole copy of B.

One factor pair is enough to build a full adapter matrix:

A big adapter matrix from two small factors.
W768×64 = A8×8 ⊗ B96×8
W is one adapter weight matrix, ⊗ is the Kronecker product, and the subscripts are the shapes: every entry of A scales a whole copy of B.

Only the factors are stored, 8·8 + 96·8 = 832 numbers, against 768·64 = 49,152 for the dense matrix.

Earlier parameter-efficient methods either still used many parameters or underperformed full fine-tuning. Compacter builds each adapter matrix as a sum of these products:

Compacter's adapter weight: shared slow factors times per-layer fast factors.
W = Σi=1..n Ai ⊗ Bi
The Ai are shared "slow" weights, reused across layers; the Bi are per-layer "fast" weights; Σ adds the n products.
Bi = si tiT
Each fast factor is rank one, built from a single pair of vectors si and ti, where the superscript T, the transpose, lays ti flat as a row.

Training only 0.047% of the model's parameters, it matches full fine-tuning on GLUE and beats it on SuperGLUE, GLUE's harder successor suite, and in low-resource settings, where only a little task data is available.

The listing uses one product with a full B; Compacter sums n of them and makes each B rank one. The big matrix is never built.

def kron_linear(x, A, B):
    # x @ (A ⊗ B) without building A ⊗ B
    # A: (m, n), B: (p, q), x: (batch, m*p)
    m, p = A.shape[0], B.shape[0]
    X = x.view(-1, m, p)
    Y = A.T @ X @ B
    # (batch, n*q)
    return Y.reshape(x.shape[0], -1)
  1. 1Reshapes each input row into an m by p matrix.
  2. 2Multiplies by the two small factors and flattens back: the same result as the full Kronecker product.

The cost is that the weight matrix is no longer fully free; it has to factor this way.

6 LoRA in practice

A LoRA fine-tune is an ordinary training loop on a model whose chosen projections were swapped for LoRALinear, with an optimizer that holds only A, B and the task head. Microsoft's loralib packages the same steps: build the layer with lora.Linear (shown for one projection), freeze everything else in model, and save only the LoRA weights.

import torch
import loralib as lora

# replaces nn.Linear
q_proj = lora.Linear(768, 768, r=8)
lora.mark_only_lora_as_trainable(model)
ps = model.parameters()
trainable = [p for p in ps if p.requires_grad]
optimizer = torch.optim.AdamW(trainable, lr=1e-4)
# ... the usual training loop ...
# A and B only
sd = lora.lora_state_dict(model)
torch.save(sd, "lora.pt")
  1. 1loralib layer with rank 8, then freeze everything except the LoRA factors.
  2. 2Optimizer over the LoRA factors only.
  3. 3Saves only A and B.
  • A step costs most of a full fine-tuning step (Figure 2); the big saving is memory: no gradients or Adam state for the frozen weights. On GPT-3 175B the LoRA paper reports 10,000 times fewer trainable parameters and 3 times less GPU memory than fine-tuning with Adam.
  • The loralib examples adapt only the query and value projections; on RoBERTa-base that is 0.8M trainable parameters against 125M for full fine-tuning (loralib README): Figure 8's 294,912 plus the classifier head.
  • A LoRA checkpoint holds only A and B, so load the pretrained weights first and then the LoRA file, both with strict=False.
  • In loralib, model.eval() merges BA into W and model.train() splits it out again, so evaluation in the middle of training is safe.
  • A fused qkv projection needs lora.MergedLinear with enable_lora, or each part gets one shared update instead of its own.

7 Pitfalls

  • Unmerged adapters cost latency. An unmerged adapter adds two matrix multiplications per block for every token (one unit piece of the input sequence) at serving time. Bottleneck adapters cannot merge, so they stay in the graph.
  • On big datasets, full fine-tuning still wins sometimes. Adapters shine when data or compute is scarce, not when both are plentiful.
  • Adapt query and value first. At a fixed parameter budget, LoRA on the query and value projections together did best (the LoRA paper, section 7.1).
  • Soft prompts need a big model. Prompt tuning trails full fine-tuning on base-size models and closes the gap only as models exceed billions of parameters (the prompt tuning paper).
  • Frozen does not mean forget-proof. The backbone is safe, but the adapter can still overfit 500 examples, learning those few examples too closely instead of the pattern that carries to new examples. Validate like always.

8 Combining adapters with quantization

Adapters shrink what is trained. Quantization, storing each weight with fewer bits, shrinks what is stored: the frozen 98 percent of the model still has to live in memory at inference time. The attention projections LoRA wraps are taught in Attention.
