Building Agents That Work

The shape of the task picks the pattern, not the other way round.

1 Start with the simplest thing

Every page in this section taught a fancier system than the last. This page steps back and asks which one a task actually needs. The guide's rule is plain: find the simplest solution possible, and add complexity only when it demonstrably improves the outcome. Many tasks need no agent at all. A single well-prompted call, with retrieval and a few examples, handles a surprising share of real work.

When one call is not enough, the order is fixed. First a workflow, when the task breaks into steps that are known ahead of time. Then an agent, when the steps cannot be known ahead of time. Each step up the ladder trades latency and cost for better task performance, so the extra machinery has to earn its keep by being measured, not by looking sophisticated.

The patterns on this page run at inference, once per task. Nothing is trained here: a pattern is the shape of the calls, not a model. The task, together with the pattern's working memory, the outline written so far, the tickets sorted so far, the draft so far, is the state the pattern carries from one call to the next.

2 Workflows against agents

An agentic system is the umbrella term for everything in this space: any system that joins a language model with tools. Inside it, the guide draws one architectural line. A workflow is a system where the model and tools are orchestrated through predefined code paths. An agent is a system where the model dynamically directs its own processes and tool usage, keeping control over how it accomplishes the task.

The difference is who holds the control, and who decides the next step. In a workflow, the next step is written down before the task starts, and the model fills in the steps. In an agent, the model decides the next step at each turn, from the ground truth the environment returned: a tool result, a test run, the state of a file. ReAct taught that loop, one thought and one action at a time, and an agent is that loop running free.

That freedom is why agents fit open-ended work, and why they are the wrong default. A workflow gives predictability and consistency for a well-defined task: the same input walks the same path. An agent fits a problem where the number of steps cannot be predicted and the path cannot be hardcoded, and where the model can be trusted to decide. The guide's own agent examples are a coding agent that resolves GitHub issues and a computer use agent that operates a computer to finish tasks.

3 The five patterns

Five workflow patterns cover most of what teams build in production, plus the agent at the end of the line. Each pattern is one shape of fixed control flow, built from the same building block: an augmented language model, a model with retrieval, tools, and memory added, that MCP can wire to third-party tools. The patterns are not a recipe: a chain can sit inside a routing branch, and an evaluator can watch an orchestrator. The test for any combination is whether it improves the outcome.

3.1 Prompt chaining

Prompt chaining breaks a task into a sequence of steps, where each call processes the output of the previous one. A gate is a programmatic check on an intermediate step, a test the output must pass before the chain continues. Chaining fits a task that decomposes cleanly into fixed subtasks. The point is to trade latency for accuracy, by making each call an easier job.

The guide's example is a document: write an outline, check it against the criteria, then write the document from the checked outline. The same shape writes marketing copy and then translates it.

3.2 Routing

Routing classifies an input and directs it to a specialized followup task. It fits a complex task with distinct categories that are better handled separately, where the classification can be handled accurately, by a model or by a plain classifier. The contrast with chaining is the shape of the flow: chaining runs every step for every input, while routing picks one path per input.

The field example from the guide is customer support: general questions, refund requests, and technical support each go to their own downstream process, with their own prompts and tools. MRKL taught the same idea as a router over expert tools; routing here is the workflow shape that router sits in. Routing can also split by cost: easy questions go to a small cheap model, hard ones to a stronger model.

3.3 Parallelization

Parallelization runs calls at the same time and aggregates their outputs with code. It comes in two variations, and the contrast between them is what they repeat. Sectioning breaks a task into independent subtasks run in parallel. Voting runs the same task several times to get diverse outputs. Parallelization fits work where the divided parts can run side by side for speed, or where several views are needed for higher confidence.

The field examples from the guide show both variations. Sectioning runs a guardrail as its own call: one model instance answers the user while another screens the same request for inappropriate content, which works better than asking one call to do both jobs. Voting reviews code for flaws with several different prompts, and flags the code if any of them finds a problem.

3.4 Orchestrator-workers

In the orchestrator-workers pattern, a central model dynamically breaks down the task, delegates the parts to worker models, and synthesizes their results. It fits complex tasks where the subtasks cannot be predicted ahead of time: in coding, the number of files that need changing and the change in each file depend on the task. The contrast with parallelization is flexibility. Parallelization fixes the parts before the work starts; the orchestrator decides the parts from the input itself.

The guide's examples are coding products that change many files at a time, and search tasks that gather from many sources.

3.5 Evaluator-optimizer

In the evaluator-optimizer pattern, one call generates a response while another provides evaluation and feedback in a loop. It fits work with clear evaluation criteria, where iterative refinement measurably improves the answer. Two signs mark a good fit: a human can articulate feedback that improves the response, and the model can provide such feedback. The shape mirrors how a human writer revises a draft.

The guide's examples are literary translation, where an evaluator catches nuances the first draft missed, and complex search, where the evaluator decides whether further rounds are warranted.

4 Tools deserve the same care as prompts

A tool definition gets the same prompt engineering attention as the overall prompt. The tool layer is the agent-computer interface, the ACI, a deliberate echo of the human-computer interface, the HCI. A product team invests in its interface because that is where users succeed or fail; an agent builder invests the same effort in the ACI, because that is where the model succeeds or fails.

Formats that look the same to a person can differ sharply to a model. Writing an edit as a diff means knowing how many lines change in the chunk header before the new text is written. Writing code inside JSON means extra escaping of newlines and quotes. Three rules follow: give the model room to think before it writes itself into a corner, keep the format close to what the model has seen in ordinary text, and strip formatting overhead like counting thousands of lines.

Three practices make a tool usable. First, put yourself in the model's shoes: if the description leaves you guessing, it leaves the model guessing too, so a good definition carries example usage, edge cases, input format, and boundaries from other tools. Second, test how the model uses the tools on many example inputs and iterate on the mistakes. Third, make mistakes hard to make. The design term for that is poka-yoke, shaping the arguments so the wrong call is hard to write. The guide's field example is a coding agent that kept failing with relative file paths after moving out of the root directory, so the tool was changed to always require absolute file paths, and the model used it without error. The team spent more time optimizing the tools than the overall prompt.

5 Guardrails and stopping conditions

An agent runs on its own for many turns, so its limits are built in before it starts. A guardrail is a check that screens what goes in or out, and a stopping condition is a rule that ends the run. The usual stopping conditions are the task being done and a maximum number of iterations. An agent with neither will run until something outside it stops it.

At each step the agent checks its progress against ground truth from the environment, a tool result, a test run, the state of a file, rather than against its own words. Pausing for human feedback at checkpoints, or when the agent hits a blocker, is part of the design, not a failure of it.

Before an agent touches a trusted setting, it is tested in a sandbox, an isolated environment where it can run code and make mistakes without touching real data. The guide recommends extensive sandbox testing with guardrails in place.

6 Practice

What a pattern costs is the model calls it makes: one call per step for chaining, one classify call and one followup for routing, one per branch for parallelization, one to break the task down plus one per worker plus one to synthesize for orchestrator-workers, a generator call and an evaluator call per loop round, and one call per turn for an agent, until it stops.

The headline setting is the five workflow patterns (Anthropic guide). There is one pattern choice per task: pick the pattern from the shape of the task, and measure whether the extra complexity improves the outcome before keeping it. There is no training run and no tuning here: the setting is the pattern choice.

The guide is the reference, verified live: Building Effective Agents. The guide itself carries a note that the tooling landscape has changed since it was written, and points to the newer post on Managed Agents for the current approach: Scaling Managed Agents. The patterns are the reference; the tooling list is a snapshot.

7 What breaks

Three failures cover most of what goes wrong, each with a cause, a visible symptom, and a fix.

7.1 A runaway agent

Cause: no stopping condition, so the loop never ends on its own. Symptom: the agent keeps calling tools long after the task is done, or circles between two failed approaches, each turn spending more calls. Fix: a maximum iteration count and a done check at each step, tested in a sandbox before the agent runs loose.

7.2 Compounding errors

Cause: each step builds on the last, so one wrong tool result steers every later step. Symptom: a small early mistake grows into a wrong answer the agent states with confidence, because nothing along the way checked the work. Fix: ground truth checks at each step, a test run or a fresh tool read, and a human checkpoint before anything irreversible.

7.3 Guardrails that fire too late

Cause: the check runs after the action instead of before it, or the same call handles both the guardrail and the answer. Symptom: an inappropriate request is already answered, or a harmful call already ran, before the screen catches it. Fix: run the screen as its own call before the answer, and put the guardrail on the path the action must pass through.
