Gradient Balancing Inside the Training Loop

What the loss, the optimizer, clipping and logging do to a balanced gradient.

Each task, one job the shared model learns, has a loss, its error score, and a gradient, the direction in which that loss rises fastest. The balancer combines the task gradients into one balanced gradient; this page follows it through the rest of the loop.

A balanced gradient can still give an unbalanced step

The balancer can do exactly what it promises and the step can still come out unbalanced, because the loop around it shapes what it sees and what happens next. Here is one step: K is the number of tasks, shared the shared layers' weights and head_params the heads' weights and loss_params any learned loss weights.

# one task's gradient as one vector
flat = lambda g: torch.cat(
    [t.flatten() for t in g])

for x, ys in loader:
    # shared layers
    feats = backbone(x)
    # 1 forward: loss weights w act here
    losses = [w[k] * crit[k](
                  heads[k](feats), ys[k])
              for k in range(K)]
    # 2 backward: one pass per task
    grads = [flat(torch.autograd.grad(
                 L, shared,
                 retain_graph=True))
             for L in losses]
    # 3 balance: PCGrad, MGDA, ...
    write_grads(shared, balance(grads))
    # heads get their own task's
    # gradient; learned loss weights
    # (the log sigmas) are added here
    sum(losses).backward(
        inputs=head_params + loss_params)
    # 4 clip
    nn.utils.clip_grad_norm_(
        params, max_norm)
    # 5 optimizer step
    opt.step(); opt.zero_grad()
    # 6 log
    log(losses, grads)

One training step, in six stages

Loss-weighting methods (GradNorm, Uncertainty Weighting) set the task weights w at stage 1. Gradient methods (PCGrad, GradVac, CAGrad, MGDA) replace the plain sum at stage 3. The shared layers are the part every task uses; each task also has its own head.

Loss-weighting methods light up in amber, gradient methods in purple.

Loss-weighting methods act through the loss, gradient methods replace the summed gradient, then clipping and the optimizer act.

The loss sets the scale every balancer sees

A loss's scale, set by its reduction (mean or sum over the batch) or any constant in front of it, changes the gradient's length but never its direction. Length is what balancers compare.

Scaling a loss scales its gradient.
∇(c L) = c ∇L
Multiply the loss L by a constant c and its gradient ∇L comes out c times longer, pointing the same way.
# averaged over the batch
crit = nn.MSELoss(reduction="mean")
# n times larger, n = number of
# elements: same direction, an
# n times longer gradient
crit = nn.MSELoss(reduction="sum")

Loss-weighting methods undo a constant scale once their weights adapt. Gradient methods feel it directly: with the pair (3, 1) and (−1, 2) and task 1's loss times 10, PCGrad turns 28.5 degrees toward task 1 and MGDA 28.5 degrees away.

Adam's step comes from an average of past balanced gradients

Plain SGD, stochastic gradient descent, steps against the gradient times the learning rate. Adam keeps two running averages for each axis, that is, for each weight.

Adam's step, from the balanced gradient g.
mt = β1 mt−1 + (1 − β1) gt
The first moment m, Adam's momentum, averages past balanced gradients g. With β1 at 0.9 it spans about 10 steps, one over (1 − β1), so this step's g gets 10 percent of the weight.
vt = β2 vt−1 + (1 − β2) gt2
The second moment v averages squared gradients, axis by axis. With β2 at 0.999 it spans about 1000 steps.
Δθ = −η m̂t√v̂t + ε
The step Δθ is the learning rate η times the momentum divided by the per-axis scale, the square root of v̂. The hats mark Adam's early-step correction, and ε is a tiny number that avoids dividing by zero.

The ten-step average smooths noise but lags: after a 90 degree turn the momentum needs 7 steps to turn 45 degrees. Adam's step itself can turn in 1 step, onto an axis that was quiet, so the lagging arrow below is the momentum, not the step.

Watching the momentum follow a turn

The dashed noise-free direction turns 90 degrees at step 150. At 0 the momentum jumps with the noise, at 0.9 it settles within a few steps, at 0.99 it is halfway round about 50 steps later.

Adam's per-axis scale reshapes the balanced step

The per-axis division cancels some of the balancer's changes, delays others, and tilts every step.

Adam cancels a steady scale, and absorbs a sudden change only slowly

A steady common factor cancels.
c m̂t√(c2 v̂t) = m̂t√v̂t
Multiply every gradient by a steady positive c: the momentum grows by c and the per-axis scale by √c2 = c, so the step does not change (ignoring ε). This holds while c stays steady over the second moment's 1000 or so steps.

A change in the task mix is not a common factor: Adam's step turns with it at first, then turns back as each axis's scale catches up.

The per-axis scale tilts each step off the balanced direction

The two-bowl example: two tasks share two weights, each loss a bowl, lowest at (3, 0) and (0, 3), ten times steeper along one weight, balanced by PCGrad. The Pareto set is the curve where neither loss can improve without the other getting worse.

Adam's step sits about 8 degrees off the balanced direction (median, far from the Pareto set), almost all from the per-axis scale, and the run ends at a different point of the same set.

What each balancer promises, and where the optimizer comes in

PCGrad's and MGDA's guarantees are about the direction they hand over, for one batch. Momentum and the per-axis scale change the step after that.

Momentum can bring back a direction PCGrad removed

Momentum, here as in PyTorch's SGD (optimizers page), carries the past into every step.

Momentum after a PCGrad step.
m2 = β m1 + g2PC
The momentum m2 is β, here 0.9, times last step's momentum plus this step's PCGrad output g2PC. If m1 holds a part of task 1's gradient that fights task 2, cutting it from this step's gradient does not cut it from m1.

On step 1 the gradients agree and PCGrad leaves them alone; on step 2 it cuts the conflict, yet the momentum still leans against task 2.

Training still converges: for two smooth, strongly bowl-shaped losses with exact gradients and tuned step sizes, Yu and coauthors prove PCGrad with plain momentum reaches either the optimum or a point where the two gradients point exactly opposite.

MGDA's shrinking gradient is not a clean stop signal

Near the Pareto front, the trade-off curve of the losses, MGDA's combined gradient levels off at the noise level instead of reaching zero, and Adam's step stays at 13 to 19 percent of its first size against 2 to 5 percent for SGD. Watch the per-task losses, not a size.

The optimizer and the balancer's own numbers

The balancer's own learned numbers, GradNorm's task weights and Uncertainty Weighting's sigmas, meet the optimizer too.

GradNorm keeps its task weights summing to the task count

Without renormalizing, the weights' sum drifts and acts as a learning-rate change; Chen and coauthors renormalize “to decouple gradient normalization from the global learning rate”.

# GradNorm's own loss, on w only
loss_w.backward()
opt_w.step()
# renormalize: the weights sum to K
with torch.no_grad():
    w.mul_(K / w.sum())

Weight decay skips the balancer, unless it decays the balancer's own numbers

Weight decay shrinks the weights a little every step, inside opt.step(), after the balancer has written the gradient, so the balancer never sees it.

# coupled L2: wd * weights is added
# to the gradient, then momentum
# and the per-axis scale act on it
opt = torch.optim.Adam(
    params, lr=lr, weight_decay=wd)
# decoupled: shrinks the weights
# directly
opt = torch.optim.AdamW(
    params, lr=lr, weight_decay=wd)

An L2 penalty written into a task's loss does pass through the balancer. Decay on Uncertainty Weighting's log sigma pulls each task's weight toward its value at sigma 1: 0.5 for regression, 1 for classification.

As sigma falls, a task's effective learning rate rises under SGD

A regression task's effective learning rate under SGD.
ηk = η2 σk2
Task k's effective learning rate ηk, how far one step moves the weights for that task's error, is the learning rate η times its loss weight. As its noise level σk falls, ηk rises, with or without momentum.

Kendall and coauthors, training three street-scene tasks with SGD with momentum, saw all three uncertainties fall and lowered the learning rate on a schedule. Under Adam, the per-axis scale on a task's head largely absorbs a slow weight change.

Only global clipping keeps the balanced direction

Global-norm clipping.
g ← g · min(1, τ‖g‖)
If the whole gradient g is longer than the max norm τ, every number in it is multiplied by the same factor, so its direction, and the balancing, survive.
# global: one factor, direction kept
total = nn.utils.clip_grad_norm_(
    params, tau)

# per task, before balance: a
# balancing change of its own
grads = [g * torch.clamp(
             tau / g.norm(), max=1.0)
         for g in grads]

# per value: each number clamped,
# so the direction turns
nn.utils.clip_grad_value_(
    params, clip_value)

Mixed precision multiplies every gradient by one number

Mixed precision multiplies every loss by one scale s so small gradients do not round to zero. Every task carries the same s, so no balancer's direction changes.

Sizes compared with fixed numbers need dividing by s, and balancer state changes only on steps where the network's update was not skipped.

scaler = torch.amp.GradScaler("cuda")
# every gradient is s times too large
grads = [flat(torch.autograd.grad(
             scaler.scale(L), shared,
             retain_graph=True))
         for L in losses]
s = scaler.get_scale()
# true sizes, for GradNorm and logs
sizes = [g.norm() / s for g in grads]
write_grads(shared, balance(grads))
scaler.scale(sum(losses)).backward(
    inputs=head_params)
# divide every gradient by s
scaler.unscale_(opt)
nn.utils.clip_grad_norm_(
    params, max_norm)
# skipped on inf or NaN
scaler.step(opt)
scaler.update()
# the scale drops only after a skip
skipped = scaler.get_scale() < s
if not skipped:
    commit_balancer_state()

Balance each micro-batch, or balance their average

A batch too big for memory is split into micro-batches. Two ways to balance them:

# average the parts, balance once
g_once = balance(mean(part_grads))
# balance each part, then average
g_each = mean(
    [balance(g) for g in part_grads])

Balancing is not linear, so with noise they differ: about 8 degrees for PCGrad and 20 for MGDA (median, two-bowl example, 4 micro-batches).

What to log to see each interaction

The weighted total loss hides all of this. The cosine between two gradients is 1 when they agree, 0 at a right angle, negative when they fight.

# raw_losses: the losses before w;
# s, total, skipped: from the blocks
# above. f: true per-task gradients
f = [g / s for g in grads]
# unweighted losses, every step
log("loss/raw",
    [L.item() for L in raw_losses])
# what the balancer sees
log("grad/size",
    [g.norm().item() for g in f])
log("grad/cos", F.cosine_similarity(
    f[0], f[1], dim=0).item())
# or the sigmas
log("weights", w.tolist())
log("grad/before_clip", total.item())
# balancer state is not changed
# on skipped steps
log("amp/skipped", skipped)

Compare each raw loss with that task trained alone, and log how much each number varies, not only its average.

Loss weights act before the backward pass, gradient methods after it

The two weighting methods, the volume knobs that learn each task's loss weight (GradNorm and Uncertainty Weighting), and the four gradient methods, PCGrad, GradVac, CAGrad, and MGDA, which stops at a Pareto-stationary point (where no small step lowers every task's loss at once), side by side:

MethodThe question it answers
GradNormHow loud should each task be, to keep progress balanced? (learned, driven by training dynamics)
Uncertainty WeightingHow loud should each task be, given how noisy it inherently is? (learned, driven by the data)
PCGradHow should the directions be edited so tasks stop fighting?
GradVacHow should each pair of tasks be nudged back to the agreement level where it learns best?
CAGradHow do we protect the worst-off task and stay near the average, with a guarantee?
MGDAWhat direction helps every task at once, and where does the run stop?
