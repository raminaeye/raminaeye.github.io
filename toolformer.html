Toolformer: A Model That Teaches Itself to Use Tools

A tool call is kept only when its answer makes the next words easier to predict.

1 The model does not know when a tool would help

Ask a language model for a fact it never saw, and it answers from memory anyway. Ask it to add, and it can slip a digit. Ask it what day it is, and it has no way to know. A search engine, a calculator and a calendar would fix all three, but the model has no idea when to reach for one.

ReAct: Thinking and Acting in One Loop hands the model its tools through the prompt: a few full traces show when to search and what to do with the answer. Toolformer takes the other road. It teaches the model to call tools by fine tuning, so the choice lives in the weights and not in the prompt. No human labels the right moments. The model finds them itself, by checking which calls make the next words easier to predict.

Training is a one-time fine tune on text the model augmented itself. At inference the model calls tools as it writes, at most one call per passage, with no state carried between passages. The passage is the unit: the model writes, calls, reads the answer, and keeps writing.

2 Propose, execute, keep what helps

Three steps turn plain text into training text. The model proposes calls, runs them, and keeps only the ones that help. This section walks each step. The next section teaches the filter that decides what helps.

2.1 A call is marked text

An API call is a request to a tool, written as text inside the passage. A tool is a program outside the model: a search engine, a calculator, a calendar. The call names the tool and gives it an input, and two markers say where the call starts and ends, so the model can write calls as part of ordinary text.

The API marker form. A call written as text.
\(\displaystyle \htmlClass{eqt}{\htmlStyle{color:#2471a3}{e(c)}} = \texttt{<API>} \, \htmlClass{eqt}{\htmlStyle{color:#8e44ad}{a_{c}}} \texttt{(} \htmlClass{eqt}{\htmlStyle{color:#0e6b59}{i_{c}}} \texttt{)} \, \texttt{</API>} \)
Read it as a sentence: the written form of a call is the API marker, then the tool name with its input in brackets, then the closing marker. \(e(c)\) is the call \(c\) written out as text. \(a_{c}\) is the tool name, like QA or Calculator. \(i_{c}\) is the input handed to that tool. The markers are special tokens, so the model can learn to write them the way it writes words.
\(e(c)\) the call written as text \(a_{c}\) the tool name \(i_{c}\) the input to the tool

Once the tool answers, the answer joins the call, after an arrow. The call plus its result is the form that ends up in the training text.

The call plus result form. The answer written into the call.
\(\displaystyle \htmlClass{eqt}{\htmlStyle{color:#2471a3}{e(c, r)}} = \texttt{<API>} \, \htmlClass{eqt}{\htmlStyle{color:#8e44ad}{a_{c}}} \texttt{(} \htmlClass{eqt}{\htmlStyle{color:#0e6b59}{i_{c}}} \texttt{)} \rightarrow \htmlClass{eqt}{\htmlStyle{color:#a04000}{r}} \, \texttt{</API>} \)
Read it as a sentence: the call plus its result is the same written call, with an arrow and the tool's answer before the closing marker. \(r\) is the result the tool returned, as text. The arrow is the marker that tells the model an answer goes here. At inference the model writes up to the arrow, waits for the tool, and the answer is pasted in before it keeps writing.
\(e(c, r)\) the call with its result \(a_{c}\) the tool name \(i_{c}\) the input to the tool \(r\) the result, as text

In practice the markers are plain token sequences, so the vocabulary stays untouched. The page uses the readable form above, with the arrow written as two plain characters in real text.

2.2 The model proposes where a call might start

Given a passage, the model first asks itself where a call might belong. A prompt shows it a few examples of annotated text, and the model scores every position in the passage by the chance it would start a call there. Positions above a sampling threshold are kept, up to a small cap, and the model writes a call at each one.

The chance of starting a call. Where a call might belong.
\(\displaystyle \htmlClass{eqt}{\htmlStyle{color:#2471a3}{p_{i}}} = \htmlClass{eqt}{\htmlStyle{color:#2471a3}{p_{M}}}( \texttt{<API>} \mid \htmlClass{eqt}{\htmlStyle{color:#5d6d7e}{P(\mathbf{x})}}, \htmlClass{eqt}{\htmlStyle{color:#5d6d7e}{x_{1:i-1}}} ) \)
Read it as a sentence: the chance of starting a call at position \(i\) is the chance the model gives to the API marker, given the prompt and the text written so far. \(p_{M}\) is the model, read as a chance over the next token. \(P(\mathbf{x})\) is the prompt, a few annotated examples for this tool. \(x_{1:i-1}\) is the passage up to position \(i\). The bar reads given. A high chance means the model, shown how calls look, expects one here.
\(p_{i}\) the chance of a call at position \(i\) \(p_{M}\) the model, as chances over tokens \(P(\mathbf{x})\) the prompt with annotated examples \(x_{1:i-1}\) the passage written so far

2.3 Every proposed call runs

Proposing is cheap, so the model proposes freely. Every proposed call is then executed for real: the question goes to the answering system, the sum goes to the calculator, the search term goes to the search engine. Each tool returns one text answer. Only after the answers arrive does the filter decide which calls were worth it.

The marker format as text: one call, built as a string and written into the sentence.

question = "What is the approximate length of the Nile?"
answer = "6,853 km"
call = "<API>QA(" + question + ") -> " + answer + "</API>"
text = "The Nile has an approximate length of " + call
text += " 6,853 kilometers, the White Nile being its main source."
  1. 1The call: the tool name, the question, the arrow, the answer.
  2. 2The call written into the sentence, where the model reads it as training text.

3 The loss filter

The filter asks one question: did the answer make the next words easier to predict? Loss here is cross-entropy loss, taught in Cross-Entropy Loss: a score for how badly the model predicts the true next words, lower when the predictions are better. A call is kept only when the answer drops that score by enough.

3.1 The loss after a call

The loss is measured over the words that follow the call, with the call given as a prefix. Words right after the call count the most, since those are the words the answer helps with. Words further out count for less.

The weighted loss after a position. How hard the next words are to predict.
\(\displaystyle \htmlClass{eqt}{\htmlStyle{color:#2471a3}{L_{i}(\mathbf{z})}} = -\sum_{j=i}^{n} \htmlClass{eqt}{\htmlStyle{color:#0e6b59}{w_{j-i}}} \cdot \log \htmlClass{eqt}{\htmlStyle{color:#2471a3}{p_{M}}}( \htmlClass{eqt}{\htmlStyle{color:#5d6d7e}{x_{j}}} \mid \mathbf{z}, \htmlClass{eqt}{\htmlStyle{color:#5d6d7e}{x_{1:j-1}}} ) \)
Read it as a sentence: the loss after position \(i\) is the weighted sum of how surprised the model is by each word from \(i\) to the end, given the prefix. \(\mathbf{z}\) is the prefix, the call or nothing at all. \(x_{j}\) is the word at position \(j\). \(p_{M}\) is the model's chance for that word, and the log turns a small chance into a big surprise. \(w_{j-i}\) is the weight on a word \(j - i\) places after the call, defined in the next line. The minus sign makes the whole sum a loss: better predictions mean a smaller number.
\(L_{i}(\mathbf{z})\) the loss after position \(i\) \(\mathbf{z}\) the prefix, a call or nothing \(w_{j-i}\) the weight on a word after the call \(x_{j}\) the word at position \(j\)

The weights fade with distance. A word right after the call counts fully. Each step further out counts less, and five words out it counts for nothing. Dividing by the sum of all the weights makes them add to one.

The distance fading weights. Nearby words count most.
\(\displaystyle \htmlClass{eqt}{\htmlStyle{color:#0e6b59}{w_{t}}} = \frac{\htmlClass{eqt}{\htmlStyle{color:#0e6b59}{\tilde{w}_{t}}}}{\sum_{s \in \mathbb{N}} \htmlClass{eqt}{\htmlStyle{color:#0e6b59}{\tilde{w}_{s}}}} \quad \text{with} \quad \htmlClass{eqt}{\htmlStyle{color:#0e6b59}{\tilde{w}_{t}}} = \max(0, 1 - 0.2 \cdot t) \)
Read it as a sentence: the weight on a word \(t\) places after the call is its raw weight divided by the sum of all raw weights. \(t\) is the distance from the call. The raw weight starts at 1 and falls by 0.2 each step, and the max with 0 stops it going below nothing. Dividing by the sum makes every weight a share of one whole, so the loss is an average over the words that follow, not a total that grows with passage length.
\(w_{t}\) the weight at distance \(t\) \(\tilde{w}_{t}\) the raw weight before dividing \(t\) how many words after the call

3.2 With the answer, against without it

One loss is not a verdict. The filter compares two: the loss with the call and its answer, against the better of two losses without it. The better of the two is the fair baseline: no call at all, or the call with its answer left out. A call whose question alone helps, because the question restates the fact, should not get credit for the answer.

The kept against dropped comparison. The verdict line decides.
\(\displaystyle \htmlClass{eqt}{\htmlStyle{color:#0e6b59}{L_{i}^{+}}} = \htmlClass{eqt}{\htmlStyle{color:#2471a3}{L_{i}}}( \htmlClass{eqt}{\htmlStyle{color:#2471a3}{e(c_{i}, r_{i})}} ) \)
The loss with the call and its answer. \(L_{i}^{+}\) is the weighted loss when the model is given the call and the result as its prefix. A small value means the answer made the next words easy to predict.
\(\displaystyle \htmlClass{eqt}{\htmlStyle{color:#a04000}{L_{i}^{-}}} = \min( \htmlClass{eqt}{\htmlStyle{color:#2471a3}{L_{i}}}( \varepsilon ), \htmlClass{eqt}{\htmlStyle{color:#2471a3}{L_{i}}}( \htmlClass{eqt}{\htmlStyle{color:#2471a3}{e(c_{i}, \varepsilon)}} ) ) \)
The loss without the answer, taking the better of two cases. \(L_{i}^{-}\) is the smaller of the loss with no call at all and the loss with the call but no result. \(\varepsilon\) is the empty sequence, nothing given. The min reads as the smaller of the two. Whichever is smaller sets the bar the call must beat.
\(\displaystyle \htmlClass{eqt}{\htmlStyle{color:#0e6b59}{L_{i}^{-}}} - \htmlClass{eqt}{\htmlStyle{color:#0e6b59}{L_{i}^{+}}} \geq \htmlClass{eqt}{\htmlStyle{color:#a04000}{\tau_{f}}} \)
The verdict: keep the call only when the answer drops the loss by at least the filtering threshold. \(\tau_{f}\) is the filtering threshold, a setting chosen separately for each tool. The left side is the drop, the loss without the answer minus the loss with it. A big drop means the answer carried real information. A small drop means the model could already predict the words, and the call is dropped.
\(L_{i}^{+}\) the loss with call and answer \(L_{i}^{-}\) the loss without the answer \(\tau_{f}\) the filtering threshold \(\varepsilon\) the empty sequence

Raising the threshold keeps fewer calls, only the ones whose answer cuts the loss the most. Lowering it keeps more calls, including weak ones that barely help. The threshold is the one setting that decides how strict the filter is.

The calls that pass are written back into the text, in place, with their results. The passage the model trained on becomes a passage with calls in it.

The augmented training text. Kept calls written back in.
\(\displaystyle \htmlClass{eqt}{\htmlStyle{color:#2471a3}{\mathbf{x}^{*}}} = \htmlClass{eqt}{\htmlStyle{color:#5d6d7e}{x_{1:i-1}}}, \htmlClass{eqt}{\htmlStyle{color:#2471a3}{e(c_{i}, r_{i})}}, \htmlClass{eqt}{\htmlStyle{color:#5d6d7e}{x_{i:n}}} \)
Read it as a sentence: the augmented text is the passage before the call, then the kept call with its result, then the rest of the passage. \(\mathbf{x}^{*}\) is the new training text. \(x_{1:i-1}\) is everything before position \(i\). \(e(c_{i}, r_{i})\) is the kept call at that position. \(x_{i:n}\) is everything from position \(i\) to the end. A passage with several kept calls gets one inserted call at each kept position. The model fine tunes on this text, and that is how it learns when to call.
\(\mathbf{x}^{*}\) the augmented training text \(x_{1:i-1}\) the passage before the call \(e(c_{i}, r_{i})\) the kept call with its result \(x_{i:n}\) the rest of the passage

4 The five tools

Five tools cover the gaps a language model cannot close on its own. Each takes text in and returns text out, and the model picks which one fits the passage it is writing. Nothing in the prompt says which tool fits where.

  • Question answering. Takes a question and returns a short answer. Example: "Where was the Knights of Columbus founded?" comes back as "New Haven, Connecticut".
  • Wikipedia search. Takes a search term and returns short snippets from Wikipedia. Example: "Fishing Reel Types" returns a passage about spin fishing.
  • Calculator. Takes arithmetic in the four basic operations and returns the result, rounded to two decimal places. Example: "27 + 4 * 2" returns "35".
  • Calendar. Takes no input and returns the current date. Example: "Today is Monday, January 30, 2023."
  • Translation. Takes a phrase in any language and returns it in English. Example: "sûreté nucléaire" returns "nuclear safety".

The tools differ in what they know, not in how they are called. The same marker form wraps every one of them, so the model learns one shape for all five.

5 Practice

The training cost is one fine tune pass over the augmented text, starting from a pretrained language model, with a batch of 128 passages and a learning rate of \(1 \times 10^{-5}\) with linear warmup (the learning rate starts near zero and rises steadily to its full value) over the first tenth of training, from section 4.1 of the paper. At inference each passage costs one model call plus one call to each tool used, and at most one tool call per passage. Decoding pauses when the model writes the arrow marker, runs the tool, and resumes after the answer. The model may start a call whenever the API marker is among the ten most likely next tokens, which makes it readier to call than plain greedy decoding.

The headline setting is the loss drop filtering threshold, \(\tau_{f}\), defined in section 2 and chosen separately for each tool in section 4.1 of the paper. Raising it keeps fewer calls, only the ones whose answer cuts the loss the most. Lowering it keeps more, including calls that barely help.

The paper released no official implementation, so there is no official code to link here.

6 Failure modes

Three failures cover most of what goes wrong. Each has a cause, a visible symptom, and a fix.

6.1 A call that helps the loss but not the reader

Cause: the filter only measures the loss, not whether the answer is on topic. Symptom: a search returns text about the wrong thing and still passes the filter, so the training text carries a call that teaches nothing. Fix: raise the threshold, or check a sample of kept calls by hand and drop the ones that add nothing.

6.2 One tool at a time, never a chain

Cause: calls for each tool are generated on their own, so the training text holds no example of feeding one answer into the next call. Symptom: the model cannot use a search result as a calculator input, or a translation as a search term. Fix: none in this method. Chaining is left to later methods.

6.3 The same fact, different words, no call

Cause: the model is sensitive to the exact wording when it decides to call. Symptom: a rephrased passage gets no call where the original got one, and the fact goes unfilled. Fix: augment with more varied text, or run the pipeline again on the new text so the new phrasings get their own kept calls.

7 What comes next

Toolformer teaches one model to use its own tools. But some questions need an expert, not a lookup: a sum goes to a calculator, a fact goes to a database, a hard question goes to a specialist model. MRKL: Routing Requests to the Right Expert hands each request to the expert that fits it, and the handoff itself is where things break.
