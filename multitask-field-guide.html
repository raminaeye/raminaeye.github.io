2 Measuring each task's loss and gradient

Builds on per-task gradients in one step (Gradient Balancing Inside the Training Loop, Section 3)

Each check reads, per task i, its loss on its own batch and its gradient gi over the shared trunk θsh: one vector over all shared weights, heads left out.

As a running example, take NYUv2, indoor photos with one network learning depth (meters to every pixel) and semantic segmentation (seg, a class for every pixel). Task 1 is depth and task 2 is seg everywhere on this page, in the figures and in the code: task 1 is the long, fast task and task 2 the one that stalls or gets hurt.

Measure each task on its own, its average loss and its gradient on the shared weights, before choosing any fix.
Li = 1Bi Σn ℓi(xn)
Task i's loss Li averages its per-example loss ℓi over the Bi examples xn of that task in the batch; Σ adds over n from 1 to Bi. Averaging keeps the loss on one scale whatever the batch size.
gi = ∇θsh Li
∇ with subscript θsh takes the gradient with respect to the shared weights only: gi has one entry per shared weight, how fast Li rises as that weight grows. Section 4 compares the lengths of these vectors, Section 5 the angle between them.
So every later check on this page reads two measured numbers per task: here depth's and seg's batch-mean losses and their gradients on two shared weights.

Look at task_grad, which turns one task's batch-mean loss into one vector over the trunk.

import torch
import torch.nn as nn
import torch.nn.functional as F
from torch.autograd import grad

torch.manual_seed(0)
trunk = nn.Linear(IN_DIM, HIDDEN)
head1 = nn.Linear(HIDDEN, OUT_DIM)
head2 = nn.Linear(HIDDEN, OUT_DIM)
shared = list(trunk.parameters())

# one batch per task, own sizes
x1 = torch.randn(BATCH1, IN_DIM)
# task 1: targets on a larger scale
y1 = SCALE * torch.randn(BATCH1, OUT_DIM)
x2 = torch.randn(BATCH2, IN_DIM)
y2 = torch.randn(BATCH2, OUT_DIM)

def task_grad(head, x, y):
    out = head(trunk(x))
    loss = F.mse_loss(out, y)
    gs = grad(loss, shared)
    # flatten, join: one vector
    v = [g.flatten() for g in gs]
    return loss, torch.cat(v)

L1, g1 = task_grad(head1, x1, y1)
L2, g2 = task_grad(head2, x2, y2)
  1. 1shared holds the trunk's weights only, marker 3 in Figure 2.
  2. 2One batch per task, each with its own size, marker 1.
  3. 3Loss and gradient over the trunk weights, the two lines of the per-task loss and gradient card.

Log each raw loss and gradient, before task weights and before the mixed-precision loss scaler multiplies them (what to log in the training loop).

PCGrad, GradVac, CAGrad and MGDA by Sener and Koltun (2018) combine task gradients, so they compute every gi each step anyway. With plain weighting or Uncertainty Weighting each logged step costs one backward pass per task; every few hundred steps is a rule of thumb. On a large model, log at the last shared layer only, for every task, as GradNorm by Chen and colleagues (2018) does, at a small extra cost.

3 Loss ratio shows learning speed

With fixed weights a task's share of each step follows its gradient, not how far it still has to go, so a lagging task gets no extra push.

In the failing run of Figure 3, whose logs are illustrative, task 1's ratio falls while task 2's stalls; with task 2 as seg, seg is the task barely learning.

The loss ratio says how much of its starting loss a task still has, so a slow task stands out.
L̃i(t) = Li(t)Li(0)
Li is the batch-averaged loss of Section 2. The loss ratio L̃i divides task i's loss at step t by its loss at step 0, so every task starts at 1 whatever its units, and a faster fall means faster learning. For a cross-entropy task whose first loss depends on the random start, log C, the loss of a uniform guess over C classes, can stand in for Li(0). Single-batch losses are noisy, so compare ratios averaged over many steps; act when one stays over twice another and the gap keeps growing, a rule of thumb.
So a ratio that stays near 1 flags a task that is not learning: in the failing run seg's ratio stalls while depth's falls.

Look at ratio1, task 1's loss ratio.

# L1, L2 from task_grad
# at step 0
L0 = [L1.item(), L2.item()]
# at each logged step
ratio1 = L1.item() / L0[0]
ratio2 = L2.item() / L0[1]

GradNorm raises a lagging task's weight.

4 Gradient norms show loss scale

The step follows the sum of the task gradients, so the longest sets its direction.

In the running example, task 1 is depth and task 2 is seg, so ρ says depth's push is longer than seg's. A common rule of thumb flags a scale problem only when norms sit more than 10 times apart, so this pair has no loss-scale problem; its harm comes from size and direction together, which Section 5.2 tests.

The ratio of the two gradient lengths says whether one task’s loss scale is drowning the other.
ρ = ‖g1‖‖g2‖
g1 and g2 are the gradients of Section 2, and a short one can explain a slow loss ratio from Section 3. The norm ‖gi‖ is the vector's length, the square root of the sum of its squared entries. The ratio ρ (rho) says how many times longer task 1's gradient is: near 1 the two pull about equally. Multiplying a loss by a constant multiplies its gradient's norm by the same constant, so the ratio exposes a scale gap. Centimeters instead of meters multiply a squared loss, and its gradient, by a large factor. Norms over 10 times apart, averaged over many steps, mean a scale problem, a rule of thumb.
So a ρ far from 1 is a loss-scale problem that loss weights can fix; depth and seg are not that far apart.

Look at rho, the norm ratio.

# g1, g2 from task_grad
n1, n2 = g1.norm(), g2.norm()
rho = (n1 / n2).item()

Uncertainty Weighting cancels a fixed scale; GradNorm equalizes the norms.

5 Cosine shows conflicting directions

When two task gradients point partly against each other, a step that lowers one loss raises the other. The cosine measures this regardless of length.

The log keeps m, a running average of the cosine over earlier steps. In the running example this step's cosine is negative, which moves m only a little, because each new step counts for just a small share of the average: one conflicting batch barely shifts it, and many in a row drag it below 0.

The cosine says whether the two tasks pull the same way, and a running average stops one noisy batch from deciding.
cos ψ = ⟨g1, g2⟩‖g1‖ ‖g2‖
This is the direction half of the pair whose lengths Section 4 compares. The dot product ⟨g1, g2⟩ multiplies matching entries and adds them up (the dot product and the cosine); dividing by both norms leaves only the angle ψ (psi). The cosine is 1 for the same direction, 0 at a right angle and negative beyond it; the PCGrad paper calls a negative cosine a conflict.
m ← KEEP m + NEW cos ψ
Single cosines are noisy and often negative in plain joint training, so the log keeps a moving average m: each step keeps most of the old value and adds a little of the new one. Keeping more, such as 0.99, smooths more but reacts later; 0.9 to 0.99 is a common range, a rule of thumb. Act when m stays below 0 for thousands of steps, also a rule of thumb.
So a cosine whose running value stays negative across steps, not one batch, signals real conflict: one conflicting batch barely moves m.

Look at m, the moving average of the cosine.

# n1, n2 from the rho check
dot = (g1 @ g2).item()
cos = dot / (n1 * n2).item()
# first logged step
m = cos
# every later logged step
m = KEEP * m + NEW * cos

For lasting conflict, try PCGrad, GradVac, CAGrad or MGDA, and judge them by the task losses; in most of Recon's tests they change how often conflicts occur only a little.

5.1 Conflicting gradients in a ravine

A ravine is a narrow valley with steep walls and a nearly flat floor. Liu and colleagues (2021), who introduced CAGrad, show gradient descent stuck in one when one task's gradient dominates.

The task steps point in different directions and task 1's is longer, so their sum points across the valley. A smaller learning rate stops the bouncing but slows the crawl; conflict methods shrink the opposing part instead.

5.2 When a conflict raises a task's loss

Yu and colleagues (2020), who introduced PCGrad, argue that conflict hurts mainly when it comes with a large norm gap and high curvature, meaning the loss surface bends sharply so a step that looks small can change the loss a lot; they call the three together the tragic triad. The two-task condition shows the norm part.

In the running example the cosine sits below the threshold, so the summed step d should raise seg's loss: its dot product with seg's gradient is negative.

A conflict raises task 2’s loss once the cosine drops below minus one over ρ, so the larger task 1’s lead in size, the milder the conflict that already hurts task 2.
⟨g2, d⟩ = ‖g2‖2 (1 + ρ cos ψ)
cos ψ is the cosine of Section 5, and d is the summed step. Writing d as g1 plus g2 and expanding gives task 2's own part ‖g2‖2 plus the cross term with task 1, which is ‖g1‖ times ‖g2‖ times cos ψ. Factoring out ‖g2‖2 leaves the norm ratio ρ from Section 4 times the cosine in the bracket.
cos ψ > −1ρ
Task 2 still improves while the bracket is positive, which holds exactly when the cosine stays above minus one over ρ. With equal norms only exactly opposite gradients fail; at a wide gap, even a slightly negative cosine raises task 2's loss.
So the test joins scale and direction into one check of whether the summed step hurts the smaller task: for seg, the first line is negative.

7 Common mistakes when balancing tasks

7.1 Watching only the average

Papers report Δm, the average relative change against single-task models; positive means worse. It can look fine while one task is sacrificed.

7.2 Combining gradients over head weights

PCGrad, GradVac and CAGrad combine gradients over the shared weights only; each head takes its own task's gradient. Head weights in the vectors pull every cosine toward 0: each task’s head entries add length to its gradient but nothing to the dot product, because the other task has 0 there. GradNorm, Uncertainty Weighting and the official MGDA code scale whole losses, which rightly scales their head gradients too.

7.3 Not renormalizing GradNorm's weights

GradNorm's loss weights wi must sum to the number of tasks K; otherwise the total drifts like a changing learning rate (why they sum to the task count).

Look at w.mul_, which rescales the weights to sum to K after each update.

import torch
# weights after a GradNorm step
w = torch.tensor([W1, W2])
K = len(w)  # number of tasks
with torch.no_grad():
    w.mul_(K / w.sum())
# w.sum() is K again

7.4 The cost of one gradient per task

Methods that combine task gradients take one backward pass per task each step. CAGrad's fast variant samples a subset S of tasks and spends one pass per sampled task plus the average. A larger S costs more and nears the full method.

8 Separate datasets and small task batches

Tasks with no shared examples still share the trunk, so their gradients can still conflict (Figure 7); what changes is noise, since each gradient averages only its own examples.

Figure 10 uses this setting: a task's gradient measured on fewer examples per step spreads wider. So if seg trains on fewer images per step beside depth, with the same per-example spread, seg's measured gradient is noisier.

A gradient measured on a small batch is noisy, and the noise falls only with the square root of the batch size.
SD(gi) ≈ si√Bi
gi is the measured gradient of Section 2, and its noise feeds straight into the conflict test of Section 5.2. SD is the standard deviation, the typical size of the random error in each entry of gi from one batch to the next, and si is that standard deviation for a single example. Averaging Bi independent examples divides it by √Bi, so more examples shrink it.
So cosines and ratios measured on the small task wobble, and the running average m of Section 5 is what steadies them: seg's gradient on fewer images is noisier than depth's.

Few examples per step inflate a task's norm and pull its cosines toward 0, so compare tasks with similar counts. Noise also misleads CAGrad, whose step favors the task the average helps least. Three fixes help, in this order.

  1. Oversample the small task (Section 9).
  2. Pick the combining weights from a moving average of each task's gradient, not one batch, at one extra copy per task. MoCo by Fernando and colleagues (2023), unrelated to the contrastive MoCo, does this to remove the bias noisy batches cause.
  3. Lower CAGrad's radius c, which sets how far the step may turn from the average gradient toward the worst-off task. At 0 CAGrad is gradient descent; the convergence guarantee needs c below 1, and very large values approach MGDA.

9 Joint batches and round robin

The checks and methods need every task's gradient at the same weights in one step, which only a joint batch gives. In round robin, one task per step, a step can raise another task's loss unseen.

Look at sampler2, which draws the small dataset with replacement so both loaders run equally long.

import torch
from torch.utils.data import DataLoader, RandomSampler, TensorDataset

# more examples for task 1 than for task 2
ds1 = TensorDataset(torch.randn(N1, IN_DIM), torch.randn(N1, OUT_DIM))
ds2 = TensorDataset(torch.randn(N2, IN_DIM), torch.randn(N2, OUT_DIM))

dl1 = DataLoader(ds1, batch_size=BATCH1, shuffle=True)
# with replacement, BATCH2 per step
sampler2 = RandomSampler(ds2, replacement=True, num_samples=len(dl1) * BATCH2)
dl2 = DataLoader(ds2, batch_size=BATCH2, sampler=sampler2)

for b1, b2 in zip(dl1, dl2):
    L1, g1 = task_grad(head1, *b1)
    L2, g2 = task_grad(head2, *b2)
  1. 1Toy data, more examples for task 1 than for task 2.
  2. 2The small set is drawn with replacement, so both run the same number of steps.
  3. 3A joint batch each step, with task_grad from Section 2.

As a rule of thumb, cap the small dataset at about 3 passes per pass over the largest. If memory is short, keep each task's gradient and combine once all are in.

10 Choosing which losses train the shared trunk

A loss belongs in multitask training only if the trunk's features need it; otherwise train it later on its own head, trunk frozen. The frozen-head test decides in four steps.

  1. Train with one main loss per task; measure each metric.
  2. Freeze the trunk, fine-tune each head with all its losses, and measure again.
  3. If the head reaches the metric you need, the extra losses stay with the head; if not, add that loss to multitask training.
  4. Add losses one at a time.

Each extra loss adds a gradient. MGDA steps opposite the minimum-norm blend of task gradients, which lowers every loss. Once the gradients point in enough different directions, the blend shrinks to zero and no step lowers them all.

11 Trunk capacity and task grouping

Balancing shares out what the trunk can represent; it adds nothing. If separate models still win on every task, try a wider trunk, soft parameter sharing (each task keeps its own layers and they exchange features), or separate trunks for tasks that keep conflicting.
