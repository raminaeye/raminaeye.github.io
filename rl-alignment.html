Aligning Language Models with RL

RLHF, reinforcement learning from human feedback, turns people's rankings of answers into a reward and trains a language model to earn it.

On this page

1 Why RLHF

A large language model (LLM) is a neural network trained to predict the next token, a word or piece of a word, of web text. People want something else from it: to "follow the user's instructions helpfully and safely". Ouyang et al. 2022 call next-token prediction misaligned with that goal and built InstructGPT by tuning GPT-3 with RLHF.

Writing the ideal answer is slow; picking the better of two takes seconds. Copying written answers alone has limits (why copying an expert falls short, on RL Basics), so RLHF also learns from people's rankings of the model's own attempts. The idea comes from Christiano et al. 2017, who trained Atari and simulated-robot agents from people’s picks between two clips.

2 RLHF in three stages

Supervised fine-tuning (SFT) teaches by example, a reward model (RM) learns a score from people's rankings, and RL with PPO, proximal policy optimization (Schulman et al. 2017), raises that score while a KL penalty charges the model for moving away from the SFT model. The stages run in order, and stages 2 and 3 can repeat on rankings of the newest policy’s answers (the InstructGPT paper); only stage 3 trains on answers the policy writes while it trains.

2.1 The language model as an agent

A model writing an answer runs the reinforcement learning loop, and each token it writes is one move.

The score arrives once per answer, which ends the episode (InstructGPT paper, section 3.5). Sampling a token has no gradient, so RLHF uses a policy-gradient update, the REINFORCE idea that PPO refines in stage 3: raise the log-probability of tokens in better-than-expected answers and lower it in worse ones.

In this code, GPT-2 from Hugging Face writes one answer, one token per pass of the loop; the reward model would score the finished state once.

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

MAX_TOKENS = 40
tok = AutoTokenizer.from_pretrained("gpt2")
policy = AutoModelForCausalLM.from_pretrained("gpt2")
END_ID = tok.eos_token_id

state = tok("Explain the moon landing.", return_tensors="pt").input_ids
with torch.no_grad():
    for _ in range(MAX_TOKENS):
        logits = policy(state).logits[0, -1]   # next-token scores
        probs = torch.softmax(logits, dim=-1)
        token = torch.multinomial(probs, 1)    # the move
        state = torch.cat([state, token[None]], dim=1)
        if token.item() == END_ID:
            break
  1. 1Loads GPT-2 as the policy and sets the answer length limit.
  2. 2The prompt is the first state.
  3. 3Scores the next tokens, turns the scores into probabilities and samples one token, the move in Figure 4.
  4. 4Appends the token to the state and stops at the end token.

2.2 Stage 1, supervised fine-tuning

The pretrained model is fine-tuned on answers written by hired labelers, with the usual next-token loss, for 16 epochs.

2.3 Stage 2, the reward model

The reward model, a language model whose last layer outputs one number, learns to score answers the way people rank them. Every pair in a labeler’s ranking becomes a training example. It trains for a single epoch, since more epochs quickly overfit.

The reward model learns by making the preferred answer score higher than the other, pair by pair.
gap = r(x, yw) − r(x, yl)
The gap is how much higher the reward model scores the answer people preferred, r(x, yw) (w for won), than the other answer, r(x, yl) (l for lost), for the same prompt x.
loss = −log sigmoid(gap)
The sigmoid turns the gap into a number between 0 and 1, the reward model's estimate of the chance people prefer yw. The log and the minus sign turn a guess near 1 into a loss near 0, so the loss is small when the preferred answer scores clearly higher and large when the pair is backwards.

A toy reward model on 8 random pairs, each answer 16 made-up numbers instead of text.

import torch
import torch.nn.functional as F

N_FEATURES, N_PAIRS = 16, 8
reward_model = torch.nn.Linear(N_FEATURES, 1)   # toy RM
chosen = torch.randn(N_PAIRS, N_FEATURES)     # y_w; rejected is y_l
rejected = torch.randn(N_PAIRS, N_FEATURES)
r_w = reward_model(chosen).squeeze(-1)
r_l = reward_model(rejected).squeeze(-1)
gap = r_w - r_l
loss = -F.logsigmoid(gap).mean()   # stable -log sigmoid
loss.backward()
  1. 1A toy reward model and 8 random answer pairs.
  2. 2Gap, eq card in Section 2.3, line 1.
  3. 3Loss, line 2, then the gradient.

2.4 Stage 3, RL with PPO

The policy, a copy of the SFT model, answers a fresh prompt, the frozen reward model scores it, and PPO (an actor-critic method that limits how far each update moves the policy) updates the policy to raise the score. InstructGPT ran about 256,000 such episodes.

Stage 3 maximizes reward minus a KL penalty, averaged over prompts and sampled answers.
KL = log π(y |⁠ x)πSFT(y |⁠ x)
π(y | x) is the chance the policy being trained writes answer y to prompt x, and πSFT(y | x) the chance the frozen SFT model would. The log of their ratio estimates the KL divergence from one answer; averaged over answers the policy writes, the KL divergence measures how far the policy has moved from the SFT model.
objective = r(x, y) − β · KL
The score r(x, y) minus β times KL; a larger β, 0.02 by default in InstructGPT, keeps the policy closer to the SFT model. The penalty stops the policy from drifting into answers that fool the reward model (Section 4).

The code uses toy numbers for one 12-token answer, with the KL penalty on every token and the score on the last one only.

import torch

BETA, N_TOKENS = 0.02, 12   # InstructGPT's beta
log_pi = -torch.rand(N_TOKENS)       # toy log pi per token
log_pi_sft = -torch.rand(N_TOKENS)
score = torch.tensor(1.3)
kl = log_pi - log_pi_sft
reward = -BETA * kl
reward[-1] += score   # score on the last token
objective = reward.sum()
  1. 1Toy per-token log-probabilities and a reward model score.
  2. 2Per-token KL estimate, eq card in Section 2.4, line 1, scaled by β.
  3. 3Adds the score on the last token and sums, line 2.
The best policy reweights the SFT model’s answers by their reward.
weight = expr(x, y)β
Each answer’s weight is exp of its reward r(x, y) divided by β. A small β makes the top-reward answer’s weight dwarf the rest; a large one keeps every weight near 1.
π*(y |⁠ x) ∝ πSFT(y |⁠ x) · weight
The best policy multiplies each SFT probability by that weight, then rescales to sum to 1; ∝ reads “proportional to” (the DPO paper, eq. 4). So a small β puts nearly all probability on the top-reward answer, and a large one barely changes the SFT model.

InstructGPT aligns to one group, mostly the labelers and researchers, and still makes simple mistakes.

4 Reward over-optimization

A reward model is a learned reward with flaws, and stage 3 finds and exploits them: reward hacking, as with the toy agent on RL Basics. Gao et al. 2022 measured this with a reward model standing in for people:

PartOver-optimization setup
Stand-in for peoplea fixed 6B "gold" reward model in the InstructGPT setting
Proxy reward models (what training sees)3M to 3B parameters (M = million), trained on the gold model's preferences
Policy1.2B parameters, trained with PPO against one proxy, no KL penalty in the main runs
Measuredgold and proxy reward model scores as the policy drifts from its starting model, drift measured by KL divergence

A KL penalty did not lift the gold curve: at the same KL distance the gold score came out about the same, so the penalty acted like stopping early.

Answer length is one measured flaw. PPO lengthened answers on all three preference datasets Singhal et al. 2023 tested, among them the WebGPT comparisons, people’s picks between two web-search answers. Judged by OpenAI models standing in for people (AlpacaFarm), a reward for length alone nearly matched standard PPO.

5 Newer alignment methods

Newer methods drop parts of the RLHF pipeline (Figure 9).

DPO, direct preference optimization (Rafailov et al. 2023), trains the language model directly on preference pairs collected beforehand, sampling nothing during training.

DPO reads a reward off the policy and reuses the reward-model loss.
rDPO(x, y) = β · (log π(y |⁠ x) − log πSFT(y |⁠ x))
rDPO(x, y) is β times the log of how much more likely the policy makes answer y than the SFT model does. It is the best-policy line of Section 2.4 solved for the reward, minus a term that depends only on the prompt (the paper’s eq. 5), so the policy carries its own reward. The paper writes πref for the frozen SFT model.
gap = rDPO(x, yw) − rDPO(x, yl)
The preferred answer’s DPO reward minus the other’s, as in stage 2; the prompt-only term is the same for both answers and cancels.
loss = −log sigmoid(gap)
The stage 2 loss on that gap, training the policy itself with no reward model or RL loop (the paper’s eq. 7).

One DPO loss on a batch of pairs. Each input is the summed log-probability of a whole answer; the ref_ ones come from the frozen SFT model without gradients.

import torch.nn.functional as F

BETA = 0.1   # the DPO paper's value

def dpo_loss(logp_w, logp_l, ref_logp_w, ref_logp_l):
    r_w = BETA * (logp_w - ref_logp_w)   # r_DPO(x, y_w)
    r_l = BETA * (logp_l - ref_logp_l)   # r_DPO(x, y_l)
    gap = r_w - r_l
    return -F.logsigmoid(gap).mean()
  1. 1rDPO for both answers, eq card in Section 5, line 1.
  2. 2Gap, line 2.
  3. 3Loss, line 3.

5.2 GRPO

GRPO, group relative policy optimization (Shao et al. 2024, the DeepSeekMath paper), is PPO with its clipped step kept and the critic dropped. It samples a group of answers to one question and judges each against the group.

GRPO scores each answer against its own group.
Ai = ri − mean(r)std(r)
The advantage Ai of answer i is its reward ri minus the group average mean(r), divided by the group spread std(r), over the 64 answers per question in DeepSeekMath. The group average replaces a critic’s estimate, and every token of answer i gets the same Ai.

One GRPO loss for one question: the group’s rewards become Ai, and the rest is PPO’s clipped objective per token, without the KL term.

import torch

EPS_CLIP = 0.2   # PPO's clip

def grpo_loss(log_pi, old_log_pi, rewards):
    # log_pi, old_log_pi: (G, T) per-token log-probs
    A = (rewards - rewards.mean()) / (rewards.std() + 1e-8)
    A = A[:, None]   # same A_i for every token of answer i
    ratio = torch.exp(log_pi - old_log_pi.detach())
    clipped = ratio.clamp(1 - EPS_CLIP, 1 + EPS_CLIP)
    objective = torch.min(ratio * A, clipped * A)
    return -objective.mean()
  1. 1Group advantage, eq card in Section 5.2, line 1, one value per answer.
  2. 2PPO’s ratio, clip and objective, the PPO clipping eq card in Policy-Based and Actor-Critic Methods: REINFORCE, PPO and SAC.
  3. 3Loss for the group; the KL term to the reference (β in Section 5.3) is left out to keep the snippet short.

5.3 GRPO in practice

Runssample 64 answers per question up to 1,024 tokens, score them, then a single update per sampling round; batch 1,024 (DeepSeekMath)
Carriesno critic; the sampling policy’s log-probabilities and a reference for the KL term
Costgenerating 64 answers per question and a reward for each, then one backward pass per round
Group size Ganswers per question; more gives a steadier group average, 1 gives no comparison at all; 64 in DeepSeekMath
KL βweights the KL term like RLHF’s β; higher stays closer to the reference, 0 turns the term off; 0.04 in DeepSeekMath, 0 by default in TRL
Clip εas in PPO: wider allows bigger changes per round, 0 freezes the policy; 0.2 in the PPO paper
CodeHugging Face TRL GRPO trainer
Gotchasa group where every answer scores the same gives A = 0 and teaches nothing (TRL logs frac_reward_zero_std); dividing by std can bias toward question difficulty (TRL scale_rewards)

When an answer can be checked automatically, a rule replaces the reward model. DeepSeek-R1-Zero (DeepSeek-AI 2025, section 2.2.2) used GRPO and checked a final math answer against the known one, ran code against set test cases, and required reasoning inside marked tags, with no learned reward model, since a learned one can be gamed.

In the on-policy and off-policy terms of RL Method Families and Value-Based Methods, PPO-based RLHF and GRPO are on-policy, learning from answers the current policy just wrote, while DPO learns offline from a fixed set of pairs (the GRPO paper).
