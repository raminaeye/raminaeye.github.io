The Multitask Field Guide

Diagnose which failure you have, batch every task in every step, admit only the losses that must shape the shared trunk, and know what no optimizer can fix.

Three failures break multitask training: scale, speed, and direction (the Introduction to Multitask Learning draws each one, with the geometry that tells them apart). Three lines of logging tell you which one you actually have, and the rest is running that shared trunk, the layers all tasks share, well.

Diagnose your failure mode first

Three lines of logging tell you which of the three failures you actually have. Only then do you pick the fix.

  1. Each task's loss, compared with training that task alone and with its own starting value. A loss is the task's error score, the number training lowers. Doing worse than the task trained alone is negative transfer. Each loss divided by its starting value shows how far that task has come; if one ratio has fallen far below another, you have a speed problem.
  2. Each task's gradient norm at a shared layer (a task's gradient is the arrow pointing where its loss rises fastest, and its norm is that arrow's length on the shared trunk). If one is orders of magnitude bigger than the others, you have a scale problem.
  3. The cosine between each pair of task gradients. The cosine scores how much two arrows agree in direction, ignoring their lengths. If it is often negative, you have a direction problem.

The norm and the cosine are each one line of arithmetic from “The math kit: norms, dot products, gradients” on the Introduction to Multitask Learning page. A cosine of 1 is the same direction, 0 perpendicular and −1 opposed. If one task's arrow is far longer, the quiet gradients vanish in the plain average, and Uncertainty Weighting or GradNorm rebalance the loudness; GradNorm also adjusts the balance as training goes, which is the fix for a speed problem. Near −1, a step against the average raises the quieter task's loss, and the fix is removing the fighting part of the update.

# flat joins one task's gradient
g1, g2 = (flat(torch.autograd.grad(
              L, shared,
              retain_graph=True))
          for L in (L1, L2))
# speed: one ratio far below other
print(L1.item() / L1_start,
      L2.item() / L2_start)
# scale: sizes far apart
print(g1.norm(), g2.norm())
# direction: often negative
print(F.cosine_similarity(
    g1, g2, dim=0))

A fight does not always fade on its own. In a ravine, a long narrow valley in the loss landscape with steep walls and a nearly flat floor, plain gradient descent (a small step against the gradient each update) needs a step small enough not to bounce between the walls, which is too small to move far along the floor. If each task pulls toward a different wall, the run crawls and the two gradients keep fighting.

Once a balancing method is running, “What to log to see each interaction” in Gradient Balancing Inside the Training Loop lists what else to watch and where in the training step to read it.

Five multitask mistakes to avoid

Each of these five mistakes quietly undoes what the balancing methods are trying to do.

  1. Watching only the average loss. A great average can hide a task that was quietly sacrificed. Report each task's own number too, ideally how far it falls short of its single-task baseline, the run where that task trains on its own. Averaging those shortfalls over the tasks gives one summary score in which every task counts equally.
  2. Running gradient methods in the task-specific heads, the final output layers each task keeps for itself. By gradient methods I mean editing how the task gradients are combined (PCGrad, GradVac, CAGrad, MGDA), rather than changing how loud each loss is. Heads share no parameters (the numbers training adjusts), so there is nothing to fight over. Combine gradients on the shared trunk only.
  3. Forgetting to renormalize after reweighting. Renormalizing means rescaling the task weights (each task's loss weight) back to a fixed total after reweighting. Without it, the task weights slowly change the overall learning speed, and the comparison against baselines stops meaning anything.
  4. Running a full K-task gradient method (K is the number of tasks) on a 50-task problem. Its real price is K backward passes per step, where a backward pass is the reverse run through the network that computes one task's gradients. To cut that cost, sample a handful of tasks each step, as the fast variant of CAGrad does. Sampling pairs alone is not enough, since every task in a sampled pair still needs its own backward pass.
  5. Treating every conflict as poison. Yu and coauthors, who introduced PCGrad, the method that cuts the part of each gradient that fights another, argue that conflict mostly hurts when it arrives together with two other conditions: high curvature, meaning the loss surface bends sharply, and a large gap in gradient sizes. They call the three together the tragic triad. Mild conflict between equals is often harmless.

Multitask deployment: what actually matters

“Our tasks have disjoint datasets. Does this still apply?” Yes. Every task can have its own dataset, with no example shared between datasets, and its own head; the gradients still meet in one place, the shared trunk. Conflict is a property of gradients on shared parameters, not of shared data.

A shared trunk with one output per task goes back to Caruana's original multitask networks. The per-task dataset, per-task head, shared-trunk setup is the standard case these methods were built on. They would only become irrelevant if the tasks shared nothing at all, and then it would not be multitask learning. To convince a skeptic, log the cosine similarity between pairs of task gradients on the shared trunk for a few hundred steps. If the cosines go negative, and in many setups they do, the conflict is real.

“What if one task's batch is much smaller?” A small batch makes a task's gradient jittery: its direction swings from step to step, even though it is right on average.

Plain averaging just absorbs the noise. Loudness rebalancing occasionally turns a knob, a task's loss weight, on a bad reading but self-corrects. PCGrad sometimes cuts against a fight that was not real, which is wasteful, not dangerous.

Steering toward the worst-off task is the most sensitive: its whole decision is “who is worst off right now,” and a jittery signal sometimes makes the small-batch task look worst-off when it simply had an unlucky batch. The fixes, in rough order of importance:

  1. Oversample the small task. Going from 8 to 32 samples per step already helps a lot. No algorithmic patch beats a steadier signal.
  2. Smooth the decision signal. Keep a running average of each task's gradient, one that weights recent gradients most and forgets old values slowly (each step keeps 90 to 99 percent of the old average and takes the rest from the new gradient). Make the steering decision on that running average, and step with the real gradients. You can use this together with worst-off-task steering. The steering stays, but it stops reacting to one unlucky batch.
  3. Keep each step closer to the plain average. If you cannot oversample, limit how far the step may move away from the plain average, so one unlucky batch cannot drag the update toward a task that only looked worst-off.
  4. Log how much the gradient norm swings (its variance), not just its average. If the small task's gradient norm swings wildly over a few dozen steps, you have confirmed a shaky signal before it confuses the algorithm.

Batch jointly every step

Three layouts, and only one of them lets the methods do their job:

  1. A joint batch carries all tasks every step. This is the standard, and the layout to use. Each task produces a loss and a gradient on the shared trunk at the same weights at the same moment, which is exactly what “do these gradients fight?” and “which task is worst off?” require.
  2. Round robin carries one task per step. The methods that compare task gradients have nothing to do, with no pair to de-conflict and no worst-off task to find. Worse, round robin does not remove the conflict. It spreads it across time, as the trunk zigzags between tasks, the same back-and-forth that a too-large step causes between the walls of the ravine described in “Diagnose your failure mode first”. It removes the diagnostic, not the conflict.
  3. A random task per step is round robin, shuffled. It has the same problem and is just as incompatible with gradient-combining methods.

What your batch layout does to the algorithms

Within a joint batch, give every task an equal share, oversampling small datasets so every gradient is measured with equal reliability. The whole point is to let the gradients decide the weighting, which only works if every gradient is trustworthy.

If repeating a small dataset worries you, cap the repetition rather than shrinking its share. For example, allow no task to repeat its own data more than three times during one epoch of the largest dataset, where an epoch is one full pass through a dataset. And if a joint batch does not fit in memory, accumulate: run each task's sub-batch, the slice of that task's own data processed in this round, store its gradient, and combine once all tasks have reported. Gradient methods need all task gradients before combining anyway, so accumulation changes where you pay the memory cost, not whether you pay it.

Only bring losses that must shape the trunk

Often each team arrives with its own mature single-task model, trained with half a dozen losses. Should all of them come into multitask training? No. The trunk is the only shared, one-shot resource in the whole system. After multitask training, a team freezes the trunk (holds its weights fixed) and fine-tunes its own head privately, with whatever losses it wants. So each loss faces one question: does this loss need to shape the shared features, or can it do its job later, on the frozen trunk, inside my own head?

Extra losses are expensive. Every added loss is another gradient pulling the trunk, the cost is paid by every team, not just the one who brought it, and the loss weights a team tuned for its single-task model no longer mean anything once loudness rebalancing or worst-off-task steering is involved. The practical filter is the frozen-head test:

  1. Baseline. Multitask-train with each task contributing exactly one loss, its main loss, the one for the answer it is scored on. Measure every task's metric (such as accuracy) against its target.
  2. Frozen-head check. Freeze the trunk; each team fine-tunes its head with its full private stack. Measure again.
  3. Gap analysis. If frozen-head fine-tuning reaches the target, the extra losses were head-level and stay private. If the metric is stuck no matter what the head does, the trunk never learned something the task needs, and that loss belongs in multitask training.
  4. Admit one loss at a time, and re-run. Confirm it closes the gap, and check the other tasks' metrics did not degrade.

Two cases show the difference: a head-level loss the head can supply on its own, and a trunk-level loss the trunk must learn.

Stage

Each loss you admit is one more arrow pulling the trunk. A step against the plain average of the arrows can raise some losses. The min-norm blend, the shortest mix of the arrows with weights that are not negative and add to one, gives a step that lowers every loss, until enough losses pile up that it shrinks to zero. MGDA is built on this blend. Pairs grow faster than losses (8 losses make 28 pairs), so bring fewer, better losses.

A few habits save real time.

  1. Start with one loss per task, no exceptions. This baseline is the control group for every later decision.
  2. When a loss joins, record the other tasks' metrics and the conflict rate (the share of steps where a pair's cosine is negative) before and after, and let those numbers settle team debates.
  3. Pre-combine a task's auxiliary losses, helper losses that are not the scored answer, with its main loss using fixed weights, so the trainer sees one loss per task.
  4. Re-run the frozen-head check after big changes. The verdict on a loss is not permanent.

When the trunk is too small, no optimizer can save it

This part matters as much as the methods. Gradient-level fixes redistribute a shortage; they do not remove it. If the shared trunk is simply too small to hold all the tasks, or the tasks genuinely work against each other, no optimizer, the rule that updates the model each step, can fix that. The limit is then set by the architecture (wider trunks, softer sharing, where tasks share only part of the trunk and keep the rest private, task-specific modules, small private parts each task keeps besides the shared trunk) and by task grouping (which tasks should share a trunk at all, so tasks that fight can be split into groups with separate trunks).

Optimization methods decide how well you use the sharing you chose; they cannot choose it for you. When a multitask setup is failing, the first question is not which optimizer to try. It is whether the tasks belong together and whether the trunk has room for them. The optimizer is the second question, not the first.

When the diagnosis points at the training itself, the fixes live on the method pages, and the introduction lists all of them side by side in “Three failures, and the pages that fix them”.
