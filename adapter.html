Adapters

Fine-tuning without the fine-tuning bill.

On this page

How do you teach a giant model a new trick without retraining the whole thing? You know me, I do not like paying for compute twice.

Full fine-tuning a transformer is simple and brutal. A transformer is a stack of blocks that processes a sequence, where each block first lets the positions exchange information with each other and then processes each position on its own, and that stack is the model this whole page modifies. You take all 110 million parameters, the learned numbers that make up the model's weights and that training adjusts, you update all of them, and you keep one full copy of the weights per task. Ten tasks means ten copies of the model on disk. Worse, the optimizer keeps two extra numbers per parameter (Adam momentum and variance, where Adam is the optimizer that runs training and those two numbers are a running average of the direction each parameter has been moving and a running measure of how spread out its recent steps have been), so training needs roughly three times the model size in GPU (graphics processing unit, the chip that trains large models fast) memory just to hold the state. And there is the quiet part nobody likes to admit: the model learns your new task and starts forgetting the old ones. That is catastrophic forgetting, and it is exactly what it sounds like.

Adapters flip the deal. Freeze the big model, bolt on tiny trainable modules, and train only those. The backbone never moves. You keep one frozen copy of the model and swap in a small adapter per task, like changing lenses on a camera instead of buying a new camera body.

Bottleneck adapters add tiny trainable layers

The original idea (Houlsby et al.) is almost embarrassingly simple. Inside each transformer layer, after the attention block, where each position mixes in information from the other positions, and after the feed-forward block, which processes each position on its own without mixing anything across positions, you insert a small two-layer MLP (multilayer perceptron) with a bottleneck. The hidden state, the vector of numbers that carries one position's information through the layer, is 768 numbers wide. You squeeze it down through a 64-wide hallway and expand it back. The squeeze is the whole trick: the hallway is the only thing that learns.

The authors were trying to solve the many-tasks problem. A pretrained model is one that was already trained beforehand on a large general body of text, so its weights already carry useful language knowledge before any task training starts. Fine-tuning a large pretrained model works well, but it is parameter inefficient: with many downstream tasks, the later tasks the pretrained model gets adapted to after its general training, you need an entire new copy of the model per task.

Their alternative is transfer with adapter modules. The base network stays frozen, each task gets a few small trainable modules, and new tasks can be added without revisiting the old ones.

They demonstrate it by transferring BERT (Bidirectional Encoder Representations from Transformers, a large pretrained language model that had already learned from general text) to 26 diverse text classification tasks including GLUE (a standard suite of language-understanding tests): adapters land within 0.4% of full fine-tuning while adding only 3.6% parameters per task, against 100% for fine-tuning. That is the idea this whole page is built on.

Here is the entire module. Down project, pass it through a nonlinearity, a bend that treats numbers unevenly instead of just scaling them, here the ReLU bend that passes positive values through unchanged and turns negative values to zero, up project, add it back to the input so the frozen signal flows through untouched if the adapter does nothing:

class SimpleAdapter(nn.Module):
    def __init__(self, hidden_dim, bottleneck_dim):
        super().__init__()
        self.down_proj = nn.Linear(hidden_dim, bottleneck_dim)
        self.relu = nn.ReLU()
        self.up_proj = nn.Linear(bottleneck_dim, hidden_dim)

    def forward(self, x):
        return x + self.up_proj(self.relu(self.down_proj(x)))

LoRA: shrink the update, not the model

LoRA (low-rank adaptation) asks a different question. Instead of adding new modules, look at what fine-tuning actually does to a weight matrix. You start with the pretrained weight W and you end with W plus an update. The update is a big dense matrix, a matrix whose entries are filled in rather than mostly zero as in a sparse matrix, but it turns out the useful part of it lives in a tiny subspace, a small low dimensional slice of the full space of possible updates, rather than needing the whole space. So instead of learning the full update, you learn it as two skinny matrices multiplied together:

The idea is: freeze what the model already knows (W) and learn only the change, as a detour through a tiny bottleneck. A squeezes the signal down to rank r, B lifts it back up, and the two together add a small learned nudge on top of the frozen weight. The rank r is the whole budget: a smaller r means far fewer new parameters and a coarser approximation of the update.

Rebuilt from the LoRA paper's Figure 1, this picture holds the whole method.

Figure 1. Our reparametrization. We only train A and B. Reparametrization is the idea taught just above: instead of training the weight itself, you write the trained weight as the frozen W plus the learned BA detour, so the same weight gets expressed through the two small matrices. Rebuilt from Figure 1 of Hu et al. (ICLR 2022). arXiv:2106.09685

Written as one line, the effective weight is the frozen weight plus the side path:

Freeze what the model already knows and learn only the change, as a detour through a tiny bottleneck.
W + BA
Read BA as one learned update: A squeezes the input down to rank r, B lifts it back up, and the pair is added to the frozen pretrained weight W. The frozen weight plus the learned update is just a matrix again, so after training I can bake the update into W permanently and the model runs exactly as fast as the original.

The LoRALinear listing below runs this line: self.linear is W at work, and the side path that sends the input through A and then B is the BA side path, with W staying frozen and B starting at zero so BA = 0 at init. The code carries an extra scale factor that this line leaves out. That factor is alpha in the listing, used as alpha / rank: it multiplies the whole side path, so it sets how large the learned update is next to the frozen path, and turning alpha up strengthens the update without widening the rank hallway.

  1. A starts from a random Gaussian, the N(0, σ²) written on the slab: each entry drawn from a bell curve centered at 0 with spread σ.
  2. B is initialized to exact zeros: so at step one the side path contributes nothing.
  3. The plus at the top is the merge: both paths adding coordinate by coordinate.
  4. Before serving you fold BA into W once.

The r brace between the slabs is the rank, the entire budget of new parameters: r times (d + k) numbers against d times k in the full weight, where d is the size of the input and k the size of the output.

Now the numbers. Take a 768 × 768 attention projection at rank 8: A holds 6,144 parameters and B holds 6,144, so the whole update is 12,288 parameters instead of 589,824 for the full matrix, about 2 percent of the matrix it modifies. The update is a shadow of the original weight, and a shadow is all you need.

What this shows
  • 1. Input goes in at the bottom, both paths feed the plus at the top.
  • 2. The blue box on the left is the pretrained weight W: input x feeds straight through it, exactly as it did before fine-tuning.
  • 3. The lower orange slab is A, the down-projection: it squeezes the input into the bottleneck. Its σ, in the N(0, σ²) start from the list above, is the spread of the draw, a different σ from the adapter card above, where σ is the ReLU bend. The random start would be a problem except B fixes it.
  • 4. The upper orange slab is B, the up-projection: the zero start from the list above is why the model behaves exactly like the pretrained model at step one.
  • 5. The plus at the top merges the two paths.
  • 6. Training wakes the side path up from zero: B leaves zero, the loss, the number training pushes down as a score of how wrong the model still is, falls as it learns, and before serving you fold BA into W once, so inference, running the trained model to answer new inputs instead of training it, runs like a normally fine-tuned model with no extra latency, no extra waiting time added to each answer.

The code wraps a frozen linear layer and adds the low-rank path alongside it:

class LoRALinear(nn.Module):
    def __init__(self, linear, rank=8, alpha=16.0):
        super().__init__()
        self.linear = linear
        self.linear.weight.requires_grad = False   # W stays frozen
        in_dim, out_dim = linear.in_features, linear.out_features
        self.A = nn.Parameter(torch.randn(rank, in_dim) * 0.01)    # (r, d)
        self.B = nn.Parameter(torch.zeros(out_dim, rank))          # (k, r), zero so BA = 0 at init
        self.scale = alpha / rank

    def forward(self, x):
        return self.linear(x) + self.scale * (x @ self.A.T @ self.B.T)

In practice you wrap the query and value projections of each attention block and leave the rest frozen. A projection here is a learned matrix that turns each position into a new vector. The query is the vector a position uses to say what it is looking for, the key is the vector a position advertises so other positions can match against it, and the value is the vector a position offers to others if they attend to it, so adapting the query and value projections changes what positions look for and what they pass along. A quarter of one percent of the model, and it usually lands within a point of full fine-tuning on classification-style tasks. That is stupid easy and gives you a fast win.

One more thing, and it matters at serving time: the frozen weight plus the learned update is just a matrix again. After training you can bake the update into W permanently and the model runs exactly as fast as the original. No extra layers in the graph, the connected chain of layers and operations the input runs through when the model answers, no latency cost. Bottleneck adapters cannot do this (their nonlinearity blocks the merge), so they stay in the graph forever.

Compacter: cheaper matrices inside the adapter

Adapters are already small. Compacter asks whether the adapter's own matrices can be cheaper. The trick is the Kronecker product: instead of storing a big dense matrix, you store two small factors A and B and let their product stand in for it. Think of describing a tiled floor by one tile plus a repeat pattern instead of listing every tile.

The key property: each element of A scales a whole copy of B.

The authors were chasing a better trade-off than adapters alone could offer. Fine-tuning giant language models is sample inefficient, needing many training examples to learn well, unstable in low-resource settings, where only a little task data is available, and wasteful, since it stores a full copy per task. Existing parameter-efficient methods either still used a relatively large number of parameters or underperformed full fine-tuning.

Compacter builds on adapters, low-rank optimization, and a construction where each adapter weight matrix becomes a sum of Kronecker products between shared "slow" weights, the common factors reused across layers, and per-layer "fast" rank-one matrices, the small factors that differ for each layer, matrices that carry only one independent direction and so can be built from a single pair of vectors, so the big matrix is built out of small shared factors that are combined in a structured way instead of being learned entry by entry.

Training only 0.047% of the model's parameters, it matches full fine-tuning on GLUE and beats it on SuperGLUE, GLUE's harder successor suite, and in low-resource settings.

An 8 × 8 factor plus a 96 × 8 factor expands to a 768 × 64 adapter matrix, but you only store 832 numbers instead of 49,152.

You never build the big matrix; you apply it with a reshape and two small multiplications:

def kron_linear(x, A, B):
    # computes x @ (A ⊗ B) without ever building A ⊗ B
    # A: (m, n), B: (p, q), x: (batch, m*p) -> (batch, n*q)
    X = x.view(-1, A.shape[0], B.shape[0])
    return (A.T @ X @ B).reshape(x.shape[0], -1)

class CompacterAdapter(nn.Module):
    def __init__(self, d_model=768, bottleneck=64, n=8):
        super().__init__()
        self.A = nn.Parameter(torch.randn(n, n) * 0.01)                       # shared factor
        self.B_down = nn.Parameter(torch.randn(d_model // n, bottleneck // n) * 0.01)
        self.B_up = nn.Parameter(torch.randn(bottleneck // n, d_model // n) * 0.01)
        self.act = nn.ReLU()

    def forward(self, x):
        h = self.act(kron_linear(x, self.A, self.B_down))   # 768 -> 64
        return x + kron_linear(h, self.A, self.B_up)        # 64 -> 768

Adapter limitations: latency, rank tuning, and overfitting

  • Unmerged adapters cost latency. Two extra matmuls, matrix multiplications, per block, every token, one unit piece of the input sequence, forever. Bottleneck adapters cannot merge, so they stay in the graph.
  • On big datasets, full fine-tuning still wins sometimes. Adapters shine when data or compute is scarce, not when you have both in abundance.
  • Adapt query and value first, skip the rest. Most of the gain comes from the attention projections; adapters on the feed-forward layers add parameters for less return on many tasks.
  • Soft prompts look sad on small models. Prompt and prefix tuning, prefix tuning being the one that adds extra learned key and value vectors set in front of the sequence in each attention layer, need a big frozen model to steer. On base-size models, LoRA beats them cleanly.
  • Frozen does not mean forget-proof. The backbone is safe, but the adapter can still overfit 500 examples, learning those few examples too closely instead of the pattern that carries to new examples. Validate like always.

Other ways to shrink the update

LoRA and Compacter are not the only way to keep the update small.

  • Prompt tuning trains a soft prompt of about 20K parameters. On base-size models it trails LoRA on SST-2, and it only pays off with a much bigger frozen model to steer.
  • Prefix tuning prepends learned keys and values to each attention layer, meaning each layer gets extra learned key and value vectors that every position can attend to, on top of the keys and values it builds from the real input, a similar parameter budget, with the same catch: it needs a big frozen model to steer.

Next: quantize the frozen 98%

Adapters shrink what you train. Quantization, storing each weight with fewer bits per number instead of at full precision, shrinks what you store: the frozen 98 percent of the model still has to live in memory at inference time. The quantization tutorial picks up where this one ends.
